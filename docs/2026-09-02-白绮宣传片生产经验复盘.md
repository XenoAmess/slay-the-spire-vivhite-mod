## 2. 可复用的生产经验

### 2.1 先划分仓库边界，再写接口

通用工具链只处理媒体字节、路径、SHA-256、时间线、证据角色、混音计划、FFmpeg 编排和
结构化审核结果；白绮仓库才处理 STS2 状态、卡牌语义、OBS/窗口预检、镜头定义和项目主张。
这样既避免把 `Vivhite`/STS2 领域词污染 xAR，也避免项目侧复制一套不可审计的媒体核心。

判定一项能力是否进入 xAR 的实用标准是：至少存在两个独立媒体项目的复用场景，API 不
依赖项目领域事实，且只验证结构/字节/时间/引用，不执行录屏、OCR、游戏控制或平台上传。

### 2.2 原始录屏必须先保全，之后所有尝试都使用新 run

OBS 使用 MKV 保存原始录屏；录制结束后立即复制到 run 目录并记录大小、SHA-256、时长、
帧率和时间基准。本次 raw 为 3,597,028,418 bytes，SHA-256 为
`C912EEA4FA3BCBC56E6DD3C0E02C03D70AF8A50E61072634AAD334E3013249DA`。

每次重试使用新的 `run_id`/attempt，保留 raw、partial、命令行、stderr、probe 和失败报告，
禁止覆盖旧文件。渲染器先写 `full-master.partial.mp4`，成功后才提升为最终文件；失败的
partial 仍是审计证据，不能因为“最后成功”而删除。

### 2.3 staged 画面不能冒充自然或语义证据

没有 API 状态、动作回执或项目语义 validator 时，镜头只能标记为
`staged`/`visual-only` 或 `hash-bound-observation`。画面中没有控制台和 overlay，只能证明
画面清洁，不能证明“这张卡确实按文案工作”。用户授权跳过暂停也只是工作流授权，不等于
独立 1.0× 审看或语义真值。

因此交付状态应拆成：capture contract、technical audit、semantic audit、human review、
signoff、export 六个门禁。技术渲染通过时，仍保持 semantic pending、signoff=false、
export=false，后续用新的自然/API 证据 run 补齐，而不是改写已封存的 MP4。

### 2.4 延迟旁白的淡化顺序是关键坑点

第一轮混音暴露出一个容易忽略的问题：如果对已经 `adelay` 的 stem 再从 `st=0` 做淡化，
淡入会消耗延迟前的静音，淡出也会落在错误的局部时间轴，导致后续旁白窗口实际无声。

正确顺序是：

```text
源 stem 局部时间轴：volume → afade in/out → adelay → amix
```

项目 renderer 和 xAR 通用 planner 均采用这个顺序，并加入回归测试，直接断言
`afade` 出现在对应 `adelay` 之前。验收不能只看 FFmpeg return code，还要在每个旁白时间窗做
PCM/响度检查。本次主片 EBU R128 为约 -19.8 LUFS，30 个旁白窗口均检测到信号。

### 2.5 短版应从同一批输入派生，而不是从签署后的 MP4 偷转码

60/30/15 秒版本各自拥有新的 EDL、filtergraph、probe、字幕、alias 和 run manifest，
但共享同一份已封存 raw、capture lineage 和旁白批次。这样可证明短版没有绕过输入哈希，
也避免对一个已审核成片再进行不可追溯的二次转码。

短版必须单独检查精确时长、帧数、编码、音频采样率/声道、最终文件与 alias/partial 的字节
一致性，以及每个旁白时间窗的信号。a4 postflight 报告将这些检查全部结构化记录。

### 2.6 工具和依赖要固定到可复现版本

生产 run 使用 xAR `v0.2.1` clean tag（commit
`fb160b1eac10cbf1758ccf729f85b14c08e0c6e9`），并记录 FFmpeg、ffprobe、OBS 的路径、版本和
SHA-256。渲染日志中保存完整 argv、filtergraph 和工具指纹；不要让本机脏工作树或未发布
私有分支成为生产输入。

### 2.7 交付包应由机器闭合，人只负责判断内容

metadata finalizer 负责把相对路径、文件大小和 SHA-256 重新计算到 run manifest、artifact
index 和 evidence coverage；它拒绝路径逃逸、缺失文件、过期哈希、run_id 不匹配和覆盖已
闭合 attempt。机器可以证明“字节和结构没有变”，但不能替人决定主张是否真实、镜头是否
好看或是否允许发布。

## 3. 下一次录制的执行清单

1. 先完成 OBS/Vulkan/窗口/overlay 预检，再创建新的 run；不复用旧 raw 的工作目录。
2. 每个 shot 立即保存 raw span、截图、`state.before/after`、动作回执和运行时 manifest；
   语义不通过时保持 RED，不修改原文件。
3. 录制、旁白、游戏声和 SFX 分轨保存；如需 BGM，单独记录授权和新 config/run。
4. 先跑 capture contract 和技术 probe，再跑白绮语义 validator，最后才进入人工 review、
   signoff 和 export。
5. 若发现错误，保留失败现场并创建新 attempt；不要为了得到绿色状态而放宽 schema 或删除
   partial。
