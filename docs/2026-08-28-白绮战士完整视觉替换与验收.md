# 白绮战士完整视觉替换与验收

## 目标与边界

- 原版 `IRONCLAD` 的视觉资源整体替换为魔法少女白绮；卡池、能量球、音频和玩法保持原样，独立角色 `VivhiteCharacter` 不受影响。
- 白绮的固定识别点为银发、紫瞳、金色眼镜、黑白蓝紫礼服、可爱而冷淡的气质；战斗表现只用魔法，不加入剑、法杖、书或其他武器。
- 运行时资源全部位于 `res://Vivhite/skins/ironclad/`。没有向原版 `res://animations/...` 写同路径覆盖，因此不会污染原资源，也便于以后让独立白绮和战士皮肤分别演进。
- 多人 point/rock/paper/scissors 四张图按用户明确豁免保留旧版本；没有第二客户端时只声明资源与离线加载通过，不冒充联机端到端通过。

## 运行时资源结构

发布器只允许下列 26 个逻辑文件，出现缺失或额外文件都会失败：

- `scenes/`：combat、merchant、rest_site、character_select 四个场景。
- `spine/combat/`：白绮私有 Spine 4.2.43 JSON、atlas、3072×2304 PNG 与 skeleton-data wrapper。
- `spine/merchant/`：只含 skeleton-data wrapper，复用白绮战斗骨骼和 atlas，而不是复用原战士骨骼。
- `spine/rest_site/`：白绮私有 Spine 4.2.43 JSON、atlas、2048×2048 PNG 与 wrapper。
- `spine/character_select/`：白绮私有 Spine 4.2.43 JSON、atlas、3713×2427 PNG 与 wrapper。
- `ui/`：顶栏头像、头像轮廓、普通/锁定选人图和地图标记。
- `multiplayer/`：四张手势图。

`IroncladReplacementAssets` 采用 fail-closed 注册：所有资源必须能以期望的 Godot 类型加载，wrapper 和场景也必须实际引用白绮私有资源；只要其中一个文件、绑定或类型有问题，就完全不注册替换，避免出现“半个白绮、半个战士”。

## 私有骨骼与动画

### 战斗与商店

- 战斗人物使用 30 根自有骨骼、345 个真正的 weighted mesh 顶点和 616 个三角形；每个顶点有三个 influence，权重和为 1。它不是把原战士持剑姿势贴成白绮，也不是逐帧整图切换。
- 精确保留八个游戏动画契约：`idle_loop`、`low_health_loop`、`relaxed_loop`、`attack`、`attack_heavy`、`cast`、`hurt`、`die`，时长与 v0.111.0 原契约一致。
- 保留 `slash_mesh`、`eye_attach_slot`，以及 `attack_slash_start`、`heavy_slash_start`、`cast_eyes_start`、`clear_vfx`。魔法波从白绮右掌发出；施法环置于人物后方；没有武器 attachment。
- 私有 combat 场景保留 `NIroncladVfx`、`SlashVfxSlot`、`EyeSlot/EyeFire`、Bounds、CenterPos、IntentPos 和原本的 shader 参数入口，只把刀剑色彩改为紫/靛/青的魔法视觉。
- 商店的第一个子节点仍是 SpineSprite，播放 `relaxed_loop`，但其 skeleton-data 指向同一套白绮战斗私有骨骼。

### 篝火

- 篝火人物使用 27 根自有骨骼和 165 个双权重顶点，以单个坐姿母源制作；姿态是低位侧坐，不复用原战士的坐姿网格。
- 精确保留 `glory_loop`、`hive_loop`、`overgrowth_loop`、`_tracks/light_off`、`_tracks/light_on`。三个章节循环首尾闭合；灯光轨道是两个可区分的静态状态。
- 场景继续保留 SelectionReticle、Hitbox、ThoughtBubbleLeft 和 ThoughtBubbleRight，避免只看到人物却无法交互。

### 选人页

- 选人人物使用 13 根自有骨骼、117 个 weighted mesh 顶点和独立魔法阵骨骼。
- `NSpineAutoPlayer` 要求骨骼恰好只有一个动画，因此这里精确导出唯一的 `animation`，时长约 5.333 秒并首尾闭合。

## 生成素材与 Alpha 规则

- 所有新增透明母源都经仓库规定的 EvoLink `gpt-image-2` 原生透明流程生成；原始付费结果、精确 prompt 和脱敏请求参数均保存在追加式归档中，即使未被选中也不删除。
- 工作脚本只允许读取模型已经给出的 RGBA、检查 Alpha、等比缩放和打包到透明画布。禁止色键、棋盘格抠图、阈值化、重建或修补 Alpha。
- 生成前必须同时检查原 atlas/spritesheet 和源码消费者；不能因为肉眼看到一张 PNG 就把四宫格手势、packed atlas 或多个 region 误认成单幅插画。

## 构建与离线验收结果

2026-08-28 使用 Godot 4.5.1 Mono、Vulkan 和游戏实际 Spine GDExtension 完成以下验证：

1. Source 契约通过：26 个文件，4 个 Spine 消费集合；combat、merchant、rest_site、character_select 均真实加载，版本、默认 skin、动画、slot 和 event 正确。
2. `dotnet build` 完整通过，无 warning/error；导出的 PCK 在安装前再次解析和验证，得到 93 个合法条目，未含 `.work/`、`bin/`、制作源或原版同路径覆盖。
3. 严格 Vulkan 批验收通过：15 个消费动画各均匀采样 5 帧，共 75 帧；0 空帧、0 裁切、0 覆盖缺口、0 自动检测问题。
4. 人工逐张检查 15 张接触表：白绮身份稳定，无武器、旧战士残片、绿边、黑块或关节翻面；魔法波从手掌发出，施法环位于人物后方，死亡姿态落地自然，篝火坐姿及灯光明暗状态正常。

离线证据保存在 `.work/ironclad-render-acceptance/`，不自动提交。离线预览能证明资源和渲染契约，但不能执行游戏程序集中的 `NIroncladVfx`，因此事件开关、真实 UI 锚点和场景比例仍必须在游戏内验证。

## 真机验收与回滚

- 先提交并推送离线成果，再通过统一 `Start-Agent.ps1` 启动游戏、brain 和 TTS，避免 brain 的异步复盘与大批未提交美术文件互相干扰。任何步骤都不得调用 Bilibili Livehime 或直播脚本。
- 选人页检查动态背景、普通/锁定图、头像与轮廓；进入战斗后由 brain 自然打出攻击并持续观察待机、受伤和状态切换，再用受控测试补齐重击、施法、低血和死亡。
- 真机重点不是“能显示”而是检查人物落点、大小、血条/意图/Bounds、右掌与魔法波起点、施法环层级、普通/重击辨识度、事件清理，以及商店和篝火在真实背景下的比例与交互节点。
- 每个动作前、中、后截图，并检查新会话 `godot.log` 中是否出现指向 `res://Vivhite/skins/ironclad/` 的 ResourceLoader、Spine、atlas、缺动画或空资源错误。
- 90 秒内不能进入主菜单、崩溃或人物不可见时，立即停止统一栈并恢复此前三件套备份；不要在坏包上继续自动点击。

## 踩坑与维护要点

- PowerShell `Set-StrictMode` 下，直接读取 JSON 不存在的可选属性会抛异常。契约验证器必须用统一的 `Get-JsonPropertyValue` 获取 `requiredText` 等可选字段，再把 `$null` 当空数组处理。
- Godot 导出的是 PNG 对应的 `.ctex` 与 `.import`，不是把源 PNG 原样塞入 PCK；逻辑文件契约与物理 PCK 条目数不同，不能把“26 个运行时逻辑文件”误写成“PCK 只有 26 个条目”。
- 独立 Vulkan 画布会按骨骼 bounds 自动适配，无法证明游戏中的实际缩放。战斗、商店和篝火比例只能由真机截图决定；如需修正优先调整私有场景的 Visuals/SpineSprite scale，不改血条、意图或交互锚点。
- 普通攻击和重击可以共用同一个魔法波 attachment，但必须在真机按事件时序检查辨识度；如果区分不足，应加强骨骼位移、蓄力或 VFX 尺度，而不是引入武器。
