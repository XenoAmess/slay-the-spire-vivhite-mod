# 2026-08-22 异步复盘队列（游玩零等待）

## 问题

同步复盘的代价：每局结束阻塞 5~25 分钟跑 opencode 复盘，游玩完全停顿。
更隐蔽的代价：复盘失败（exit=1）会触发优先模型 6 小时冷却，期间完全没有复盘。
（本次就是 ox-alpha 在一场复盘中途 exit=1 中断，冷却了半天。）

## 设计（用户提的追及队列思路）

- `_finalize` 只调 `enqueue_review`：写 `knowledge/review_queue.json` + 确保工作线程存活，立即开下一局。
- 工作线程串行消化：drain 时**一次性取走全部 pending**，一场复盘分析多局（追及）。
- 队列上限 `review_queue_max`（默认 5 批），超出丢最旧。

## 异步化的三个并发坑与对策

1. **git 竞争**：游玩线程每局 autogit 存档 vs 复盘线程的提交/回滚 →
   autogit 加全局 `threading.Lock`（`_GIT_LOCK`），所有 git 调用串行化。
2. **半成品代码被卷入存档**：复盘 agent 改代码改到一半，对局存档 `git add sts2-ascend` 会把它提交 →
   复盘激活期间（`set_review_active(True)`）对局存档只 `git add sts2-ascend/knowledge`。
3. **回滚误伤对局存档**：早期共享工作树方案无论回退整个 HEAD，还是按目录恢复/清理，
   都无法可靠区分模型 hunk 与同文件并发用户 hunk。该历史方案已废弃；当前模型在独立 clone
   内运行，宿主只导出并应用经过全仓越界扫描、自检和 allowlist 校验的精确 patch。
   回滚只接受 marker 指向的已验证单父复盘 commit，并创建受控反向 patch 提交；冲突时
   fail closed、保留现场，绝不执行全仓强制覆盖或目录清理。

## 验证

- 队列语义测试：连入 3 局 → 工作线程先消化 [1]、再把 [2,3] 合并为一批（正是追及行为）。
- selfcheck SELFCHECK OK。
- 激活方式：杀 brain 进程由 runner 自动以新代码重启（对局状态在 mod API 侧，重启无损续玩；
  仅当前局的决策日志从重启点重新计数）。

## 注意

- 复盘进行中大脑自重启（exit 42）不会发生——request_restart 只在复盘**完成后**置位，
  主循环在下一局间安全点重启，因此重启时绝无活跃复盘子进程。
- 崩溃重启的极端场景：孤儿 opencode 可能还在写 stream/文件；新进程启动时清 `reviewing` 残留标记，
  队列未消化部分会由新工作线程重新消化。
