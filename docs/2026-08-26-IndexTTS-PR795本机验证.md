生产虚拟环境中已有 IndexTTS 依赖，但没有 pytest。为避免同步或污染生产 venv，pytest 由 `uv tool run`
放在隔离工具环境中运行，并通过 `PYTHONPATH` 只读复用生产环境依赖。

执行的测试节点：


3 个 warning 来自导入的 SWIG/librosa 依赖，均为 deprecation warning，与本次改动无关。

## 精确分支 CUDA/checkpoint 实测

### 前置条件与配置

第二次测试前确认：游戏、brain、Edge TTS 和旧 IndexTTS owner 均已退出；直播姬和 OBS 仅驻留。资源快照为：

```text
GPU memory: 562 / 6144 MiB used, 5468 MiB free
GPU utilization: 12%
System RAM: about 12.7 GiB free
CPU load: about 38%
```

测试配置：

```text
PR head: 7a72015226fbf1505fedd5835bb89f494a313077
device: cuda:0
reference_device: cpu
precision: FP32 (use_bf16=False)
GPU: NVIDIA GeForce GTX 1060 6 GB, driver 582.66
Python: 3.11.13
PyTorch: 2.8.0+cu128
QwenEmotion / DeepSpeed / accel / torch.compile / custom CUDA kernel: disabled
```

Pascal 没有原生 BF16，因此没有运行会发生模拟且异常缓慢的 BF16 路径。模型代码从独立 PR 工作区导入，
checkpoint 只读复用生产 clone；测试脚本和产物位于 PR 工作区被 `.gitignore` 忽略的 `outputs/`，没有修改
PR 分支或生产 clone。

### 模型布局断言

| 组件 | 实际设备 |
| --- | --- |
| GPT / semantic codec / S2Mel / BigVGAN | `cuda:0` |
| Wav2Vec2-BERT / CAMPPlus | `cpu` |
| semantic mean / std | `cpu` |
| speaker / emotion 条件缓存 | `cuda:0` |

初始化耗时 33.969 秒；完成后 PyTorch allocated/reserved 为 4389.6/4498.0 MiB，初始化阶段峰值
allocated 为 4425.1 MiB。

### 参考条件与缓存

| 操作 | 耗时 | 峰值 allocated / reserved |
| --- | ---: | ---: |
| speaker A 首次 cache miss（15 秒 WAV，冷启动） | 19.644 秒 | 4413.6 / 4500.0 MiB |
| speaker A cache hit | <0.001 秒 | 4404.1 / 4500.0 MiB |
| 默认 emotion reference 首次 cache miss | 8.175 秒 | 4407.3 / 4500.0 MiB |
| 默认 emotion cache hit | <0.001 秒 | 4407.3 / 4500.0 MiB |
| 动态切换 speaker B 的 cache miss | 8.617 秒 | 4542.0 / 5296.0 MiB* |
| speaker B cache hit | <0.001 秒 | 4527.1 / 4876.0 MiB |
| 切换独立 emotion reference 的 cache miss | 8.229 秒 | 4530.0 / 4876.0 MiB* |
| 独立 emotion cache hit | <0.001 秒 | 4530.0 / 4874.0 MiB |

`*` `reset_peak_memory_stats()` 不会把当前已 reserved 的缓存变小；动态切换行的 reserved peak 可能继承上一条
推理已经保留的 reservation，因此该步骤更应看 allocated 和最终状态。

测试同时断言：相同路径再次调用返回同一批缓存 tensor 对象；speaker 或 emotion 路径改变时，各自缓存路径和
tensor 均正确刷新。

### 实际合成与 WAV 验收

| 场景 | 合成耗时 | WAV | 峰值 allocated / reserved |
| --- | ---: | --- | ---: |
| speaker A + 默认 emotion fallback，暖缓存 | 14.820 秒 | 2.508 秒，110636 bytes | 5157.0 / 5296.0 MiB |
| 动态 speaker B + 独立 emotion reference，暖缓存 | 13.736 秒 | 1.939 秒，85548 bytes | 5279.7 / 5662.0 MiB |

两条输出均为 22050 Hz、单声道、有限数值且非静音：

```text
default-warm-cache.wav
SHA-256 1EE0EA14DFC66F283C0CDC9E560717D679BC9399C66D3AE7659C912F469E1247

dynamic-speaker-independent-emotion.wav
SHA-256 0A3A4B335D0D0EFAF335EE4562716A89612E1FA6073434420DC6731C43EE6C2F
```

测试过程没有 CUDA/OOM 异常。最紧张时 WDDM 全局可用显存读数短暂四舍五入为 0 MiB，但推理仍正常完成；
进程退出后显存占用恢复到约 449 MiB。这个结果说明 6 GB FP32 路径能跑，但不能据此承诺与游戏或其他 CUDA
程序并发。

本轮是功能 smoke test，没有进行主观音质 A/B，也没有在同一轮强行运行历史上已超过 6 GB 容量的全 CUDA
baseline。

## 同卡真实合成证据的适用边界

本机直播 owner 使用 `upstream/main` 加 `sts2-ascend/tts/indextts_gpu.py`：它在 CPU 构造模型，生成并缓存
固定参考条件，移除 reference encoders，再把逐句推理模块移到 CUDA。该布局验证了“reference encoders
不常驻 GPU 后，6 GiB Pascal 仍可持续合成”的工程前提，但实现路径和精度设置都不等于 PR #795。

当前稳定 session（15:35:10 后）的日志统计：

| 项目 | 结果 |
| --- | ---: |
| 连续成功合成 | 99 次 |
| 合成/CUDA/OOM 失败 | 0 次 |
| 单进程峰值显存 | 3174–3289 MiB |
| 文本长度 | 2–16 个中文字 |
| 合成耗时中位数 | 17.2 秒 |
| 合成耗时 P95 | 56.7 秒 |

这组数据使用下游 FP16 wrapper 和固定缓存引用，只能标记为 downstream equivalent-layout soak，不能标记为
exact-branch checkpoint benchmark。PR 正文和评论均明确写出了这项限制。

## 第一次为什么没有强行跑第二份 GPU 模型

测试时资源快照：

```text
GPU: NVIDIA GeForce GTX 1060 6 GB
GPU memory: 5512 / 6144 MiB used, about 518 MiB free
GPU utilization: 100%
System RAM: 32 GiB total, about 3 GiB free
CPU load: about 92%
```

PR 的完整 CUDA 验证至少需要为合成模块和新的 CUDA context 留出数 GiB 显存。当时并发加载第二份模型有很高
概率导致 OOM、游戏掉帧、TTS owner 退出或直播卡顿。停止现有 owner 又会直接违反直播期间不得干扰稳定项目的
约束，所以第一次只执行了不会加载 checkpoint 的精确提交测试。用户明确确认直播和游戏停止后，才执行了上面的
独占 GPU 测试。
