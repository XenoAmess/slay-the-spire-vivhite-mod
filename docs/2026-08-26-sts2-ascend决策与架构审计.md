# sts2-ascend 决策、探索与架构审计

## 审计结论

截至本轮审计，知识库记录 554 局、0 胜。系统长期学习的总体分层方向是对的：实时 API
负责观察，确定性策略负责动作，统计库负责跨局学习，异步 LLM 负责低频复盘。但四条边界此前
不够可靠：原生事实没有进入在线策略、动作尝试与成功混账、复盘批次与实际 run 证据没有精确
关联、自动 Git 会污染共享工作树。本轮均已建立显式边界。

```text
游戏 API ──> 原生快照补全 ──> Policy 评分 ──> Decision
   │                                      │
   └── 观察态结算 <── Agent <── 回执/动作效果确认 ──> 确认后提交学习账
                              │
                              └── 原子 JSON ──> active runs / stats
                                                   │
                           可校验 compact <────────┴──> ZIP + catalog
                                                   │
                  精确 run_number 批次 + 原生事实 ──> LLM 受限复盘
                                                   │
                         私有 index + CAS + allowlist ──> 安全 Git 提交
```

## 为什么会有能量却不出打击、防御

这不是一个原因，而是八个评分、生命周期和事务缺陷叠加：

1. **格挡预留互锁**：例如敌方意图 6、已有 5 格挡、剩 1 能量时，第二张防御实际只多挡
   1 点，边际分约 0.03；旧逻辑仍因“手里存在格挡牌”给打击固定扣 8 分。防御与打击同时低于
   `play_threshold=0.4`，于是带着能量结束回合。真实日志
   `20260826-021556_G115RL55CFCC.json` 出现了该型现场，历史日志中有大量同型理由。
2. **敌方格挡被错误当作零收益**：旧攻击价值近似 `max(1, 伤害-敌方格挡)`，没有把削掉
   的敌方格挡计入有效伤害，打击面对 8 格挡常只值 1 分。
3. **选牌归因反噬执行**：某卡的跨局选牌 outcome/bias 为负时，旧代码继续给已经拿在手里且
   已支付抽牌机会的牌扣分，甚至把当前正收益牌压到阈值以下。
4. **失败动作被记成成功**：旧 Agent 在 HTTP 请求前增加 `plays` 和 credit tags；409、断线、
   签名错误也会训练统计，形成“系统认为打过，游戏实际没打”的假证据。
5. **新战斗继承上一战的“已可出牌/失败/结束等待”状态**：旧的回合身份只看回合号，同为
   T1 的下一场战斗可能被当作上一场延续，两次轮询后直接结束回合。
6. **动作端点短暂未就绪时过早结束**：手牌和能量已经显示可用，但 `play_card` 暂时没有出现在
   `available_actions`；旧逻辑只等两个 tick 就弃权。现在在仍有可支付手牌时最多等待 30 个 tick。
7. **异步僵局结论跨战斗泄漏**：上一场的 `giveup`/`offense` 分析可能在下一场落地，导致新战斗
   从第一回合开始摆烂或只攻不守。结论现与发起分析的 combat 对象身份绑定，过期结果直接丢弃。
8. **响应丢失与刷新竞争误伤当前候选**：POST 可能已执行但响应断掉；旧客户端重放会重复打牌，
   随后的 409 又会把仍合法的卡永久拉黑。现在 POST 不透明重放，`pending`/断线按动作特定效果
   对账；连续 409 只短暂冷却精确对象并轮转同屏候选。

修复后，只有一张格挡牌自身具有足够即时边际时才预留能量；攻击削掉的敌方格挡计入有效
输出；战斗执行只接收非负的 learned prior；若所有长期评分都被阈值压住，仍选择即时边际为正
的安全牌，不再白白浪费能量。卡牌 play、路线/事件/休息等 credit tags 和决策轨迹只在服务端
明确完成，或后续同局状态满足该动作的精确后置条件时提交。`pending` 只代表受理，不等于效果
已落地；断线后最多观察若干新状态，不能证明就释放为可轮转重试。参数/协议型确定性错误仍会
熔断，动画窗口、409 和断线不会污染学习账或永久封禁一个可用候选。

## 对新卡、新事物的探索意愿

旧系统确实可能永久不尝试新牌，而且旧 `seen` 不是可靠的“奖励出现次数”。评分函数在每次
轮询候选时都会增加 `seen`；基础打击/防御分别累计到 5,386/7,763 次，显然是屏幕轮询污染。
当前 149 个有统计的卡 ID 中，40 个从未拾取，4 个拾取后没有成功出牌；Ironclad 原生 90
张牌中有 10 张完全没有统计记录：`BLAZE`、`BLOOD_WALL`、`BREAK`、`CORRUPTION`、
`DEMONIC_SHIELD`、`INFERNO`、`MIDNIGHT`、`OUTRAGE`、`TANK`、`TEAR_ASUNDER`。

新机制把“评分”和“观察”分开：只有真实、可跳过的奖励 offer 才增加 `offered`，同屏重试和
重复 ID 去重；v2 可靠口径从第 554 局建立基线，旧 `seen` 保留作兼容但不再冒充曝光率。
选牌使用确定性的近优 UCB 探索：每局最多 2 次，只探索距当前最优不超过 2.5 分、原始价值
至少 1.0、拾取样本少于 2 的候选；诅咒、状态、不可打出牌、基础打防、已经实锤差的牌和
当前卡组无法触发的条件引擎不会为了“新”而乱拿。同一个 offer 的选择跨 tick 稳定。

战斗端也给“零成功出牌但当前可用且即时边际为正”的牌每场一次受控试用机会。这样既不会因
历史空白永久封印新牌，也不会牺牲明显更优的生存决策做无边界随机试验。原生卡牌快照现在会
补齐 API 省略的类型、费用、规则文本和动态数值，所以第一次见到的牌也能先做机制评分，而不
必完全依赖历史样本。

非卡牌域原来也有自锁：事件的 5% epsilon 在稀有事件有限次出现时可能永远不命中，等值遗物
稳定偏向 API 首槽，商店中无法分类的新药长期低于购买门槛。现在事件按“样本最少→原值最高→
稳定键”确定性轮转，但仅限高血、近优、非显著负收益且通过 `will_kill_player` 与历史 `hp_min`
重尾闸门的选项；样本键包含 `event_id`，不同事件的同名选项不串账。遗物只在近优且无明确负面
描述时每局试一次，未知药只在有空位、血线安全、价格低、买后仍保留金币时试购一次。所有探索
样本和配额只在最终成功回执或动作特定状态效果确认后入账；`pending`、409 和断线本身不会伪造
“已探索”。未知屏幕没有安全参数协议，因此没有增加任意动作盲探。

## 知识库 compact

应当 compact，且已经完成。559 份逐决策日志原为 42,242,819B；按最近样本、胜局、深层局、
异常局、最长/最大轨迹和楼层代表样本保留 154 份 active（约 14.88MB），其余 405 份
27.37MB 原始证据进入 2,837,641B 的可校验 ZIP。`lessons.md` 从 618 节压到 155 节，
`meta_review.md` 从 76 节压到 33 节；被移出的原文也在 ZIP 内。`stats.json` SHA256 前后
不变，第二次 apply 是精确 no-op。

压缩工具默认只做 dry-run；写入时先校验 ZIP CRC、路径安全、成员大小和逐文件 SHA256，
发布 manifest 后再次核对源文件才移除 active 副本。`run_catalog.jsonl` 可检索 active 与
archive，深读归档 run 时再次验 hash。约 40MB 的运行日志不是模型上下文或学习充分统计，
本轮只报告、不删除、不混入知识归档，避免在进程活跃时截断诊断证据。

## 原生游戏知识如何进入学习闭环

`knowledge/game/v0.111.0/` 是只读、版本化快照：

- runtime：596 卡、299 遗物、107 怪物、66 药水、57 事件、283 Power、5 角色；
- mechanics v4：2,202 个托管类型、837 个构造器、2,132 个 accessor，抽取失败 0；除 Model 全覆盖外还纳入 Commands、GameActions、Combat、卡牌引擎、Runs、Creatures、Players、ValueProps、Random、Core.Events 和四个决策关键 helper；每个成员的嵌套 `control_flow` 树保留 if/else、switch case 与分支效果映射；
- PCK：15,890 个资源目录项，以及英文/简中本地化；
- 双语 union：7,028 key，6,937 双语，91 个官方缺中文项显式回退英文；
- 额外规则：角色/卡池/遗物池/药水池、遭遇、事件、Power、Orb、词缀、升阶、战斗、
  怪物招式状态机、地图、商店、奖励、篝火、房间、解锁和运行规则。

快照绑定游戏 `v0.111.0` commit `41cef1ea`、完整 PCK SHA256
`c60f672ee7804e6aefa1e19a582fa1c80b126a7b0eef4d084d3abf110df2eab7` 和程序集 SHA256
`0861bfa1df347538d932f22d580e75420f08082792eb914e53b4882764acdbe9`。最终校验 24 pass、

证据相关的有界事实，不把 11.7MB mechanics / 19.5MB 全快照塞进每轮上下文，但给出完整 corpus 路径供精确
深读。manifest 校验失败时该层显式不可用，不会静默混用旧版 STS1/STS2 记忆。

## 架构安全与数据一致性修复

- 自动 Git 使用进程内锁和跨进程锁包住整个事务，私有 `GIT_INDEX_FILE` 从 HEAD 构树；
  不读取用户真实 index，不再 `git add sts2-ascend`。复盘先在无 remote、无 hardlink 的独立
  clone 内运行，只导出精确 allowlist patch；分支固定 symbolic-ref 身份并使用 `update-ref` CAS，
  HEAD 并发前进则从新基线重建，分支切换则拒绝。
- 普通存档、复盘变更有不同精确 allowlist。复盘失败只反向应用本次 allowlist patch；runner
  只对校验过的单父复盘 commit 创建正向 revert commit，不再 `reset --hard` 覆盖共享树。
- 本轮实际观察到旧自动 Git 把并发中的原生知识和 TTS 工作一起收入 `243947e`/`85c14e2`；
  这不是理论风险，正是上述事务隔离修复的直接证据。
- JSON 持久化由固定共享 `.tmp` 改为唯一同目录临时文件、进程内按路径串行、flush+fsync、
  原子 replace；并发压力测试保证最终文件始终是完整 JSON。
- 动作执行成为显式事务：读请求可在重新发现端口后重试，POST 永不自动重放；服务端
  `pending` 和丢失回执进入 accepted/ambiguous 状态，由同一 run/combat、精确卡牌/奖励/药水/
  选项身份的后置条件确认。刷新竞争只建立短冷却并轮转，不把临时 409 写成永久黑名单。
- HTTP 2xx 也必须是严格的 `{ok: bool, ...}` envelope；缺失/伪布尔 `ok`、失败响应缺少对象型
  `error`、截断 JSON 都按“可能已经执行但回执不可证”进入状态对账。请求体在发送前无法 JSON
  序列化则是明确本地错误，不会伪装成未知成功。宝箱只用目标遗物入库存、该精确 option 消失或
  被标记 claimed 证明领取成功，普通离屏或 sibling 变化不再误记。
- 事件、地图、篝火、商店、选牌和宝箱共享“屏幕实例 + action + 精确 option”短冷却：重复
  transient 409 或 accepted/pending 超时后先轮转同屏兄弟候选；全部候选冷却时只等待，不能
  `proceed`/skip。篝火选项若声明 `requires_target`，会从 `valid_target_indices` 选择合法且稳定的
  `target_index`；关闭商店也只有成功回执/后置条件成立后才标记本店已完成。
- `credit_tags` 明确限定为进程内事务握手流，不在重启时回放；拿牌、拿遗物和路线节点另写
  `attribution_tags`，每次变化立即进入增量 run 日志，重启后恢复并用于终局归因和连战疲劳。
- stats/policy 等 JSON 读取仅在文件确实不存在时使用默认值；瞬时 I/O 错误有界重试，畸形 JSON
  必须先成功隔离原件，否则 fail closed。Policy 的读-合并-替换与复盘 patch 共用跨进程仓库锁；
  review queue 严格校验 schema、唯一临时文件 + fsync + 原子替换，只有队列落盘成功后才推进
  cadence marker，避免一次读锁/写锁或损坏文件把待复盘批次静默清空。
- watchdog signature 现在包含生命、格挡、能量、手牌身份/费用/可用性/动态值、敌方生命/
  格挡/Power/意图和非战斗屏核心 payload，不再把“同一屏但游戏状态已变化”误判为卡死。
- 新 run 从创建时携带稳定 `run_number`。异步复盘优先按队列中的第 N 局读取 exact active/
  archive 原证据；历史旧 run 无映射时明确标记 `recent_fallback_unmapped`，禁止把最近 N 局
  冒充目标批次。

## 仍保留的技术债

`policy.py` 和 `selfcheck.py` 都是数千行单体文件，维护成本偏高；但它们承载了 500 多局形成
的大量耦合行为。在没有黄金 replay corpus 前直接按文件拆分，会把“架构整洁”变成不可见的
策略回归。本轮先修复事务边界、事实来源和可验证性；后续合理顺序是先将代表性 active/archive
runs 建成无副作用 replay 基线，再按 combat、reward、route、event 模块拆 Policy。

历史 `seen` 污染无法从聚合值精确反演，v2 `offered` 必须从第 554 局以后重新积累。历史 run
也没有 `run_number`，只能对新日志保证精确批次关联；系统现在会显式暴露缺口，而不是伪造
确定性。这两项是有版本边界的数据迁移，不应通过猜测回填。

隔离 clone 不是操作系统权限沙箱：全仓指纹可发现绝大多数直接逃逸，却不能彻底阻止延迟子进程，
也无法判源被排除的合法在线数据路径。若未来把复盘模型视为恶意代码，需要额外的 Windows 文件
权限/进程沙箱。当前 push 为维持既定事务不变量仍在仓库锁内，连续网络超时最坏会占锁约 380 秒；
这是可用性而非数据完整性风险，后续应改为 commit CAS 完成后由锁外队列推送。

ambiguous POST 的观察上下文和 UI 冷却刻意是进程内状态：持久化它们会在重启后回放一次性握手，
造成更危险的假成功；代价是进程恰好死在“请求已到游戏、效果尚未出现在 GET”窗口时，只能从
重启后的实时页面重新判断，无法百分之百证明旧请求是否执行。当前用动作特定后置条件、精确目标
冷却和不持久化学习 credit 把风险限制为保守重试，不把不确定性写进长期模型。
