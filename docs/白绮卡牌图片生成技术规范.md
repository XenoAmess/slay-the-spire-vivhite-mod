# 白绮卡牌图片生成技术规范

> 状态：生产规范，生成前门禁
> 最近更新：2026-08-31
> 适用范围：白绮卡牌的完整插画、运行时卡图准备、验收与接入
> 上位文档：[白绮 AI 生成图 Prompt 工程手册](白绮AI生成图Prompt工程手册.md)

## 1. 核心结论

白绮卡牌图片是**带完整场景背景的单幅成品插画**，不是角色抠图、透明 VFX、Sprite、
Spine attachment、atlas page 或多格 spritesheet。

生成链按最终消费者是否真正需要 Alpha 分流：

| 最终素材 | 生成方式 | 背景要求 |
| --- | --- | --- |
| 完整卡牌插画、场景图、封面式成品 | **Codex 原生图像生成能力** | 不透明、满幅、有叙事场景 |
| 明确由运行时单独叠放的 Sprite、Spine 部件或透明 VFX | EvoLink `gpt-image-2` 原生透明链 | API 参数 `background: "transparent"` |

以下做法一律禁止：

- 用 EvoLink 透明链生成完整卡图；
- 先生成透明人物，再用程序、蒙版或另一张图补背景；
- 因为“以后也许方便抠图”就把完整卡图判成透明素材；
- 让透明卡图进入运行时后依赖卡框底色填空；
- 用平面渐变、黑色虚空或单层光晕冒充场景背景。

只有源码或场景证明最终资源需要独立 Alpha 叠层时，才允许进入透明生成链。白绮卡牌
当前没有这种需求。

## 2. 运行时消费契约

### 2.1 资源类型

- 每张卡消费一张独立 PNG；
- 不是 atlas，也没有 region、bone、slot、pivot 或动作帧；
- 卡牌模型通过 `CustomPortraitPath` 指向自己的图片；
- 尚未完成专属插画的卡继续使用 RitsuLib 内置占位图，不用临时透明人物替代；
- 三张初始牌的计划路径为：
  - `res://Vivhite/images/cards/LuminousProjection.png`
  - `res://Vivhite/images/cards/ClosedDomainMapping.png`
  - `res://Vivhite/images/cards/VivhiteTransformation.png`

### 2.2 运行时文件契约

运行时卡图统一为：

- 尺寸：`1000×760`；
- 比例：`25:19`；
- 格式：PNG，RGB8，不携带 Alpha 通道；
- 画面：背景满幅延伸到四边，不留透明边、棋盘格、纯色抠图底或未完成区域；
- 图片中不包含卡框、费用、卡名、类型条、规则文字、升级标记或其他 UI。

若 Codex 原生返回 RGBA，必须先确认所有 Alpha 都为 `255`，再确定性转换为 RGB8。删除一个
恒为 `255` 的冗余通道只是运行时像素格式适配，不属于抠图或 Alpha 修补。若存在任何非
`255` Alpha，则不能用转换隐藏问题，必须判生成结果不符合“不透明完整图”契约。

### 2.3 源码与现有资源证据

- `VivhiteCard` 自身不覆盖 `CustomPortraitPath`，因此未配置专属图的卡由 `ModCardTemplate`
  回退到 RitsuLib 内置 `card_art_placeholder`；
- Godot 通过每张 PNG 自己的 `.import` 直接导入纹理，没有卡图 atlas、region 或 Spine 消费；
- 仓库既有 `VivhiteStrike.png` 与 `VivhiteDefend.png` 均为 `1000×760`、8-bit PNG color type 2，
  即 RGB8；这证明卡图消费者不要求透明通道；
- 三张初始牌的专属路径只应由各自卡模型覆盖，其余 58 张卡继续回退占位图。

### 2.4 生成母版与确定性裁切

Codex 原生生成时要求横向、约 `3:2` 的高分辨率完整插画。原始返回图必须原样保存；运行时
版本从原图中央取能够容纳 `25:19` 的最大矩形，再使用 Lanczos 缩放到 `1000×760`。

若源图为 `2512×1680`，固定裁切为：

```text
source rect: x=156, y=4, width=2200, height=1672
target:      1000×760
```

其他源尺寸按相同的“最大居中 `25:19`”规则计算，不得按人物 Alpha、脸部位置或每张图的
视觉包围盒单独自动居中。构图问题应在生成阶段解决，不能靠每图不同的后处理掩盖。

## 3. 满幅场景背景规范

### 3.1 背景不是装饰填充

每张完整卡图至少要同时具备：

1. 前景：与施法动作相关的局部光、碎片、遮挡或空间框景；
2. 中景：白绮与本牌的主要魔法结构；
3. 远景：能够说明地点、空间尺度和透视方向的真实场景。

背景必须参与牌义：攻击的环境被方向性魔法切开或照亮，防御的环境在闭合边界外承受冲击，
能力的环境围绕人物形成升华和变身秩序。只在透明人物后铺渐变、星点或一圈光，不算场景。

### 3.2 满幅与安全区

- 场景、光照和色块必须自然覆盖最终 `1000×760` 全画布；
- 关键脸部、眼镜、双手、牌义核心与魔法端点放在最终画面的
  `x=80..920, y=50..710` 内；
- 最重要的脸、手势与魔法核心优先放在 `x=120..880, y=80..660` 内；
- 外围 `80 px / 50 px` 允许被卡框轻微遮挡，但只能放可牺牲的背景和次要光效；
- 攻击的光束可以形成继续向外的动势，但可见尖端必须在安全区内完成，不能被图片右缘截断；
- 不再使用“所有可见像素必须塞进中央 70%”的透明 vignette 规则。完整卡图的背景本来就
  应该触及四边，安全区只约束不可丢失的叙事信息。

### 3.3 场景一致性

三张初始牌属于同一个视觉世界：冷色星术、数学几何、白金结构、深靛空间与少量金色秩序线。
可以改变地点和镜头，但应保持：

- 同一白绮身份：短银发、冷紫瞳、圆形金框眼镜、蓝蝶、白／深靛／紫／金魔法少女服装；
- 同一绘制语言：精致二次元幻想卡牌插画，空间和材质经过绘制，不是角色商品渲染；
- 同一魔法体系：几何、星图、投影、闭域、轨道和变换；
- 同一人物气质：可爱、华丽、克制、冷静，不靠狰狞表情表达强度；
- 空手施法，不使用剑、法杖、魔杖、书本或其他武器、工具和持握道具。

## 4. 攻击、防御与能力的视觉语法

卡名、文字、边框和颜色隐藏后，仍必须能从轮廓与动势判断卡牌用途。

| 类型 | 主轮廓 | 空间动势 | 场景响应 | 禁止混淆 |
| --- | --- | --- | --- | --- |
| 攻击 | 开放三角、箭头、斜线、锐角投影 | 从白绮向敌方明确射出，强烈非对称 | 远景透视、尘光或几何结构沿出射方向被切开 | 不得形成包围人物的完整球壳 |
| 防御技能 | 闭合圆、球壳、穹顶、连续边界 | 向内维持，稳定居中 | 冲击和碎片停在边界外，内部空间保持完整 | 不得有穿出护域、指向敌方的主光束 |
| 自身能力 | 竖轴、星冠、同心轨道、向上展开 | 围绕自身重组与升华，相对对称 | 背景建筑、星图或光柱沿竖轴响应 | 不得像护盾封闭，也不得像攻击射线命中远处 |

颜色只能辅助，不能承担区分职责：

- 攻击：高对比白蓝光核、紫色锐边、深色纵深；
- 防御：靛蓝／青蓝主体、白金闭合边界、外部冲击亮点；
- 能力：白金／紫色升华轨道、纵向星光、深蓝星术背景。

首轮还应制作去色缩略图；若去色后只能靠卡名或类型边框区分，视觉语法失败。

## 5. 三张初始牌的生成规格卡

### 5.1 弦光投影 `LUMINOUS_PROJECTION`

**牌义读法：攻击，开放、向外、精确投射。**

- 场景：具有明确纵深的夜间星术回廊、悬浮几何观测台或开阔魔法都市高处；不得是空白虚空；
- 人物：白绮位于中左区域，三分之四视角，双手完整可见，空手拉出弦状光并建立投影面；
- 主魔法：从投影面向 screen-right 射出单一白蓝锐光，开放三角与平行投影线清晰；
- 背景响应：远景透视线、悬浮晶体或星图被出射光统一带向右侧；
- 构图：光束尖端在最终 `x<920` 结束，右缘仍有场景，不得贴边或被截断；
- 禁止：闭合护球、武器、红色攻击编码、嘴部异物、空场景透明底。

### 5.2 闭域映射 `CLOSED_DOMAIN_MAPPING`

**牌义读法：防御，闭合、包围、冲击被阻断。**

- 场景：星术观测厅、几何穹顶室或被魔法风暴包围的平台；远景必须可见；
- 人物：白绮稳定居中，双手向内维持一层完整球形或穹顶式几何边界；
- 主魔法：闭合边界连续可追踪，中心内外关系明确，不能画成朝敌人射出的炮口；
- 背景响应：外侧风雨、晶体碎片或来袭光痕在边界处停止、折射或偏转，内部平静；
- 构图：闭域完整落在安全区，外部场景继续满幅延伸到四边；
- 禁止：从球体穿出的主光束、开放箭头主轮廓、只画人物抱着一个透明球而没有场景。

### 5.3 白绮的变身式 `VIVHITE_TRANSFORMATION`

**牌义读法：能力，自身升华、纵向变换、持续强化。**

- 场景：竖向星术圣堂、数学天象仪核心、无限上升的几何仪式空间；
- 人物：白绮居中、相对对称，姿势克制，完整双手围绕胸腹间的星核施法；
- 主魔法：竖向星核、星冠和多层同心轨道围绕自身重组，能量向上展开；
- 背景响应：高处星图、光柱、建筑线或悬浮公式式几何随竖轴向上延伸，但不出现可读文字；
- 构图：人物是变化中心，轨道不闭合成防御球壳，也不形成射向敌人的命中线；
- 禁止：敌方目标、冲击碰撞、护盾受击、横向攻击束、透明空底。

## 6. Prompt 技术契约

完整卡图使用 Codex 原生图像生成能力，一张牌一次独立调用。Prompt 必须明确写场景；不得沿用
透明素材的“isolated vignette / no environment / empty canvas”语言。

推荐骨架：

```text
Use case: stylized-concept + identity-preserve
Asset type: one complete opaque full-bleed game card illustration, artwork only

Runtime contract:
The source will receive one deterministic centered 25:19 crop and a resize to 1000x760.
The painted environment must cover the entire frame. Keep all critical face, hands,
spell core and directional endpoints inside the stated safe area.

Input images:
Image 1 defines identity and costume family only.
Image 2 defines face, glasses, hair and temperament only.
Image 3, when used, defines only the approved action topology; it does not define background.

Scene/backdrop:
<具体地点、前中远景、透视、场景如何响应牌义>

Subject and action:
<白绮身份、姿势、双手、空手施法、视线与牌义动作>

Visual grammar:
<攻击开放向外 / 防御闭合向内 / 能力纵向升华>

Composition and lighting:
<人物位置、镜头、焦点、安全区、场景满幅、明暗层级>

Constraints:
No card frame, UI, text, number, equation, pseudo-glyph, logo, signature or watermark.
No weapon, held prop, second character, duplicate limb or cropped critical hand.
No mouth-adjacent red line, strand, ribbon, liquid, blood or mouth-emitted magic.
```

Prompt 不写模型名、内部工具参数或不存在的文件格式控制。身份参考和动作参考必须逐张声明职责；
不得把透明候选的空背景当成新场景参考。

## 7. 生成、归档与额度

### 7.1 Codex 原生生成归档

Codex 原生生成结果保存到追加式目录：

```text
assets/vivhite-ironclad/generated/codex-native/YYYY-MM-DD/
  <card-id>-attempt-XX/
    original.png
    prompt.txt
    generation.json
    inspection/
```

其中：

- `original.png`：原生工具返回的未经后处理原图；
- `prompt.txt`：逐字完整 Prompt；
- `generation.json`：只记录能够验证的事实，例如提供方为 `codex-native`、日期、卡牌 ID、
  尝试编号、参考图仓库路径、原图 SHA-256 和验收状态；
- 不臆造不可见的内部模型 ID、采样器、seed、token 或请求参数；
- `inspection/`：确定性裁切、原色／灰度缩略图、卡框截图和验收记录；
- 原图、失败图和不采用候选均不得覆盖或删除。

### 7.2 尝试上限

同一张卡的同一视觉语义最多 8 次生成。每次返回后立即验收；下一次只能针对一个主要失败点，
例如背景不成场景、攻击端点被裁、闭域不闭合或能力误读成防御。不同卡可以一牌一代理并行，
同一张卡的重试必须串行。

## 8. 验收门禁

### 8.1 原图门禁

- 是一张完整、满幅、不透明场景插画；
- 背景具有前中远景和空间叙事，不是渐变、透明虚空或人物商品图；
- 白绮身份、蓝蝶、眼镜、服装和气质正确；
- 双手和牌义核心清楚，没有武器、第二人物、重复肢体、文字或水印；
- 嘴边没有红线、猩红丝带、液体、血丝或从口中延伸的魔力；
- 攻／防／能力轮廓符合对应视觉语法。

### 8.2 运行时转换门禁

- 原图保持不变，另存确定性 `25:19` 中央裁切；
- 输出严格为 `1000×760 RGB8` PNG；
- 若原生输出带 Alpha，转换前已证明所有像素 Alpha 均为 `255`；
- 重要脸、手、魔法核心和端点没有被裁切或卡框遮挡；
- 不做逐图人物检测、自动重心居中、内容感知裁切、补画或 Alpha 清理。

### 8.3 可读性门禁

同一张运行时图至少检查：

1. `1000×760` 原色图；
2. `1000×760` 灰度图；
3. `250×190` 原色与灰度缩略图；
4. `100×76` 原色与灰度缩略图；
5. 真实游戏卡框、手牌缩略状态和放大查看状态。

隐藏卡名和类型边框后，应仍能判断：弦光投影“向外射出”、闭域映射“闭合包围”、
白绮的变身式“自身向上升华”。

### 8.4 代码与真机门禁

- `CustomPortraitPath` 只覆盖已经有专属图的卡；
- 其他卡仍严格回退 RitsuLib 占位图；
- 自动测试校验路径存在、PNG 签名、`1000×760` 和 RGB8 color type 2；
- 完整构建后在 Vulkan 真机查看三张牌同屏、单张放大、手牌缩放和实际卡框裁切；
- 真机截图是生产通过的必要证据，不能用透明直显或独立 PNG 预览代替。

## 9. 现有初始牌透明批次的处置

`0108–0117` 是在消费契约尚未纠正前走 EvoLink 透明链生成的卡图尝试：

- `0108–0114` 包含嘴边猩红长条、错误“謦欬”视觉化或其他已记录问题，只作审计；
- `0115–0117` 已消除嘴边红线，攻／防／能力轮廓方向基本成立，但仍是透明人物与魔法
  vignette，没有场景背景，属于**素材类型错误**；
- 三张都不得作为运行时卡图；
- `0115–0117` 最多只能作为动作拓扑参考，其中 `0115` 的光束贴右缘问题不得继承；
- 它们不计入 Codex 原生不透明卡图的新尝试编号，但历史 EvoLink 请求与额度记录保持不变。

这次纠正不是删除旧结论：透明批次证明了类型视觉语法可行，同时证明“视觉语法正确”不能
弥补“消费者素材类型错误”。下一轮必须从本文的完整场景契约重新开始。
