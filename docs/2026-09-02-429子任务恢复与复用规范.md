# 429 中断的子任务恢复与复用规范

## 目的

模型 provider、OpenCode/Codex、远程 API 或任务调度器返回 HTTP 429 时，通常表示暂时限流，而不是本次工作内容错误。**只有服务端明确允许重试的 429 才按本规范恢复；硬配额耗尽、账户停用或明确永久拒绝另行判定。**项目应尽量让原子进程在等待后继续，而不是丢掉上下文、重复启动一个代理或把已有部分结果判成失败。

本规范适用于：

- Codex/GLM/Luna 等复盘子进程；
- 宣传片 TTS、媒体分析和渲染辅助子任务；
- 其他由主代理拆分出来、具有 canonical task identity 的长期工作。

它不改变游戏 API 的业务语义，也不把 429 当作录制素材或宣传主张的证据。

## 判定与优先级

按以下顺序处理：

1. **确认是 429**：保存原始响应/事件、HTTP 状态、`Retry-After`、provider/model、task ID、attempt ID 和时间戳。只凭“进程退出”或普通 `error` 文本不能擅自归类为 429。
2. **确认原任务身份并立即恢复**：检查 canonical task name、session、工作目录、输出路径、锁、checkpoint 和已有部分结果。主代理直接安排恢复，不因可重试 429 再向用户等待确认；若原子进程仍存活，先复用它；不要再开第二份。
3. **等待后续**：优先采用服务端 `Retry-After`；缺失时采用有上限的指数退避加随机抖动。等待由单一调度器负责，不能多个线程/代理同时唤醒同一任务。
4. **原地续作**：使用同一 prompt/上下文、模型亲和性和 evidence lineage，通过 follow-up/resume 入口继续。能从 checkpoint 续写时，只追加缺失输出；不能从 checkpoint 续写时，启动同一 canonical task 的新 process attempt，并保留旧 partial。
5. **有界收敛**：首次 429 就保全 partial、transcript 和响应摘要；每次恢复写入 `resume_attempt`、等待原因、恢复结果和新的 checkpoint。达到项目规定的有界恢复次数、收到明确永久拒绝，或原身份/证据无法安全绑定时，停止主动请求并转入失败保全和人工诊断，但不删除或丢弃原队列任务。

## 不允许的做法

- 429 后立即并行 spawn 同一部件的多个代理；
- 未读取 `Retry-After` 就连续重试，或用忙等消耗额度；
- 把 429 直接标记为语义失败、`blocked`、永久 cooldown 或“无成果”；
- 用另一模型/另一任务名无记录地接管原任务；
- 覆盖原始 prompt、partial、transcript、日志、manifest 或已验收的中间文件；
- 因一个复盘/媒体子任务限流而停止不相关的训练、录制或审计轨道。

## 最小审计记录

每一次恢复至少记录：

```json
{
  "event": "resume_after_429",
  "canonical_task": "<原任务身份>",
  "session_id": "<session>",
  "attempt": 2,
  "provider": "<provider>",
  "model": "<model>",
  "status": 429,
  "retry_after_seconds": 30,
  "resume_mode": "same_task_followup|same_task_checkpoint|same_task_new_process_attempt",
  "previous_partial": "<相对路径>",
  "result": "resumed|deferred|exhausted",
  "timestamp": "<UTC ISO-8601>"
}
```

`retry_after_seconds` 没有服务端值时必须明确记录为本地退避值及其策略；不得写入凭据或完整授权头。恢复记录与原任务的 transcript/失败包一起保全，便于确认是否重复计费、是否发生上下文丢失以及最终成果由哪一次 attempt 产生。

## 与本仓库生命周期规则的关系

- 复盘队列的 `retry_group`、模型亲和性和失败包 lineage 继续有效；429 恢复不得绕过现有证据绑定、私有 index/CAS、自检、提交和推送门禁。
- provider 适配器必须把结构化 HTTP 状态和 `Retry-After` 暴露给宿主；在适配器只能看到未分类 `error` 的旧版本中，不得猜测为 429，也不得宣称已经执行本规范。
- `Stop-Agent.ps1` 或用户明确停止时，恢复等待必须响应 stop sentinel；停止优先级高于继续请求。停止后下一次启动仍从耐久队列/失败包恢复，不手工改 `knowledge/`。
- 429 只描述 provider 运输层状态。即使恢复成功，也必须分别通过代码自检、技术审计、语义审计和人工审核，不能把“provider resumed”写成发布批准。

## 操作示例

```text
provider → 429 + Retry-After: 45s
        → 保留原 task/attempt/transcript
        → 单一调度器等待 45s（含上限与 stop 检查）
        → follow-up 原 task，复用原模型和输出目录
        → checkpoint/partial 增量写入
        → 成功则继续原验收；再次 429 则递增 resume_attempt
        → 达到上限才进入失败包和后续人工诊断
```

该策略的核心是“复用身份、保留证据、单路退避、有限重试”，而不是无条件无限重试。它同时适用于白绮宣传片和其他项目，属于通用工作流规则，不把白绮领域知识写进工具链核心。

## 本次会话的验证

本次工作中一个子任务确实因 429 中断。主代理没有新建同部件的重复代理，而是用原 canonical task 的 follow-up 入口续接；任务从已有上下文继续完成，只读审查结果和 lineage 保持不变。这验证了“先复用、再考虑替代”的调度顺序。该过程没有把 429 误记为语义通过，也没有覆盖原有输出。
