## 真机验证范围

游戏日志对 `STS2-RitsuLib` 和 `Vivhite` 均记录 `user has not yet seen the mods warning`。本机首次启动时，游戏将两者识别为已安装但跳过加载。玩家在原生界面同意后，游戏会保存设置并主动退出。下一次用 Steam 离线和 Vulkan 启动时，先核对 RitsuLib 的兼容模块和 `Vivhite initialized.` 日志，再检查白绮选人页、初始遗物与首场战斗。以上结果仅覆盖正式版 v0.111.1。

## 依赖清单字段

用 v0.111.1 的游戏原生解析器读取修复前的 `Vivhite.json`，得到依赖 ID `STS2-RitsuLib` 和空的最低版本。该版本的 `ModDependency` 读取 `id` 与 `min_version`。旧清单使用 `version` 记录 RitsuLib `0.5.14`，因而只触发依赖存在校验。要由游戏强制最低版本，发布清单与构建写入逻辑需要使用 `min_version`。[白绮发布清单](../Vivhite/Vivhite.json)

## 2026-11-26 修复与复测

1. **构建降级依赖。** 用 NuGet 的真实 `CopyRitsuLibPackageModFiles` 目标复现。旧的默认完整构建把 `0.6.16` 运行库的根 DLL 和清单覆盖为 `0.5.14`，并留有 `0.6.16` 的 `compat/` 与 `shared/`。`RitsuLibAutoCopy` 现默认关闭，显式传 `true` 仍可部署锁定的 NuGet 包。本机完整 Release 部署前后，已安装 RitsuLib 的 24 个文件路径和 SHA-256 一致。
2. **最低依赖版本未生效。** 发布清单、构建同步和 Workshop 预检现使用 `min_version`，最低版本为 `0.5.14`。v0.111.1 原生解析器确认新清单的版本值。将隔离测试清单的最低版本提高到 `9.0.0` 后，游戏加载器确实拒绝以 `0.6.16` 加载白绮。

完整验收 **69 项通过，0 项失败**。Release 构建和 PCK 验收通过，且已部署的 DLL、JSON、PCK 与已验证候选逐件哈希一致。

隔离 Godot 进程使用本机 v0.111.1 的 `sts2.dll`、原生 `ModManager` 与游戏 PCK，并在临时测试设置中启用两项 Mod。原生加载器报告 RitsuLib 和 Vivhite 均已初始化，`ModelDb` 收录了白绮、61 张卡、4/4/1 的初始牌组及使用旧存档 ID 的孤高冠冕。隔离宿主使用 Godot 编辑器构建，日志含 RitsuLib 调试 C# 源文件查找信息。Steam 客户端仍离线。真实游戏窗口已重启并识别修复后的清单，首次 Mod 加载确认及 Vulkan 选人画面、完整首战仍待交互桌面可用和档案同意。
