# 白绮初始卡图生成与接入

## 结果

弦光投影、闭域映射和白绮的变身式已完成首轮完整场景图。每张牌只调用一次 Codex 原生图像
生成，没有调用 EvoLink，也没有重试。三张原图都是真正的不透明 RGB8 场景，而不是透明人物
vignette；因此背景、空间透视和卡牌语义在同一张图内完成。

视觉分工已经落到画面结构，而不是只靠边框或颜色：

- 弦光投影：人物位于左侧，几何投影面与光束向右展开，形成开放、定向的攻击轮廓；
- 闭域映射：人物稳定居中，完整连续的球壳向内闭合，外部碎光在边界停止或偏转；
- 白绮的变身式：人物、腹前星核和上方星冠形成纵向轴线，多层轨道围绕自身升华。

三张图都遵守白绮身份、空手施法、无武器、无文字和单一人物约束。嘴部自然闭合，脸旁没有
红色长条、血丝、液体或从口中发出的魔力。

## 技术接入

原生图统一归档在：

`assets/vivhite-ironclad/generated/codex-native/2026-08-31/`

每个目录保存 `original.png`、逐字 `prompt.txt`、事实型 `generation.json` 和确定性检查图。
原图均为 `1536×1024 RGB8`。`tools/art/prepare_vivhite_card_portrait.gd` 执行以下固定转换：

1. 拒绝任何 Alpha 小于 255 的源图；
2. 从中心取得最大整数 `25:19` 矩形，本批统一为 `x=105, y=8, 1325×1007`；
3. 使用 Lanczos 缩放到 `1000×760`；
4. 保存为 PNG color type 2 的 RGB8 文件；
5. 不覆盖既有目标，不做补画、抠图、蒙版或 Alpha 清理。

三张运行时资源由对应基础卡自身覆盖 `CustomPortraitPath`；其余 58 张白绮牌继续使用 RitsuLib
占位图。验收测试同时检查“恰好 3 张自定义／58 张占位”、资源路径、PNG 签名、尺寸、位深和
RGB8 color type。

## 经验与后续门禁

这轮再次证明，先查消费契约比先选生成服务重要。完整卡图的消费者需要一张独立不透明 PNG，
因此透明生成能力并不是优势；把人物与魔法单独透明化反而会丢掉背景叙事。EvoLink 继续只服务
确实需要 Alpha 的独立部件和叠层。

静态预览不能代替游戏卡框。当前三图只标记为
`static_accepted_pending_game_validation`。完整构建后还需在 Vulkan 真机检查三张同屏、单张放大、
手牌缩略和边框裁切；特别关注弦光投影的右侧尖端是否离边框足够，以及规则文字是否遮挡关键手势。
