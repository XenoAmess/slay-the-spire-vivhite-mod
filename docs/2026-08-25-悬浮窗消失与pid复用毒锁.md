# 2026-08-25 直播悬浮窗消失：pid 复用毒锁与心跳锁

## 现象

直播悬浮窗（ASCEND-VISION）从屏幕上消失，手动拉起也活不长。
期间叠加了上一轮"焦点修复"的清理误杀，观测互相矛盾、数度误判。

## 根因链（三层）

1. **直接原因**：viewer 只在复盘开始时由大脑拉起；中途被杀（清理/崩溃）后，
   本场复盘内无人补位——直到下一场复盘才恢复。
2. **深层：pid 复用毒锁**。viewer 单实例锁是 pid 判活式：锁文件存 pid，
   新实例 OpenProcess 该 pid 判活。**Windows 会快速复用 pid**，而本生态
   常驻几十个 python 进程——陈旧锁的 pid 被自家 python 复用后，
   `_pid_alive` 误判"锁持有者活着" → 新 viewer 全部被挡退 → 永久锁死。
   第一版加固（QueryFullProcessImageName 校验映像名）也无效：
   复用者往往就是自家 python，映像名同为 python。
3. **连带 bug**：SELFCHECK 金闪颜色算式未钳制（k>1 时分量溢出成 7 位 hex），
   `TclError: invalid color name "#ffd111d"` 每帧刷 viewer_exc.log。

## 修复：心跳锁（mtime 即生命信号）

- 持有者每 5s `LOCK_FILE.touch()`（帧循环里顺手做）；acquirer 看 mtime：
  `<15s` = 活，拒绝；`≥15s` = 死锁接管（unlink + O_EXCL 重建）。
  **pid 复用彻底无关紧要**——判活依据从"pid 是谁"变成"锁最近有没有心跳"。
- 保留 O_EXCL 原子创建 + 失败拒绝（fail-closed）。
- speaker/quipper 的同名 `_pid_alive` 判活同样有此弱点，已一并加固映像名校验
  （它们后续也应迁移心跳锁）。

## 观测性补全（本次排查的最大障碍是"死得无声"）

- **启动轨迹**：viewer_boot.log 记录 main-entered → init-start → tk-created →
  ui-mapped → init-done → run-entered → frame-first 全链路——卡在哪一目了然
  （py-spy 不支持 Python 3.14，抓不了栈，这是替代手段）。
- **stderr 落盘**：`_launch_viewer` 改重定向到 viewer_err.log（原 DEVNULL 吞掉
  一切崩溃 traceback）。
- **main 退出尸检**：Viewer 异常退出时 traceback 追加 viewer_exc.log（此前
  静默 release_lock）。
- **金闪钳制**：`k = max(0, min(1, ...))`。

## 验证

- boot 轨迹七里程碑全贯通；锁心跳 0s；截图确认悬浮窗覆盖在全屏游戏上方；
  大脑拉起的重复实例被锁正确挡退（boot 日志只留 main-entered 一行即退出）。

## 排查方法论教训

1. **工具会话会清理会话内启动的进程**——用 shell 起的 viewer 活不过工具调用
   结束，造成"viewer 反复生灭"的假象。要观测长生命周期进程，用 WMI
   `Win32_Process.Create` 启动（脱离会话作业树），或直接观察大脑拉起的实例。
2. **pid 判活锁在进程高 churn 环境不可用**——pid 复用是 Windows 常态；
   心跳（mtime）是唯一可靠的生命信号。
3. 观测互相矛盾时，先给目标进程加**里程碑轨迹日志**，再谈推理。
