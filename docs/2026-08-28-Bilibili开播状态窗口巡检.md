# Bilibili 开播状态窗口巡检

## 需求边界

窗口层级存在两条不同的看门狗，不能混为一个开关：

- `ASCEND-VISION` 自身的周期置顶是常驻能力，约每 500ms 用无激活 `SetWindowPos` 恢复一次，不区分是否开播。
- 《杀戮尖塔 2》的新增巡检只在直播姬实际为 `Streaming` 时生效，周期固定为 60 秒。

因此，未开播时蓝色悬浮窗仍会保持自身置顶，但它不会强制改变游戏窗口的层级。

## 实现

- `broadcast_window_patrol.py` 复用直播姬保护桥的本地状态码口径：先确认 `livehime.exe` 进程存在，再从 `bililive_debug.log` 尾部取最新 `set_streaming_status`。直播姬为高完整性进程时，Windows 可能隐藏完整映像路径；此时通过 Toolhelp 只退化到精确文件名 `livehime.exe`，仍需同时满足本机日志的 `Streaming` 状态才生效。
- 只有最新状态码映射为 `Streaming` 才进入窗口操作；`Idle` / `Starting` / `Stopping` / `NotRunning` / `Unknown` 和任何异常都 fail closed。
- 游戏路径只从当前 `.runtime/session.json` 的 `game_exe` 读取，必须是运行中 session 的绝对路径。Win32 枚举可见顶层窗口后，通过进程完整映像路径精确匹配，不依赖模糊标题。
- 每次有效巡检先对游戏调用 `HWND_TOPMOST + SWP_NOACTIVATE`，然后对 `ASCEND-VISION` 再调用一次无激活置顶，保证游戏不失去输入、悬浮窗仍在最上方。
- 巡检集成在已有常驻 viewer 的帧循环中，不新增 PowerShell 守护进程、计划任务、PID/锁文件或停止协议。

## 资源与安全性

这条路径只使用 Python 标准库、本地文件和 Win32 API，不访问浏览器或 Bilibili 私有 Web API，不调用 LLM / OpenCode / Minimax / OpenRouter，token 消耗为 0。所有异常都在 viewer 内吞掉并等待下一个 60 秒周期，不得中断游戏、智能体、直播或悬浮窗。

## 验证

- 本地状态解析覆盖最新状态码、进程不存在与脏日志。
- 非 `Streaming` 单元测试要求游戏查找、游戏置顶和巡检内 viewer 重排均为零调用。
- `Streaming` 测试要求调用顺序为游戏置顶、游戏复验、viewer 置顶，且 60 秒内不重复执行。
- 原有 viewer 500ms 周期看门狗的独立回归测试继续保留。
