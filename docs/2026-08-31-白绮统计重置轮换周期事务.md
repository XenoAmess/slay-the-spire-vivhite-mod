# 白绮统计重置与轮换周期事务

## 问题

只清空 `profiles/vivhite/` 的楼层统计会保留根级
`knowledge/character_rotation.json` 的旧 `catchup_index`。因此新的白绮样本可能从旧
4:1 周期的中间位置继续，而不是作为重置后的第一局。

## 实现

`sts2-ascend/scripts/reset_profile_statistics.py` 现在把轮换状态纳入同一个可回滚事务：

- 只接受 `schedule_mode=catchup_4_to_1`。
- 只允许没有活动局，或活动局经完整状态校验确认为 `VIVHITE`。
- 将原始 `character_rotation.json` 原字节归档，并纳入 `SHA256SUMS` 与 v2 manifest。
- 新状态写为 `catchup_index=0`、`next_character=VIVHITE`、
  `catchup_completed=false`。
- 若已有活动白绮局，将它的 `scheduled_character` 固定为 `VIVHITE`，使该局终局后
  消耗新周期第一个槽位并推进到 `catchup_index=1`。
- 任一统计或轮换写入失败时，删除不完整的新基线并恢复全部原始文件。

## 验证

定向测试全部使用临时目录，不读取或修改真实 `knowledge/`。覆盖成功归档、无活动局、
活动白绮局计入第一个槽位、balanced 模式拒绝、活动战士局拒绝，以及轮换写入失败时
统计与轮换共同回滚。

本次仅修改代码、测试和本文档；没有执行真实重置、生命周期、部署、提交或推送。

## 已有新样本时仅重置轮换

若旧版工具已经清空统计且新白绮局正在进行，禁止再次执行完整统计重置。此时使用显式
`--rotation-only` 路径。该事务仍要求确认短语和 Stack 完整停止，但不会解析、创建、
移动或写入 `stats.json`、`runs/`、`.active_run_learning.json`、`review_queue.json`。

它只执行以下操作：

1. 使用与完整重置相同的 `_prepare_rotation_reset` 校验 catch-up 模式和活动局身份。
2. 将当前 `character_rotation.json` 原字节移入独立的
   `knowledge/rotation_reset_archives/vivhite/` 归档，并记录 SHA-256。
3. 原子写入新周期状态；若后续任一步失败，删除替换状态并把归档原件恢复到原路径。

定向测试额外验证了新统计与当前 run 文件逐字节不变、CLI 正确路由、确认短语与停栈门禁，
以及 rotation-only 写入失败时的原字节回滚。

## Progression 混合 Schema 与完整重置

源码消费者证明 `progression.json` 同时承载三类状态：

- 对局累计：`wins_by_ascension`、`runs_by_ascension`、
  `best_floor_by_ascension`。它们只在终局反思时按进阶写入；最高楼层也可作为旧统计迁移的
  兜底证据。
- 非楼层策略：`character`、`current_ascension`、`max_ascension_goal` 以及未来未知扩展键。
  选角和进阶难度决策会直接消费这些字段。
- 复盘运行状态：`last_llm_review_run`、`last_successful_review_run`、
  `review_closure_last_runs`、闭环连续计数和最近结果等。

完整 reset 的 v3 事务现在先原字节归档 progression，再执行字段级重置：

- 三个对局累计映射清空。
- 与已经清零的 run 编号和复盘队列冲突的复盘局号游标归零，
  `review_closure_last_runs` 清空。
- 角色、当前进阶、进阶目标、闭环策略、自定义键和未知未来键原样保留。
- 文件缺失时创建白绮身份的默认 progression；非 JSON 对象或关键策略字段类型错误时，
  在创建归档和移动文件前拒绝执行。
- progression 写入与 stats、runs、review queue、rotation 属于同一回滚事务。

`--rotation-only` 不进入 profile 根目录，测试会对调用前后的整个 profile 文件树逐字节比较，
因此仍绝不读取、归档或改写 progression。

## 已产生新样本后的单次 Progression 迁移方案

旧 progression 只有按进阶聚合的次数、胜场和最大楼层，没有 run ID、时间或重置 epoch。
因此不能仅凭该文件把“旧约 5 局”与“清零后首局”做数学相减；最大值尤其不可逆。

安全迁移必须以清零后重新建立的 `runs/` 为逐局事实源，并在完整停栈后执行：

1. 原字节归档当前 progression，写入 SHA-256 和 prepared manifest。
2. 只枚举当前 profile 中已终局、非 `in_progress`、非人工接管、非
   `excluded_from_learning` 的 run；正在进行的第二局不计入本次重建。
3. 从每个合格 run 的 `ascension`、`victory` 和最终 `floor` 重建三个按进阶映射。
4. 用 `stats.global.runs / floor_sum_raw / best_floor_raw`、run 编号连续性和唯一 run ID
   交叉校验。当前预期应恰有一局完成且总楼层与最高楼层均为 33，但这必须由真实文件证明，
   不能仅凭口头数值写盘。
5. 保留 progression 的所有非累计策略字段；复盘局号游标归零，避免旧编号阻止新基线复盘。
6. 原子替换后重新读取并复核；任一步失败恢复归档原件。

若已完成 run 缺少进阶、胜负或最终楼层，或逐局证据与 stats 不一致，则现有证据无法可靠
分离旧贡献。最小无猜测方案是拒绝迁移并保留原文件；不能把三个映射直接清空，因为那会
丢掉已经完成的 F33 首局，也不能猜测它的进阶或胜负。获得真实数据只读检查许可并闭合上述
交叉校验后，才适合实现或执行一次性迁移。
