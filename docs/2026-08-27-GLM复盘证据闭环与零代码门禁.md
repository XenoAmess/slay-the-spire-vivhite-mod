# GLM 复盘证据闭环与零代码门禁

## 问题

第 705～716、717～720、721～723 局连续三次复盘只提交
`meta_review.md` 与口播短评。日志证明这些批次均正常退出、正常通过宿主验收，不是审核墙、
自检或 Git 失败；“零代码纪律”是 GLM 从前一份报告中自行继承并强化的说法。旧宿主还把
报告 patch 当成运行时代码变更，造成一次没有加载价值的局间 Brain 重启。

## 闭环机制

- 宿主按真实变更路径分类。`policy.py`、`agent.py`、`reflect.py`、`knowledge.py` 等生产路径
  才可能算行为或运行时观测闭环；报告、仅 `selfcheck.py`、生产文件的注释/空白变更不算。
- 当前每个成功复盘批次都必须落地一个有界实验。纯文档在提交前被拒绝，全部沙箱文件进入
  `knowledge/code_backups/review_salvage/`，批次回队退避重试，线上工作树不受影响。
- 提示词要求同一问题在 3 个独立 run 或连续 2 个复盘批次出现时进入成熟态；实验只要求
  相对安全、可观测、可记录、可继续调整或撤回。拿不准策略时必须先加生产观测。
- 最近零代码章节以有界历史债务包注入提示词。模型必须逐项对账，只有能指向已存在生产代码
  与实际行为的项才可标记 resolved；否则每批优先补做一个最高价值债务。
- 历史 run 追回后队列可能不是局号顺序；批次标题按去重后的最小/最大局号描述，并明确实际局数，
  避免出现 `730~729` 这类倒序标题误导模型，权威范围仍以 packet 的 exact run 列表为准。
- 宿主把闭环结果写入 `progression.json`；只有生产路径变化才发布 restart marker。报告路径
  仍可作为实验记录提交，但不能单独构成一次成功复盘。

## “参数顶格”的正确含义

`reflect.py` 的在线学习使用有界调整：参数到达 `BOUNDS` 后，同方向的死亡证据不再继续把它
推向极端，避免形成“更防守 → 战斗更长 → 再加防守”一类单向棘轮。正确后续是把证据转交给
同语义接替旋钮、结构规则或新观测，而不是停止改代码。

当前真实边界包括：`block_safety=2.1`、`kill_bonus=20`、输出饥饿加分 `8/12`、
`deck_burst_floor=45`、两条锻造血线 `0.45`、长战能力加分上限 `12`、药水防守线 `0.80`、
危险组合防御斜率 `0.60`。`kill_race_prior_eff=0.39` 尚未到 `0.35` 下限。
GLM 报告中所谓 `power_starve=6/8` 与 `pick_threshold_starve_relief=2.5` “顶格”并不准确：
它们是静态校准值，不在 `reflect.BOUNDS`，没有运行时 clamp。

## 验证与运维

- 单测覆盖路径分类、每批硬门禁、Git 历史迁移、历史债务提取、提示词纪律、计数归零，以及
  报告批不重启/运行时批才重启。
- 上线时先在 Brain 运行期间完成离线自检和提交；最后使用统一 `Stop-Agent.ps1 -KeepGame` 与
  `Start-Agent.ps1 -SkipDeploy` 快速换代，游戏保持运行，Brain 断流控制在两分钟内。
- 若实验后续表现恶化，按报告记录的观测与撤回条件继续调节；必要时用受控反向提交撤回，
  不使用工作树强制重置。
