## 任务与最终方案

历史目标：反复游玩战士（Ironclad）、局势分析、自我总结进化、通关后冲击更高进阶（Ascension）。
2026-08-30 起扩展为 Vivhite 与 Ironclad 双角色隔离游玩；下文早期只写 Ironclad 的内容保留为
方案演进记录，当前角色契约以“2026-08-30 双角色 Profile 与轮换扩展”一节为准。

最终架构：**上游 mod [CharTyr/STS2-Agent](https://github.com/CharTyr/STS2-Agent)（v0.9.0 release）做驱动层**
（游戏内 HTTP API：`GET /state` `/actions/available` `POST /action` `GET /data/*`），
**自研 Python 大脑做决策层**（`sts2-ascend/brain/`，纯标准库），
持久化知识库 `knowledge/` 做进化基底（stats.json / policy.json / progression.json / lessons.md / runs/）。

关键决策：最初计划自研 C# 驱动 mod（已完成 API 调研），发现上游项目已覆盖全部需求
（含 `increase_ascension`/`decrease_ascension` 进阶调整、`end_turn_will_kill_player` 致死预警、
意图 `total_damage`、`dynamic_values` 精确数值），改为直接基于它，把精力集中在学习与进化上。

## 2026-08-30 双角色 Profile 与轮换扩展

当前契约是“算法共用，角色数据与参数分离”：`Policy` 仍是同一份决策代码，`Agent` 按
`CharacterProfile` 维护独立的 `Knowledge` / `Policy` 实例。Ironclad 的既有根数据继续留在
`knowledge/`，不迁移、不手工改写；Vivhite 使用 `knowledge/profiles/vivhite/`。无角色字段的旧日志
按 Ironclad 解释。每份新日志携带 `profile_id`、API 实际 `character_id`、角色自己的
`profile_run_number`；`stats`、`progression`、`lessons`、`policy` 和 `runs` 均从所属 Profile 根解析。
只有版本化的原生游戏事实 `knowledge/game/` 是共享输入，不包含任何角色学习结论。

分角色统计不是对同一份总数据加显示标签。`FloorStatsProvider` 以 Ironclad 根目录和
Vivhite 子 Profile 分别建立数据源：生涯平均楼层分别使用各自的 `floor_sum_raw / runs`，
生涯最高楼层分别使用各自的 `best_floor_raw`，“近 20 局”也只从该 Profile 已完成、
非幻影的对局日志取最后 20 局。Vivhite 子目录即使为空也是权威结果，不会用旧根目录的
Ironclad 数据回填。驾驶舱按当前 Profile 展示其独立的最高、平均和近 20 局；角色对比比值
另由两个 Profile 各自的 5 局滚动平均派生，不参与对局学习记账。

轮换状态机的行为已经固定：全新状态第一局选择 Vivhite；Vivhite 完成总局数少于 Ironclad 时按
四局 Vivhite、一局 Ironclad 的五局周期追赶，追平后恢复 Vivhite ↔ Ironclad 严格交替。重连或已有
活动局时，以 API 返回的 `run.character_id` 绑定 Profile，不用预期目标猜角色。只有终局日志和统计
成功持久化后才推进轮换配额，重复终局按 `run_id` 去重。目标角色缺失、锁定或没有有效
`option_index` 时保持等待并记录错误，不允许回退到角色列表中的第一个可用项。

Vivhite 参数实例当前定义为：实际謦欬 `-1.25/点`，生命严格低于 35% 时风险权重翻倍；余裕
`+1.25/点`；汲取按实际回复生命的 `85%` 计收益；永久最大生命 `+3.0/点`；击杀回复按实际触发量
计分。所有收益函数按实际量线性计算，不对余裕、永久成长、回复量、汲取百分比或汲取收益增加
自定义裁剪。`VIVHITE_CARD_CATALOG` 对 61 个唯一卡牌 ID 做启动时数量校验，`Policy` 在出牌、
奖励拿牌、选牌与构筑协同评分时消费该目录及实时 `dynamic_values`。目录已同步当前謦欬、
余裕、抽弃牌、汲取、孤高冠冕 20% 和归纳法阵百分比规则。语义上，謦欬按余裕抵扣后的
实际耗血评估，余裕按完整数量线性评估，汲取先汇总整张攻击造成的实际敌方生命损失，再按总汲取率
计算并向上取整一次；汲取率可超过 100%，不做自定义上限或评分截断。当前生命不超过最大生命、
謦欬付款后不得低于 1 点生命等仍是游戏有效性规则，不属于 Brain 的人为裁剪。

## 2026-08-31 人工接管边界

全套运行时，`Ctrl+Alt+F9` 是 Windows 全局停止键：Brain 立即停止发送游戏操作，保留游戏与
runner。只要某局跨过一次人工接管边界，该局便永久标记为 `human_assisted=true`、
`excluded_from_learning=true`；`Ctrl+Alt+F10` 只恢复动作发送，不会恢复同一局的学习写入。

每个 Profile 使用自己的 `.active_run_learning.json` 保存精确 `run_id`、局前 Knowledge `stats`
基线与排除标记。F9 先持久化排除标记，再把卡牌、敌人、事件、房间及其他在线统计整体恢复到
该局开始前的基线；此后所有在线学习入口保持禁用。若进程在标记与恢复之间退出，重启会按该
持久标记 fail-closed 地完成回滚，而不是重新接受这局样本。

混合局已有及随后产生的增量决策/战斗日志继续以 `in_progress=true` 保留，并携带
`human_assisted=true`、`excluded_from_learning=true` 作为审计证据；归档 catalog 也保留这两个
排除字段。该局结束时不调用自动对局的 `finalize_run`：不增加角色总局数或胜场，不更新最高楼层、
平均楼层、近 20 局、终局卡牌/遗物/房间归因或该局的 policy/progression/lessons，不进入 LLM
复盘队列，也不消耗 4:1 / 1:1 轮换配额。`release_human_controlled_run` 只释放该活动局的轮换占用，
调度器仍保持在原来的目标角色槽位；下一局未被人工边界触及时才恢复正常学习。

## 2026-08-31 原生终局分数与解锁闭环

此前 Brain 在 `GAME_OVER` 直接返回主菜单，绕过了游戏原生 Run Summary 协程，因此分数条、角色
解锁计算及对应存档确实没有执行。修复后的 Agent 状态版本为 12，增加
`game_over.phase=intro|summary_animating|summary_ready` 与 MCP 动作 `continue_game_over`。当阶段为 `intro`
时，MCP 只通过 `continue_game_over` 真实点击 `NGameOverContinueButton`；此后状态进入
`summary_animating`，Brain 只等待原生 Run Summary 处理分数条、分数解锁与保存；只有真实
`NReturnToMainMenuButton` 可见且可用时才进入 `summary_ready` 并暴露 `return_to_main_menu`。

Brain 在 `summary_ready` 屏障处先幂等保存本局日志、所属 Profile 统计和轮换记录，下一次轮询才点击
真实返回按钮。后续 `UNLOCK` 展示屏逐项使用 `confirm_unlock`，按钮未就绪时只等待，不用通用
`proceed` 或盲点跳过。终局去重同时由内存中的 `run_finalized` 和轮换账本按 `run_id` 持久记录：
重复终局通知不会再保存统计、再入 LLM 队列或再翻转轮换，重连到旧 `GAME_OVER` 回声也不会伪造空对局。

## 2026-08-31 按 Profile 隔离 LLM 复盘

复盘仍由一个进程内调度器串行消化，但调度器遍历的是 Profile 本地队列。每个新队列项都携带
`profile_id`；历史上没有该字段的队列项按 Ironclad 处理。队列读取会拒绝与所在 Profile 根不一致的项，
批次绑定也要求所有项的 `profile_id` 完全一致，因此一个 LLM 批次不会混入另一角色的对局。

每批执行时会绑定该 Profile 的精确 `Knowledge` 实例和路径集：`review_prompt_latest.md`、`runs/`、
`stats.json`、`progression.json`、`policy.json`、`lessons.md`、`meta_review.md`、`review_conclusion.txt` 与
`review_queue.json` 均从该 Profile 根目录解析。所以 Vivhite 的提示、运行证据、策略、教训、报告和待处理队列
与 Ironclad 相互隔离；共享的只是调度与决策代码。

本次仅做静态代码与文档对照，未运行测试或真机流程；本节只记录当前代码实现，不新增任何测试通过结论。

## 踩过的坑（按时间顺序，全部真机验证）

1. **`/health` 发现逻辑判错字段**：mod 响应信封 `{ok, data}`，客户端 `_decode()` 已剥壳返回
   `data`；`discover()` 却继续判 `data.get("ok")` → 永远失败 → 误启第二个游戏实例。
   **教训**：两个实例都能玩（mod 端口 8080 占用自动递增到 8081），用户会看到"另一个没在被玩的窗口"。
   修复：判 `data.status == "ready"`；`ensure_game` 先查进程再决定是否重启游戏。

2. **手牌载荷没有 `card_type` 字段**：`CombatHandCardPayload` 与奖励/商店载荷字段集不同
   （后者有 `card_type`）。按类型分支的评分全部落入"未知类型 0.3 分" → 低于出牌阈值 0.4 →
   **永远不出牌只结束回合，挂机送死**。修复：战斗评分改为从 `dynamic_values`（Damage/Block 精确数值）
   推断功能，与类型字段解耦。**教训**：先真机 dump 一份完整载荷再写策略，别只读源码推断字段。

3. **`end_turn` 与 `play_card` 的就绪时序不同**：mod 对出牌有 200ms 稳定窗，end_turn 出现得更早。
   看到 end_turn 就点 → 把还没抽好的手牌整回合扔掉。修复：`play_card` 未出现且 `end_turn` 出现时，
   必须连续 4 个 tick 确认无牌可出才允许结束回合。

4. **`BUNDLE_SELECTION` 屏幕漏处理**：涅奥事件可能给"卡包 2 选 1"（`NChooseABundleSelectionScreen`），
   不在文档的屏幕清单里。大脑只会"观察"不会动手 → 卡死。修复：注册 `_bundle` 处理器，
   并在 `_unknown` 里按载荷（`bundles`/`capstone` 存在性）兜底路由，防新屏幕名漏网。

5. **商店开→关→开死循环**：评估完关闭货架后，`can_open` 又变 true → 再打开。
   修复：`_shop_done_floor` 记住本层商店已评估，之后直接 proceed。**教训**：所有"可重复打开"的
   界面都要考虑幂等推进。

6. **死因归因错误**：离开 COMBAT 屏幕时一律记"战斗胜利"——死在战斗里会先经历 GAME_OVER 屏幕，
   导致敌人危险度模型全是假胜利、`lessons.md` 死因恒为空。修复：离开战斗/事件时检查
   `screen == "GAME_OVER" && !is_victory` → 记为致死并归因到该敌人组合/事件选项。

7. **日志中文乱码的三层幻觉**：(a) Start-Process 重定向按 GBK 写文件；(b) PowerShell 管道按
   GBK 捕获输出；(c) `Get-Content -Encoding UTF8` 显示仍乱码——但**文件本身是正常的 UTF-8**，
   乱码发生在显示环节。最终方案：大脑自己用 `open(..., encoding="utf-8")` 双写日志文件，
   读日志一律用 Read 工具而非 PowerShell。

## 大模型复盘层（当日追加，已真机验证）

> **2026-08-22 历史实现记录。** 本节保留当日单角色、单复盘队列方案的原始结论；
> 当前多角色路径与批次边界以前文“按 Profile 隔离 LLM 复盘”为准。

**需求**：每 10 局由大模型统一复盘，调整策略与代码缺陷，沉淀新知识。模型指定 Kimi K3。

**关键架构决策**：不直接调模型裸 API（裸 chat completion 只能输出文本，"改代码"只能靠
脆弱的字符串替换沙箱），而是 spawn **`opencode run` 无头会话**——带完整工具链的智能体，
复用本机已有 OpenCode 授权（`kimi-for-coding/k3`），零额外 key 成本。

实现（`brain/llm_review.py`）：
- 触发：agent 每局 finalize 后检查，间隔 ≥10 局则执行；复盘期间大脑暂停（游戏停在主菜单，无并发写冲突）
- 提示词：内嵌紧凑数据摘要（近 10 局摘要+统计摘要，~6k 字符控 token）+ 文件路径供深读 +
  明确安全边界（只许写 knowledge/、唯一可改代码文件 policy.py 且必须 py_compile、**禁止 git/进程/删除操作，
  显式覆盖仓库 AGENTS.md 的"完成即提交推送"默认规则**）
- 命令：`opencode run --model kimi-for-coding/k3 --dir <repo根> --auto <prompt>`（--auto 是无头编辑的前提）
- 完成后大脑在主菜单安全点 `os.execv` 自重启，加载新策略/代码

**验证**（手动 `--now` 触发，2 局样本）：复盘 agent 产出高质量报告（meta_review.md），
识别出"补刀死"模式（致死战掉血 1 → 真凶是前置节点累计失血）、多页事件学习盲区
（真理石板连点解读 -34HP），做了 7 项有界参数调整（精英线 0.55→0.65、篝火权重 1.0→1.25 等），
并在样本不足时**克制地不改卡牌 bias、不动代码**——边界约束生效。

坑：`opencode run --help` 的输出走 stderr，PowerShell 会当错误流显示，属正常。

## 广权限复盘 + git 安全网（当日二次迭代）

> **历史方案，已废弃，严禁照此执行。** 本节记录 2026-08-22 当日演进过程，曾经的
> 全仓强制回滚/清理会覆盖用户或在线线程的并发改动。当前实现见
> `docs/2026-08-26-sts2-ascend自动Git事务安全.md`：模型只在无 remote、无 hardlink
> 的独立 clone 中工作；真实仓库只接收通过 allowlist 与自检的精确 patch，回滚也是
> 单个已验证复盘 commit 的受控反向 patch，失败即保留现场。

用户决策：复盘 agent 从"只许改 policy.py"放开到 **sts2-ascend/ 下全部文件**（含数据结构），
安全模型从白名单沙箱改为 **git 版本化**：

- 改前：大脑自动 commit+push 全量备份（`复盘前备份`）
- 改后（历史实现）：selfcheck 通过才提交；失败时曾采用全仓强制回滚与目录清理，
  该做法现已删除，不能在共享工作树复用
- 重启：大脑退出码 42 → `runner.py` 监督进程拉起；新代码起不来则按
  `pending_restart.json` 里的备份点 hash 再回滚一次（双保险）
- 当前由重新加载过复盘 commit 的大脑完整完成 2 局后删除健康标记
- 当前每局存档和复盘提交各有精确 allowlist，并使用私有 index，不扫描整个目录

已验证：runner 拉起大脑、杀掉大脑进程后 runner 记录异常并自动重启（rc=-1 → 新进程）。
注意：不要把“忽略文件不受某种清理模式影响”当作安全边界；当前流程不执行全目录清理。

## 药水 bug：从"绕开"到"根治"（重要教训）

现象：精英战中大脑每 11 秒重复使用 AoE 药水（爆炸药瓶）刷屏卡死。

**第一反应（错）**：给药水加"本场战斗黑名单"绕开。用户指正后追根溯源：

1. 手动 `use_potion` 复现：返回 `pending`，`is_queued=False`，敌人不掉血——动作根本没入队
2. 读上游源码：`ResolvePotionTarget` 对 `TargetType.AllEnemies/AllAllies/RandomEnemy` 走
   default 分支返回 `potion.Owner.Creature`（把自己当目标），游戏静默丢弃非法目标
3. 对照实验：自瞄准的果汁（AnyTime）status=completed 正常生效 → 坐实是 AoE 目标解析的上游 bug
4. **根治**：克隆上游源码，补丁 3 行（三类 AoE 目标返回 `null`，游戏内部自行解析），
   `scripts/build-mod.ps1` 从源码构建部署（csproj 引用路径用 `STS2_DATA_DIR` 环境变量提供，
   与 build 脚本的 `-GameRoot` 部署参数是两回事），重启游戏后实测：completed，敌人 81→71。
5. 补丁归档：`sts2-ascend/third_party/STS2-Agent-v0.9.0-aoe-potion-fix.patch`（注意 `git diff -w`，
   否则 PowerShell 改写行尾会污染整个 patch）

**教训**：智能体的"失败记忆/黑名单"是兜底，不是解决方案。动作反复失败时先手动复现 +
读响应体细节（pending vs completed 语义不同！）+ 对照实验（自瞄准 vs AoE）。

"It was not possible to find any installed .NET Core SDKs"——构建前显式设置两者。
