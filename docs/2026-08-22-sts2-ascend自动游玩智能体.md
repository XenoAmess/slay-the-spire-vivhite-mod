# 2026-08-22 sts2-ascend 自动游玩智能体（基于 STS2-Agent）

## 任务与最终方案

目标：反复游玩战士（Ironclad）、局势分析、自我总结进化、通关后冲击更高进阶（Ascension）。

最终架构：**上游 mod [CharTyr/STS2-Agent](https://github.com/CharTyr/STS2-Agent)（v0.9.0 release）做驱动层**
（游戏内 HTTP API：`GET /state` `/actions/available` `POST /action` `GET /data/*`），
**自研 Python 大脑做决策层**（`sts2-ascend/brain/`，纯标准库），
持久化知识库 `knowledge/` 做进化基底（stats.json / policy.json / progression.json / lessons.md / runs/）。

关键决策：最初计划自研 C# 驱动 mod（已完成 API 调研），发现上游项目已覆盖全部需求
（含 `increase_ascension`/`decrease_ascension` 进阶调整、`end_turn_will_kill_player` 致死预警、
意图 `total_damage`、`dynamic_values` 精确数值），改为直接基于它，把精力集中在学习与进化上。

## 踩过的坑（按时间顺序，全部真机验证）

1. **`/health` 发现逻辑判错字段**：mod 响应信封 `{ok, data}`，客户端 `_decode()` 已剥壳返回
   `data`；`discover()` 却继续判 `data.get("ok")` → 永远失败 → 误启第二个游戏实例。
   **教训**：两个实例都能玩（mod 端口 8080 占用自动递增到 8081），用户会看到"另一个没在被玩的窗口"。
   修复：判 `data.status == "ready"`；`ensure_game` 先查进程再决定是否重启游戏。

2. **手牌载荷没有 `card_type` 字段**：`CombatHandCardPayload` 与奖励/商店载荷字段集不同
   （后者有 `card_type`）。按类型分支的评分全部落入"未知类型 0.3 分" → 低于出牌阈值 0.4 →
   **永远不出牌只结束回合，挂机送死**。修复：战斗评分改为从 `dynamic_values`（Damage/Block 精确数值）
   推断功能，与类型字段解耦。**教训**：先真机 dump 一份完整载荷再写策略，别只读源码推断字段。

3. **`end_turn` 与 `play_card` 的就绪时序不同**：mod 对出牌有 200ms 稳定窗，end_turn 出现得更早。
   看到 end_turn 就点 → 把还没抽好的手牌整回合扔掉。修复：`play_card` 未出现且 `end_turn` 出现时，
   必须连续 4 个 tick 确认无牌可出才允许结束回合。

4. **`BUNDLE_SELECTION` 屏幕漏处理**：涅奥事件可能给"卡包 2 选 1"（`NChooseABundleSelectionScreen`），
   不在文档的屏幕清单里。大脑只会"观察"不会动手 → 卡死。修复：注册 `_bundle` 处理器，
   并在 `_unknown` 里按载荷（`bundles`/`capstone` 存在性）兜底路由，防新屏幕名漏网。

5. **商店开→关→开死循环**：评估完关闭货架后，`can_open` 又变 true → 再打开。
   修复：`_shop_done_floor` 记住本层商店已评估，之后直接 proceed。**教训**：所有"可重复打开"的
   界面都要考虑幂等推进。

6. **死因归因错误**：离开 COMBAT 屏幕时一律记"战斗胜利"——死在战斗里会先经历 GAME_OVER 屏幕，
   导致敌人危险度模型全是假胜利、`lessons.md` 死因恒为空。修复：离开战斗/事件时检查
   `screen == "GAME_OVER" && !is_victory` → 记为致死并归因到该敌人组合/事件选项。

7. **日志中文乱码的三层幻觉**：(a) Start-Process 重定向按 GBK 写文件；(b) PowerShell 管道按
   GBK 捕获输出；(c) `Get-Content -Encoding UTF8` 显示仍乱码——但**文件本身是正常的 UTF-8**，
   乱码发生在显示环节。最终方案：大脑自己用 `open(..., encoding="utf-8")` 双写日志文件，
   读日志一律用 Read 工具而非 PowerShell。

## 验证结果（真机）

- 全流程：主菜单 → 选 Ironclad → 进阶调整 → 涅奥事件 → 卡包选择 → 地图选路（含 1 步前瞻）
  → 战斗（伤害/格挡/击杀检测/AoE/药水）→ 奖励（金币/遗物/卡牌评估+跳过）→ 商店（购买/删牌/离开）
  → 篝火（休息/锻造按血量阈值）→ 宝箱 → 结算 → 复盘 → 下一局，全自动闭环。
- 进化证据：block_safety 1.00→1.05（普通战阵亡后）、exploration_rate 逐局衰减、
  卡牌价值榜（POMMEL_STRIKE 8分/3局）随对局形成。
- 稳定性：看门狗（同签名 25 tick 试 proceed、90 tick 弃局）+ 断线重连 + 进程检测。

## 上游 mod 关键契约备忘

- 屏幕枚举：MAIN_MENU / CHARACTER_SELECT / MAP / COMBAT / REWARD / CARD_SELECTION / SHOP / REST /
  CHEST / EVENT / MODAL / GAME_OVER / TIMELINE / BUNDLE_SELECTION / CAPSTONE / UNKNOWN
- `POST /action` 体：`{action, card_index, target_index, option_index, command}`；响应
  `{action, status, stable, message, state}`（status 常见 `completed`）。
- 状态里有但文档没强调的好东西：`combat.hand[].dynamic_values`（精确伤害/格挡）、
  `combat.enemies[].intents[].total_damage`、`combat.end_turn_will_kill_player`、
  `character_select.ascension/max_ascension`、`map.nodes`（全图含 children 可做路径规划）。
- mod 部署布局是 `mods/` 根目录平铺（与 RitsuLib/Vivhite 的子目录布局共存无冲突）。
