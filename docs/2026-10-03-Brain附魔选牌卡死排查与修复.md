## 根因与纠正证据

1. Brain 的通用选牌确认分支只比较 `selected_count >= min_select`。由于附魔界面的原生偏好允许 `MinSelect=0`，首次进入就发送零选择确认。
2. 原生 `NDeckEnchantSelectScreen.ConfirmSelection` 实际包含 `_selectedCards.Count != 0` 条件。零选择时即使按钮已启用，确认也不执行完成逻辑。因此不能把“偏好允许零张”或“按钮 enabled”当作有效空确认的证据。
3. 原生完成条件允许选择 1 至 3 张；达到 3 张时自动进入附魔预览。提示中的 3 是本次上限，不能把它误记成原生必须选满 3 张。Brain 应在候选充足时使用已有附魔额度，API 则应如实公开至少一张才可完成的有效下限。
4. 2026-09-26 的维护提交 `3685b5895f` 为恢复已验证基线，连同此前维护 Agent 的附魔 `selection_target` 与对应等待条件一起移除了。这次修复只恢复该交互数量契约，不恢复整份历史策略，也不改变模型的评分或复盘成果。

API 源码中的 `TryGetCardGridSelectionMetadata` 原先直接使用 `prefs.MinSelect/MaxSelect` 计算 `CanConfirm`。`confirm_selection` 执行路径虽检查按钮/预览，但零选择确认最终仍由原生代码忽略，表现为 pending。这纠正了巡检初期“只要检查真实按钮就能解决”的假设：必须同时遵守原生非空完成条件。

现场部署 DLL、fork 原 Release DLL 与构建产物的 SHA-256 均为 `1BA3E7424336004F26196B825DA1070490035B30DEE7E1BEDB13C18AC69D8727`，Release SourceLink 对应 fork 提交 `21dc9dc55c7093fe21e62fc6a91c324e450053be`，不是以当前源码代替部署版本证据。

## 修复与验收方式

- Brain 仅对 `deck_enchant_select` 使用附魔目标数量，候选充足时先选满上限，再确认；已成功选择但尚未反映到下一帧的回执仍等待刷新，避免反选。普通可选零张界面保持原确认行为。
- fork API 针对附魔屏将有效最小数量限制为至少 1，其余选牌屏保留原生偏好；零选择不再公开可执行的确认动作。
- 使用真实故障样本离线重放，覆盖连续三个不同候选、旧帧等待、失败重试、同层新界面和普通零选择确认。
- 通过统一 `Stop-Agent.ps1 -KeepGame` 协作停止旧 Brain 栈，再用 `Start-Agent.ps1 -SkipDeploy` 加载修复，保留原游戏进程与当前选牌界面。维护 Agent 不向 `/action` 注入操作，不使用人工接管快捷键，不手改 session、锁或学习账本。
- 真机验收须取得同一原局的两个不同且时间递增的 `applied` 回执，并证明离开 F38 附魔界面；“Stack ready”只能作为启动证据。
