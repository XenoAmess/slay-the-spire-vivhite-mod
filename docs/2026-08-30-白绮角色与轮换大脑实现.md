# 白绮角色与轮换大脑实现

日期：2026-08-30  
状态：已批准的实现契约；代码、构建、部署、真机与平衡验收结果均以本文末尾未勾选清单为准，不在本文中预先宣称完成。

## 1. 任务目标与边界

本任务从头实现独立角色“白绮（Vivhite）”，不继承此前旧白绮占位卡的名称、数值或机制。白绮是精通数学、计算机与艺术的魔法少女和魔法大师，不使用剑、法杖、魔杖或其他武器。

角色核心循环是：以当前生命进行魔法演算，换取高于常规牌的伤害或防御；通过击杀即时回血、余裕抵消耗血、永久增维和百分比汲取维持生命，再将续航转化为下一轮输出与成长。综合自动游玩手感目标约为战士的 `1.5×`，正式平衡窗口为 `1.35×～1.65×`。

本阶段全部卡图只使用 RitsuLib 占位图，不生成、重绘或修改任何图片，也不发起任何 AI 生图调用。独立白绮角色与战士替换皮肤共用仓库中已经存在的白绮 V3 五页战斗 atlas 及其商店、休息、选人、UI、Spine 和多人资源；不得回退旧单页 atlas，也不得覆盖现有创意素材。

Mod 目标版本为 `0.2.0`。

## 2. 无硬上限原则

### 2.1 禁止加入的人为玩法上限

以下数值与触发次数均不得增加自定义封顶字段、单次裁剪、每回合额度、每场额度或每局额度：

- 永久最大生命增长；连续增维超过 30、100 或更高数值后仍须继续生效。
- 临时生成牌、复制牌、重复结算牌和从消耗堆回收牌触发的永久成长。
- 余裕的持有量、产生量和消费量。
- 击杀回血的单次回复、每回合回复、每场回复及触发总次数。
- 牌面汲取率、全局汲取率及二者相加后的总汲取率；总值允许超过 `100%`。
- 汲取的单牌回复量、每回合回复量和每场回复量。
- 由汲取、击杀、抽牌、力量、格挡或其他能力形成的成长计数。

后续平衡只允许调整能量费用、謦欬费用、基础伤害、基础格挡、成长系数、汲取百分点、击杀回复数值、稀有度、保留或消耗等牌面属性，不得以任何形式重新加入硬上限。

### 2.2 必须保留的自然引擎不变量

自然引擎不变量用于保持游戏状态有效，不属于“上限设计”：

| 不变量 | 语义 |
| --- | --- |
| 当前生命不超过最大生命 | 普通治疗仍遵循游戏原生生命容器；超量治疗只有在对应能力存在时才转换为余裕。 |
| 謦欬实际费用最低为 0 | 余裕可以完全抵消费用，但不能把生命费用变成负数或反向治疗。 |
| 支付后生命不得低于 1 | 若结算謦欬会令角色低于 1 点生命，该牌不可打出。 |
| 手牌、抽牌与能量遵循原生规则 | 手牌容量、抽牌失败、X 费取值等继续由引擎决定。 |
| 同一死亡事件只结算一次 | 同一敌方实体的同一次死亡以实体身份去重；不同敌人分别触发。这是事件幂等，不是回血次数上限。 |
| 数值按机制定义取整 | 汲取在一张攻击牌的全部伤害结算完成后汇总，并只取整一次。 |

实现时最容易犯的错误，是把“避免重复事件”误写成“每回合最多触发一次”，或把“当前生命不超过最大生命”误写成“治疗收益只计到某个自定义阈值”。前者破坏多敌人击杀循环，后者会错误压低超量治疗转化和无上限构筑的价值。

## 3. 角色初始配置与核心机制

### 3.1 初始配置

- 最大生命：`78`
- 每回合能量：`3`
- 每回合抽牌：`5`
- 初始金币：`99`
- 初始牌组：`4×弦光投影`、`4×闭域映射`、`1×白绮的变身式`
- 初始遗物：`孤高冠冕`

孤高冠冕：每当任意敌人死亡，立即回复最大生命的 `5%`，向上取整。白绮直接击杀、间接伤害、环境伤害、队友击杀和召唤物死亡均可触发；同一实体的同一次死亡去重，不限制总次数和总回复量。增维提高最大生命后，后续触发量按新的最大生命即时重算。

旧的白绮打击、白绮防御、白绸结及其旧机制必须从注册、初始牌组、卡池和本地化中移除，旧卡图不再接入运行时。

### 3.2 关键词与结算顺序

- `謦欬 N`：打牌前受到 `N` 点不可格挡、不可被力量修改的生命损失。先用余裕按一比一抵消，再支付剩余生命；若支付后会低于 1 点生命，则该牌不可打出。
- `余裕 N`：自动按一比一抵消謦欬并被消耗，可无限叠加。
- `增维 N`：永久增加 `N` 点最大生命，并同时增加 `N` 点当前生命。每次效果结算都生效，临时牌、复制牌、重复结算和回收牌与原牌同权。
- `汲取 N%`：攻击牌全部伤害结算后，按实际造成的敌方生命损失乘以汲取率回血。多段与群体攻击先汇总实际生命损失，再取整一次；不计算格挡、过量伤害、自伤、荆棘或非攻击牌伤害。牌面汲取率与全局汲取率按百分点相加，例如 `80% + 45% = 125%`，不封顶。
- `致命`：该牌的伤害直接令目标死亡时触发。

推荐的统一结算顺序为：检查可支付性 → 消耗余裕 → 支付剩余謦欬 → 执行牌面效果 → 汇总攻击牌实际生命伤害 → 结算汲取 → 处理死亡去重与即时击杀触发 → 处理超量治疗转化。所有卡牌必须调用同一战斗规则层，避免各牌分别实现后出现顺序和取整差异。

### 3.3 被动等价物

STS2 v0.111.0 的 `CharacterModel` 没有独立的 `PassiveAbility` 注册槽；原生角色通过初始遗物与角色专属资源/Hook 形成被动身份，例如铁甲战士的燃烧之血和故障机器人的充能球槽。白绮同样不维护一条隐藏的第二被动：她的被动等价物是初始遗物“孤高冠冕”，而謦欬、余裕、增维和汲取是由专属卡牌与统一规则层驱动的角色机制。

## 4. 三套构筑

### 4.1 守恒几何

守恒几何以余裕减免耗血、永久增加最大生命和超量治疗转化为主。标准循环为：生命流形持续积累余裕，拓扑增生和生命公理反复增维，守恒穹顶将无上限余裕转换为巨额防御。它应是三套中最稳定、最耐久的一套，但不能靠人工成长上限压制后期。

### 4.2 递归星算

递归星算强化高伤害、击杀回血、抽牌和能量连锁。标准循环为：并行星雨削弱群体，终止证明同时制造多次死亡，孤高冠冕、星算追猎和最优算法分别补充生命、手牌与能量，然后继续施法。实现重点是每个敌人的死亡必须独立结算，同时避免重复终局或重复死亡通知造成双触发。

### 4.3 绯彩积分

绯彩积分以多段伤害和可超过 `100%` 的百分比汲取为核心，并把实际回复转化为格挡、力量或进一步汲取。标准循环为：光谱积分叠加全局汲取，多段攻击恢复生命，血色守恒律转化力量，无限画布继续提高汲取，令输出与续航共同成长。汲取必须基于实际敌方生命损失，而不是牌面伤害、格挡伤害或过量伤害。

跨体系牌负责将余裕、抽牌、击杀和汲取连接起来。混合构筑应有组合空间，但验收时不得长期领先最佳纯构筑超过 `15%`。

## 6. 代码实现说明

### 6.1 统一战斗规则层

謦欬、余裕支付、永久增维、死亡事件、攻击牌伤害聚合、汲取、超量治疗和牌复制身份应集中在统一规则层。卡牌只声明自身费用和效果参数，不应各自复制核心结算代码。

关键实现约束：

- 永久增维直接写入当前 run 的角色状态，不创建“本局已成长额度”或类似封顶字段。
- 复制或临时生成只改变牌实例来源，不改变其触发永久成长的资格。
- 无限延拓的额外增维必须标记为非递归来源，防止自身无限递归；这是一条触发图不变量，不是成长上限。
- 死亡监听以敌方实体与死亡事件身份幂等，完成去重后立即依次结算遗物和已叠加能力。
- 汲取使用攻击牌完整结算聚合器，读取实际敌方生命损失；多段、群攻和超过 `100%` 的汲取均走同一路径，不对收益裁剪。
- 牌因生命不足不可打出时，应在出牌合法性检查阶段阻止，不能先把角色扣至死亡再尝试回滚。
- 超量治疗转余裕必须同时保留当前生命的自然最大值约束，并将超出部分交给闭合流形处理。

### 6.2 角色、遗物与注册

白绮保留独立的角色 ID、卡池、遗物池、生命、能量和统计身份。注册层应仅暴露本方案 61 张牌和孤高冠冕，完全移除旧占位牌与白绸结。中英文文本、升级文本、关键词和内容 ID 必须一一对应。

战士和白绮的资源加载应指向同一套 V3 五页白绮皮肤，但角色模型、卡池和资源视觉层不能因此混为同一身份。白绮独立角色不得继续使用静态占位战斗形象路径。

### 6.3 CharacterProfile 与分角色存储

brain 使用统一 `CharacterProfile` 接口，至少包含：

- `profile_id`
- `character_id`
- 目标选人 ID
- 卡牌目录与关键词估值
- 策略参数
- 统计、课程、运行日志与复盘目录

现有 `knowledge/` 根目录历史数据继续视为战士数据，不搬迁、不手工改写；没有角色字段的旧日志同样归战士。白绮数据写入 `knowledge/profiles/vivhite/`。新运行日志必须记录 `profile_id`、`character_id` 和 `profile_run_number`。

共用的是决策算法，不是参数实例。白绮初始参数为：

- 实际耗血每点 `-1.25`；当前生命低于 35% 时风险权重翻倍。
- 余裕每点 `+1.25`。
- 汲取按实际回复生命的 `85%` 计入收益，不裁剪。
- 永久最大生命每点 `+3.0`。
- 击杀回复按实际触发量计分，不裁剪。

战士继续使用原有参数，不能读取白绮卡牌语义、估值、策略结论或学习记忆。

### 6.4 追赶期 4:1 与追平后严格轮换

轮换状态机规则：

1. 没有活动对局和轮换历史时，第一局选择白绮。
2. 当白绮已成功持久化的总局数仍少于战士时，按 `白绮 → 白绮 → 白绮 → 白绮 → 战士` 的耐久配额循环追赶。
3. 白绮总局数首次追平或超过战士后，永久锁定为 `白绮 → 战士 → 白绮 → 战士` 的严格 1:1 轮换，不再回到追赶模式。
4. 若启动时存在活动战士局，先按 API 返回的实际角色绑定战士 profile 并跑完；只有实际角色与当前配额位一致时才消费该配额位。
5. 只有终局日志、分角色统计和必要持久化全部成功后，才原子推进配额或切换下一角色。
6. 重复终局通知按 run ID 去重，不重复推进。
7. 重连后始终按 API 返回的实际角色绑定 profile，不能按预期角色猜测。
8. 目标角色未解锁或不存在时暂停选人并记录明确错误；严禁退回第一个可用角色。

把轮换翻转放在终局通知到达时而非持久化成功后，是最危险的实现陷阱：进程在两者之间崩溃会导致跳过角色或连续跑同一角色。轮换记录应携带已处理 run ID，并以原子写入保证重启幂等。

### 6.5 LLM 复盘与驾驶舱隔离

复盘仍可共用一个调度器，但每个队列项必须携带 `profile_id`，单批只能包含同一角色。提示词、运行记录、统计、lessons、policy、报告和待处理队列按角色分离。白绮复盘应获得本方案机制和完整 61 张卡牌目录；战士复盘不得看到白绮策略结论。只有经证明与角色无关的决策逻辑才进入共用代码。

驾驶舱分别展示两个角色的平均真实楼层、最高真实楼层、胜率、卡牌选择和构筑分布，并展示白绮/战士同窗口滚动平均楼层比值。所有展示使用 `floor_sum_raw / best_floor_raw`，不得把包含胜利 50 分的学习评分口径当作真实楼层。

自动提交、路径分类、压缩、复盘隔离与失败现场保全都必须支持 `knowledge/profiles/vivhite/` 这类嵌套目录，不能因路径多一层而漏交、串库或丢失复盘证据。

## 7. 已知陷阱与规避方法

- **结算顺序漂移**：謦欬若在牌面效果后支付，会允许先回血再付款；必须统一在牌面效果前支付。
- **余裕快照时机错误**：星体测度必须记录扣费前余裕 M，随后才允许謦欬消费余裕。
- **多段汲取重复取整**：逐击取整会系统性放大或缩小回复；必须整张攻击牌汇总后只取整一次。
- **把牌面伤害当作实际伤害**：格挡、过量伤害和无效目标均不得进入汲取基数。
- **死亡事件重复或漏计**：按回合布尔值去重会漏掉多杀，完全不去重会双触发；应按实体的单次死亡事件去重。
- **复制牌被降级**：临时牌和复制牌若绕开标准出牌管线，会错误失去增维等永久效果；所有来源必须同权。
- **无限延拓递归**：额外增维不能再次触发自身，但仍应触发其他合法的“发生增维”观察者；需要明确来源标记。
- **百分比单位混淆**：`8%`、`25 个百分点` 和倍率 `0.25` 在数据层必须采用一致单位，避免把 `80% + 45%` 算成 `116%` 或 `0.125%`。
- **角色目录污染**：历史无标签记录归战士；未知显式角色应报错，不能静默写入默认 profile。
- **错误的选人回退**：目标白绮不存在或未解锁时必须暂停，不能选择第一个角色，否则统计和轮换都会被污染。
- **先翻轮换后保存**：只有终局资料耐久化成功才切换；重复通知必须以 run ID 幂等。
- **皮肤身份耦合**：共享视觉资源不等于共享角色状态，白绮的能量 UI、角色 ID 和卡池必须保持独立。
- **验证口径混用**：平衡统计只使用真实楼层，不使用“真实楼层 + 胜利 50 分”的学习分。
- **误宣称验收完成**：静态测试、编译、PCK 导出、真机注册、皮肤一致性和实际轮换是不同门禁，必须逐项留证。

## 9. 平衡调整协议

平衡必须在白绮与战士各至少 20 局同窗口新数据后进行。样本不足时只记录观察，不据此做大幅数值改动。每轮只调整一项，继续收集同口径样本，避免多项同时变更导致无法归因。

若比值高于 `1.65`，依次尝试：

1. 孤高冠冕回复比例 `5% → 4%`。
2. 基础攻击/防御由 `10/9 → 9/8`。
3. 下调卡牌基础伤害和基础格挡。
4. 下调增维数值、击杀回复系数和汲取百分点。
5. 提高能量费用或謦欬费用。

若比值低于 `1.35`，按相反顺序逐项放宽。任何方向都不得以增加最大生命成长上限、击杀回血上限、汲取率上限、回复量上限、余裕上限或回合触发上限来调平衡。

除总体比值外，还需按守恒几何、递归星算、绯彩积分和混合构筑分别统计卡牌选择、关键牌出现率、胜率、平均真实楼层、耗血、击杀回复、汲取回复与永久增维。若某套构筑偏强，应优先调整其专属费用或系数，不应削弱所有白绮机制。

## 11. 实施结果与验收记录

记录日期：2026-08-30。以下结论基于当前仓库生产源码、编译输出、自动化测试、PCK 部署日志和运行时 API；这些短时验收不替代完整机制实战、连续三局轮换或 20+20 平衡长跑。
