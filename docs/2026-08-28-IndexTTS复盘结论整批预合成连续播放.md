# IndexTTS 复盘结论整批预合成与连续播放

## 现场与根因

用户要求白绮复盘结论采用严格的两阶段流程：先把结论拆成短句并逐句生成完本批全部音频，再按原顺序连续播放；
播放期间不能等待下一句合成。

2026-08-28 的生产日志证明旧实现不符合要求。12:35:06 开始的 78 字结论被拆成 8 段后，日志顺序是：

1. `GPU 开始合成 [conclusion 1/8]`；
2. 该段播放返回后才记录 `GPU 合成完成`；
3. 12:35:22 才开始合成 `2/8`；
4. 后续每段重复该流程，单段 GPU 推理约 11～17 秒。

源码中的原因同样直接：`SpeechService._run()` 在同一个短句循环内依次执行
`engine.synthesize(segment, path)` 和 `play(path)`，播放结束后才进入下一轮合成。因此句与句之间必然插入下一句的
完整 GPU 推理等待，并不是连续播报。

## 修复

唯一 IndexTTS GPU owner 仍把整份结论作为一个不可插队的逻辑任务，但内部改为两个明确阶段：

1. `synthesizing`：按既有 10 字目标、20 字硬上限拆句，逐一生成独立临时 WAV；不播放任何一句。
2. 全部 WAV 成功后记录“批次预合成完成”，切换为 `playing`。
3. `playing`：按原始短句顺序阻塞播放所有已准备 WAV；这期间不再调用模型，也不会等待合成。
4. 每个短句中的标点继续交给 IndexTTS 生成自然语气，短 WAV 之间不额外插入长等待。
5. 整批结束、停止、超时或失败后统一清理本批全部临时 WAV。

`/health` 新增 `current_phase`，并继续提供 `current_segment`、`segment_count` 和 `segment_chars`，可区分当前在预合成
还是连续播放阶段。日志也分别记录短句合成与短句播放的开始/完成边界。

## 单句生成失败语义

旧流程在中间短句生成失败前可能已经播放前面的句子，结果会变成无法撤回的半段结论。新流程采用批次准备原子语义：

- 任一句生成失败，立即停止生成后续短句；
- 已经准备好的 WAV 全部清理；
- 本批一律不开始播放，不会跳过失败句后打乱语义或顺序；
- HTTP 调用返回包含失败段序号、已准备段数和“未开始播放”的错误，owner 日志保留 traceback；
- 后续独立语音任务仍由现有队列继续处理。

这样没有假装补齐失败内容，也不会把不完整结论播给直播观众。

## 验证

针对唯一 owner 增加了事件顺序测试，要求完整事件严格等于：

`synth:1, synth:2, ... synth:N, play:1, play:2, ... play:N`

同时增加第 2 段生成失败的回归测试，验证第 3 段不会继续生成、播放事件为零、临时 WAV 均被删除、逻辑任务不计成功。
既有停止中断、多调用者串行、短句边界、HTTP session 和生成 token 上限测试继续覆盖原有契约。

本次只修改静态代码、测试和说明，没有重启或扰动正在运行的生产栈。运行中的 owner 不会热加载 Python 源码；需要上线时
再通过统一 `Stop-Agent.ps1 -KeepGame` / `Start-Agent.ps1 -SkipDeploy` 完成一次受控重启。
