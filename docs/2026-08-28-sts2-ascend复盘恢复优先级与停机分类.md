# sts2-ascend 复盘恢复优先级与停机分类

## 问题

持续巡检发现两个相互放大的机制缺口：

1. Brain 重启时，`reviewing` 事务被追加到 `pending` 队尾。频繁热更新期间，新局持续排在它前面，已经实际开始过的失败包重审可能长期饥饿。
2. 队列虽然写入 `retry_same_model`，worker 却没有读取它。失败现场可能沿用偶然残留的入队计划，但没有“半成品必须交回原 runner/model”的可验证保证。
3. 统一 Stop 后的 CLI 返回码通常为 1；旧分类先看返回码，导致预期停机被记成 `process_exit`，看起来像模型连续失败。

## 修复

- 启动恢复把完整 `reviewing` 事务去重后放回队首，保持原顺序和 `retry_group`，不再退到队尾。
- 调度器按“最早可运行事务”取批：
  - `retry_group` 全组的 `retry_after` 与绑定模型冷却都结束后才整组取出，绝不拆组；
  - 队首失败包仍在退避或模型冷却时，跳过该组，允许后面的新批运行；
  - 无 group 的历史 sticky 项只与相同 runner/model/source 亲和的项同批。
- `retry_same_model=true` 现在由 worker 实际读取。已尝试批次和失败包固定回到原 runner/model；只有尚未尝试的 fresh 批次在启动前调用既有可用性解析器，才允许走 fallback。
- 新失败 manifest 与队列同时保存 `runner`，历史记录缺失时按当前唯一支持的 `opencode` 兼容。
- `sandbox.stopped` 在失败分类中优先级最高，稳定类型为 `lifecycle_stop`，原因为“统一停机中断并全量保全”。它仍然创建完整失败包、更新拒合清单并等待 GLM 重审，但不会计作模型失败或触发 preferred model cooldown。

## 回归覆盖

- 中断事务回到队首、内部去重且 retry group 保持完整。
- 组内只有部分成员到期时不拆组，并且不阻塞后面的 live 批次。
- 原 GLM 处于 cooldown 时失败包等待，但 fresh 批次可运行。
- sticky 批不调用 fallback resolver；fresh 批可以在启动前选择 Kimi fallback。
- lifecycle stop 优先于非零退出、timeout 和 stall；停止路径仍调用保全但不调用模型失败冷却。
- 复盘持久化/失败包测试与 Brain `selfcheck.py` 覆盖最终兼容性。

## 注意事项

- “恢复优先”不等于阻塞队列：物理顺序恢复到队首，能否运行仍由事务级时间与模型冷却共同决定。
- 模型亲和必须在第一次启动前写入 `reviewing.items`，否则恰好在启动后崩溃时无法证明原执行者。
- 正常停机记录不能被吞掉；分类改名只修正运营语义，不能删减取证、清单 commit 或逐包重审闭环。
- 本次只修复现有 OpenCode 两级模型链，没有实现预研中的 Codex/Luna 第三级，也没有重启生产栈。
