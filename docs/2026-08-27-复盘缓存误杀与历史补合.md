# 复盘缓存误杀与历史补合

## 根因

隔离复盘完成后，宿主为了满足“失败时保留全部文件”的要求，以 `git add --all --force`
捕获 tracked、untracked、ignored 和被规则拒绝的全部现场。旧实现随后错误地把这份取证路径
再次当作自动合入验收路径。OpenCode 在分析或执行自检时产生的 `__pycache__/*.pyc` 因而被
判为越过 allowlist，已经通过自检的 Python 源码也随整批被拒绝。

正确模型是三条互不混用的链：

1. 允许源码 patch：只含模型真正要合入、且通过 allowlist 与自检的文件。
2. cache 临时产物：不合入、不阻断，但记录路径并保留原始字节。
3. 全量取证现场：失败时保留所有文件，供人工逐批分析和补合。

cache 分类兼容所有工具：任一层路径名只要包含 `cache`（大小写不敏感），或文件为标准
Python 字节码缓存后缀，都会进入第二类；是否写在 `.gitignore` 中不影响分类。非 cache 的
ignored 或越界文件仍然阻断自动合入。

## Windows 补合包发布

旧实现复制完整 sandbox 后，还会把内部临时目录改名为 `raw_sandbox`。Windows 杀毒、索引器
或刚退出进程的短暂文件句柄可能让目录改名报 `WinError 5`，留下未完成 `.tmp` 包。新实现直接
续拷到包内最终子目录，以外层包发布或 pointer + manifest 作为完成边界；已有半包会在下次
恢复时补齐，而不是因目标目录存在就误判完成。最终原子发布对短暂共享锁有有限重试。

仍有价值的知识结论，排除 cache、`.runtime/rvtmp/`、viewer 日志和锁文件；通过隔离应用检查、
自检、提交和远端确认后，才删除对应失败包与重复 sandbox。最终处理结果会继续追加在本文。

拒合索引另设为受 Git 跟踪的 `sts2-ascend/REVIEW_REJECTIONS.md`。宿主在新失败包完成原子发布后

## 重启 marker 长期阻塞复盘

13:23 的 per-Boss 批次并不是被源码 allowlist 拒绝。现场日志明确显示：旧
`pending_restart.json` 已存在，排他 `os.link` 发布新 marker 报 `WinError 183`，prepare 回调因此
拒绝了已经通过隔离自检的 patch。旧 marker 指向 `c5005a7`，11:33 已累计一局健康；11:36 新
session 后第 731~750 局都完整结束并推送，但 marker 再未更新。

健康数停在 1 的根因是启动版本只探测一次：Agent 开一个 daemon 线程执行 `git rev-parse HEAD`，
若 Windows 杀软/进程检查卡在 `CreateProcess`，超时甚至尚未开始计时；`_boot_head` 会永久为空，
每局健康检查又在加锁和日志前静默返回。一次偶发启动探测故障于是与排他 marker 叠加，演变成
永久拒绝后续代码复盘。

修复拆成三层：

1. Runner 在创建每一代 Brain 前直接读取 `.git/HEAD`、loose ref 或 `packed-refs`，把不可变
   `STS2_ASCEND_BOOT_HEAD` 和当前 `committed` marker commit 一起传给子进程；不创建 Git 子进程，
   不增加直播启动卡顿。健康计数只比较“本代启动时加载的 marker epoch”，不再在游戏线程跑 Git。
2. 新复盘 marker 先以 `prepared` 原子替换旧 marker，并内嵌有界的前任链；工作树 patch 与 Git ref
   都成功后，同一仓库事务内才二阶段确认为 `committed`。Git CAS 失败且 patch 已无损撤销时，abort
   只在 marker 仍属于本次 provisional commit 时恢复前任；若外部 C 已接管则不覆盖 C。`prepared`
   不参与健康、崩溃归因或回滚。
3. 最新复盘启动失败并被 runner 安全反向提交时恢复前任 marker；另写独立的有界 tombstone，即使
   Windows 暂时锁住 marker、runner 本身随后重启，也不会重复反向应用同一 patch。异常重试间隔从
   60 秒缩到 10 秒，五次尝试仍保留，但正常恢复预算回到两分钟直播死线内。
4. 只有本代 Brain 在没有活动 run 时先观察到主菜单/选人局间边界、再从头开始并完整结束的局才推进健康数；
   中途重连局不算。健康记账只等仓库锁 0.1 秒，锁忙就保留 marker 给下一完整局，绝不拖住终局流程。

回归覆盖旧 A → 新 B 接管、发布 B 故障保留 A、B abort 恢复 A、无 A 时 abort 删除 B、迟到 B
abort 不覆盖 C、runner 回滚 B 恢复 A、marker 恢复失败时 tombstone 跨 runner 生效、`prepared`
不进入启动 epoch、完整局/中途重连边界、进程内短锁真实超时、子进程冻结环境传递，以及启动 HEAD
不可读但 committed marker epoch 明确时仍可完成两局健康确认。

### 中间版上线后的第二轮收口

`6574cc4` / `917311c` 已先按直播要求热切换，停止到新栈 ready 用时 46.1 秒，游戏进程全程保留。
随后审计发现并补齐三个罕见窗口：

- Runner 现在持仓库锁创建子进程，并用既有 session-scoped brain PID 文件回显本代唯一 `boot_id`、
  冻结 HEAD/marker 与 `stage=imported`；全模块和 config 完整驻留后立即放锁，再在锁外等待
  `stage=ready`。这样既不混载多文件 patch，也不会和 Knowledge 初始化时的仓库锁形成父子自锁。
- 启动前只对 `prepared` marker 运行有界精确恢复：commit 已在 HEAD/祖先则补二阶段确认；HEAD
  仍是 parent 时，以 provisional commit 的 binary patch 证明“未应用”或“完整应用后反向撤回”；
  两种都证明不了就保留现场，禁止混合版本启动。已回滚 wrapper 会沿内嵌链下钻到最近仍有效前任。
- 一次连续断流现在从第一次启动开始只认同一个 115 秒绝对 deadline；导入、ready、短重试、prepared
  多条 Git、回滚与旧代重启都消费同一预算。复盘代码两次握手失败即回滚，`push=False`，成功后
  不再额外 sleep。prepared 若与外部编辑重叠到无法精确证明，会先原子保存全部目标文件、当前与
  provisional patch、marker，再恢复当前已知 Git 树；失败包由新 worker 自动补录清单。

停止临界区还暴露了清单窗口：失败指针包可能在 daemon 退出前来不及建立清单 commit。新 worker
除补全 raw clone 外，会幂等扫描所有现存 salvage 并补录遗漏 marker；原始包仍是证据真源。另移除
“积压时无视可用 GLM、强制轮换 K3”的旧守卫，积压只影响追及节奏，fallback 只由真实可用性触发。
