# 2026-08-25 复盘模型调度：k3 死锁（守卫反噬）与交替出牌

## 问题

ox-alpha 恢复可用后，复盘仍一直卡在 kimi-k3（且 k3 已不可用）——
上一轮加的"成功复盘守卫"发生**反向死锁**。

## 根因：守卫 v1 的自锁

守卫 v1 逻辑：`距上次成功复盘 >= 5 局 → 强制 k3`。
当 k3 本身不可用时：守卫强制 k3 → k3 失败 → 永无成功 → 永远强制 k3。
**ox-alpha 复活了也没机会被探测**——preferred 计划每次都被守卫翻掉。
数据实证：`last_successful_review_run=262` 冻结，
`last_llm_review_run` 冻结在 266，runs 一路涨到 366——**100 局零成功**。

教训：**"饥饿保护"若不给饥饿源头恢复的机会，就变成反向饥饿**。
任何"状态坏→切备胎"的守卫，必须同时保证主胎定期被探测。

## 修复：守卫 v2——饥饿态交替出牌

- 饥饿（≥5 局无成功）时：上次尝试是 fallback → **放行优先链**（恢复探测）；
  上次是 preferred → 强制兜底。按 `last_review_attempt_source` 交替。
- 任一路成功即刷新 `last_successful_review_run`，退出饥饿态回纯优先链。
- 饥饿态豁免兜底节奏门槛（交替本身就是节奏）。
- **批次来源取最新入队决策**：混批时按"含 fallback 即整场 k3"的旧规则，
  优先链探测永远被 k3 吞掉——最新入队项携带最新的世界状态。
- 追及队列上限 `review_queue_max` 5→10（代码默认+config 双改），
  与 `max_runs_in_packet: 10` 对齐——每场复盘最多追及分析 10 局。

## 验证

- mock 四场景：饥饿交替序列、不饥饿纯 preferred、恢复探测+退出饥饿、
  混批取最新——全过；SELFCHECK OK。
- 生产：重启后第 369 局即放行 ox-alpha → 复盘成功 →
  `last_successful_review_run=369` 刷新 → 饥饿退出；
  第 372/373 局复盘继续在 ox-alpha 上滚动。meta_review 恢复出新章节。

## 运维手法备忘

- 换调度逻辑后可**播种 `progression.last_review_attempt_source`** 引导
  第一场探测方向（已知 k3 挂时播种为 fallback，省一轮 25 分钟超时）。
- 守卫类逻辑的 mock 测试要覆盖"保护机制本身成为故障源"的反向场景。
