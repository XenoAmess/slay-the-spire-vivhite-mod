# 白绮战士全套美术生成与接入

## 完成结果

本次完成的是原版 `IRONCLAD` 的白绮全视觉换皮，现有独立角色
`VivhiteCharacter` 没有修改。白绮的统一设定为银发、紫瞳、金框眼镜、华丽而
冷淡可爱的魔法少女；她是纯粹的空手施法者，不持剑、法杖、魔杖、法书、盾、
手持法球或任何其他武器，也不使用白绫。

仓库现保留三层资源：

1. `assets/ironclad-v0.111.0/`：游戏 v0.111.0 的只读制作模板、骨骼参考和清单；
2. `assets/vivhite-ironclad/`：用户参考图、ImageGen 原图、透明化中间件、190 个
   region 母片、10 张最终 atlas 页、9 张 UI/多人贴图和审计报告；
3. `Vivhite/Vivhite/skins/ironclad/`：发布器生成的 30 个逻辑运行时资源。

Mod PCK 不携带模板目录或复制的 `.skel/.spskel`。四套私有 skeleton-data 组合
“游戏 PCK 内原版 skeleton + Mod 私有白绮 atlas”，既保留全部原动作，又避免
发布原版骨骼 binary。

## 美术生产方式

人物设定图决定服装、蝴蝶、配色和比例，头像参考决定脸、银蓝发质、紫瞳、
金镜与冷淡神态。先生成统一全身 A-pose 身份锚点，再分别生成：

- 战斗/商店基础、攻击、死亡三张高分辨率部件源；
- 一张篝火部件源；
- 一张选人动态背景 atlas 源；
- 头像、选人按钮、地图标记和四张多人手势共七张独立 UI 创意源。

内置生成器在“透明背景”提示下会画出不透明棋盘格，因此透明资产统一使用纯绿
技术底，再由 `remove_chroma.gd` 转为 straight-alpha RGBA。这个后处理会清除
绿边，不使用预乘 Alpha。

ImageGen 不能可靠保持 Spine atlas 的逐像素 region 坐标，所以最终没有直接把
生成整页塞进游戏。`atlas_region_tool.gd` 先按 `.atlas` 解包每个未旋转逻辑
region；`build_vivhite_gameplay_regions.gd` 按头、发、身体、手臂、手、裙、腿、
鞋和法术效果等语义，从批准后的 AI 图确定性裁切迁移；packer 再恢复各页原始
尺寸、bounds、rotate、offset 和页名。

Combat 与 merchant 虽有完全相同的 83 个 region 名，但 42 个同名 region 的
rotate 状态不同，不能整页缩放。逐 region 回包解决了这个问题，并让两套分辨率
共用同一人物与材质来源。

## 无武器实现

- Combat/merchant 的 `sword blade` 与 `sword_handle` 在逻辑母片和最终 packed
  rect 中强制 alpha=0；
- 原 `slash`、`slash2`、`zaps*` 和眼部效果改成紫蓝晶光、魔法弧与蓝蝶；
- 攻击姿态保留原手臂动作，但手中没有物件，攻击读感由事件触发的魔法效果承担；
- Character Select 的 `top arm` 原本是“手臂 + 剑”复合 region，不能仅清空剑
  slot；生产脚本改用独立空手护臂裁片重建该 region，最终页只有裸手和白护臂；
- UI、多人数势、篝火和选人肖像均逐张目检，没有武器、持有物或白绫。

## UI 规格

最终 UI 位于 `assets/vivhite-ironclad/custom/ui/`：

- `icon` / `icon_outline`：85×85；outline 从最终头像 Alpha 程序派生；
- `select` / `select_locked`：132×195；locked 与 select 同构图灰黑派生，不跳帧；
- `map_marker`：49×64，蓝蝶 + 紫晶下指徽记；
- `point/rock/paper/scissors`：422×1200，同一白色分节护臂、底部渐隐和一致锚点。

七张创意 UI 各自调用一次 ImageGen；outline 与 locked 因必须像素同构而不单独
生成。所有透明图的技术绿残留计数为零，手势最高/最宽 Alpha 包围盒按原版锚点
回填。

## 发布与验证结果

仓库内发布：

```powershell
py -3 -B .\tools\art\publish_ironclad_skin.py
```

发布器成功生成 30 个逻辑运行时资源，且没有 `.skel/.spskel`。本次完成的离线
验证如下：

- Gameplay 静态审计：190/190 region 与模板像素不同；10/10 packed PNG 的
  SHA-256 与模板不同；战斗/商店 weapon alpha 全为 0；在全新 `.work/` 初始化
  后重建的四域 212 个 region/layout/atlas/page/report 文件与仓库成品逐文件
  SHA-256 一致；审计还逐块比较当前母片、packed rect 和 build-report 像素哈希，
  故意更新母片但保留旧 atlas 的负向测试以非零码失败；
- UI 静态审计：九张尺寸、Alpha 包围盒、手势语义与绿边检查通过；从已跟踪
  `ui_alpha` 重建到 `.work/` 后 9/9 PNG 的 SHA-256 与 `custom/ui` 一致；缺失源图
  负向测试返回非零码，原输出 9/9 哈希不变且没有遗留事务目录；
- 发布器：严格检查 PNG CRC/zlib/filter/尺寸和解码像素，拒绝仅重编码的原版图；
  atlas 必须与模板逐字节一致；运行时目录精确镜像 30 项并清除陈旧文件；
- Source contract：30 files、19 张 PNG 尺寸、atlas bounds、4 Spine sets 通过；
- Spine 真实加载：combat/merchant 4.2.43、rest 4.2.37、select 4.2.40；所有
  animation、`default` skin、必要 slot/event 通过；
- 完整离线 `dotnet build`：0 warning、0 error；明确设置
  `CopyModOnBuild=false`、`RitsuLibAutoCopy=false` 并把 `ModPckPath` 改到
  `.work/final-validation/dotnet-build/Vivhite.pck`，不允许本 Mod 或依赖包写入
  直播中的游戏目录；
- 隔离 PCK：104 entries，Godot 4.5.1 pack format 3，精确私有 entry 白名单与
  文本 payload 后验通过；没有部署到游戏目录。

Windows 官方 Godot 4.5.1 的 `--headless` 使用 dummy rasterizer。离线探针可以
加载 skeleton-data 并采样 `idle_loop`，但 `SubViewport` 没有真实纹理，无法在
headless 下渲染动画 PNG。仓库保留了只允许写 `.work/` 的
`render_ironclad_skin_preview.gd`；窗口化 GPU 预览留到直播结束后再做，不能把
当前的 headless 加载成功误报为视觉逐帧验收。

## 直播期间的安全边界

制作期间用户正在直播，因此本次只进行了仓库内生图、headless 图片处理、静态
校验、离线 C# 编译和 `.work/` PCK 导出。没有关闭、重启或聚焦游戏，没有操作
鼠标键盘，没有替换 `G:\...\mods\Vivhite`。完整构建只使用 no-copy 属性并把
PCK 输出改到 `.work/`，没有执行会自动部署的普通 `dotnet build`。

真正生效仍需要在可接受的维护窗口执行：

```powershell
cd .\Vivhite
dotnet build
```

然后彻底退出并以 Vulkan 重启游戏。由于 PCK 已在当前游戏进程中加载，不能把
仓库文件或旧会话热替换当成可靠验收。

## 踩坑与后续

- texture-only 保留原战士的骨骼比例、mesh、权重与 deform，因此当前版本是
  “全套可运行重绘”，并不会自动获得设定图那样纤细的新骨架；若真机出现明显
  宽肩或接缝拉伸，下一阶段应在 Spine 4.2 中调整 attachment mesh/权重，而不是
  改坏 atlas 坐标；
- AI 整页生成适合提供统一材质和部件语义，不适合担任 atlas 坐标真值；坐标、
  旋转和 Alpha 必须由确定性工具恢复；
- 原剑区域不能简单改画成“水晶法杖”，因为角色设定明确无武器；最稳策略是
  weapon slot 全透明，并把读感移到 slash/event VFX；
- 选人页的剑和手臂在同一 region，必须重建该复合图，单靠清空剑 attachment
  无法解决；
- 透明棋盘格是生成器画出来的 RGB，不是真 Alpha；必须读取 PNG 像素格式和角落
  Alpha 验证，不能只凭预览判断；
- `CopyModOnBuild=false` 原本只关掉本 Mod 的复制目标，RitsuLib 的 transitive
  target 仍可能独立写 `mods/STS2-RitsuLib`；项目现将 no-copy 模式联动为
  `RitsuLibAutoCopy=false`，离线构建仍建议显式传入两项属性；
- 当前仍缺真机逐帧视觉验收。直播结束后的首要工作是完整构建、Vulkan 重启，
  依次检查 idle/low-health/attack/heavy/cast/hurt/die、商店、三章篝火、选人
  动画和多人手势；发现网格问题后从对应 region 母片修，不直接涂 packed page。
