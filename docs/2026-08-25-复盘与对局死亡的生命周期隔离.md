# 2026-08-25 复盘与对局死亡的生命周期隔离（掐断路径排查）

## 问题

"LLM 复盘到一半，新的对局死了，复盘会不会被掐断？"

## 结论：主路径安全，但存在两条真实掐断/丢失路径（已修）

### 安全的部分（设计如此）

- 复盘 worker 是大脑进程内的守护线程 + 独立 opencode 子进程，与游戏状态解耦；
  对局死亡本身不触碰复盘。
- `request_restart` 只在**局间**生效（agent.py 对局结束处理器里 `sys.exit(42)`，
  "此时处于局间，重启无损"）；主循环每 tick 有异常兜底，大脑进程不会因
  对局内异常退出；runner 只在大脑进程退出后才介入。

### 掐断路径一：局末退场带走正在执行的复盘

复盘 C 局中完成 → 置 `request_restart=True` → worker（无闸门）**立刻开跑
下一场复盘 A** → 该局结束时 `sys.exit(42)` → A 随进程死亡被孤儿化，
opencode 变孤儿继续跑、改文件没人收集。

### 丢失路径二：中断的复盘对局被直接丢弃

大脑无论因何中断（exit 42 / 崩溃 / 被杀），正在执行的复盘覆盖的对局在
`reviewing` 标记里；旧逻辑启动时**只清标记不入队**——这些对局永远丢失复盘。

### 实证活案例

修复上线后的第一次自然重启恰好复现了路径一：372~373 复盘局中完成置位 →
worker 开跑 374~377 → 局末退场孤儿化（孤儿 opencode 存活 6 分钟被查获）。
新大脑首次局末：孤儿被清 → 374~377 重新入队 → 追及批次 [374~379] 共 6 局
正常执行。全链路自愈。

## 修复（b7c8933）

1. **worker 闸门**：`request_restart` 已置位时拒绝开新场次（pending 原地保留，
   由下一个大脑消化）——濒死大脑不再开注定被掐断的复盘。
2. **中断复盘重新入队**：worker 启动时把 `reviewing.runs` 重新入队追及
   （此前只清标记），对局永不丢失。
3. **孤儿清理**：worker 启动时按命令行特征（`sts2-ascend` + `--auto`，
   用户会话不含此组合）精确击杀遗留 opencode，防双写。
   注意 worker 是懒启动（首次 run end 才拉起），清理发生在局间而非进程启动时。

## 验证

- mock：restart 置位不开新场次且不丢队；中断复盘重新入队被下一场执行。
- 生产：自然重启复现竞态 → 自愈序列完整落地（见上）。

## 备忘

- runner.py 尾部曾有一段重复的 `__main__` 块（无害），顺手清除。
- 生命周期设计口诀：**异步任务的安全退出点要和重启点对齐**——
  重启标志置位后，进程内一切"准备开新活"的路径都必须闸死。
