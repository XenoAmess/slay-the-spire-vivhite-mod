# sts2-ascend 原生 GAME_OVER 分数与解锁完整落盘

## 范围与证据基线

本文描述自动游玩终局链的完整目标契约，证据基线为：

- 根仓 `e2a4bdbf`；其中已经包含 `e018e72d` 的跨进程 Brain 账本恢复。
- 嵌套 STS2-Agent 的原生存档验证基线 `6861d6c`。
- 在该基线上完成的 MCP 动作不重放与即时状态对账实现；当前仓内对应提交为 `a8676a0`。
- 尚待主任务集成的 `.tmp/brain-native-save-barrier.patch`。

本文会明确区分已经提交的实现、待集成屏障以及无法从历史持久产物证明的事实。Brain 与 MCP 不仿造
角色分数、epoch 或解锁，也不直接写游戏存档；它们只驱动原生按钮、观察原生 `progress.save`，并在
证据完整后推进 Brain 自己的账本。

## 问题与根因

人工游玩死亡后，游戏会先进入 GAME_OVER 引导，再由原生总结流程累计角色分数、推进 epoch/解锁，
并保存角色进度。旧自动游玩链在 GAME_OVER 直接调用 `NGameOverScreen.ReturnToMainMenu`。这能够离开
界面，却没有点击 `NGameOverContinueButton`，因而可能绕过承担这些副作用的原生总结协程。

所以“经验条没显示”不是纯 UI 问题。即使已经回到主菜单，也不能据此推断分数、解锁和存档已经成功；
`summary_ready` 也只证明总结界面动画结束、返回按钮可用，不等于磁盘写入成功。

## 原生 Agent 状态协议

`6861d6c` 将完整状态协议提升为 `state_version=13`，并将
`agent_view.version` 提升为 `8`（下文简称 `agent_view_version=8`）。完整状态与精简 Agent View 都在
`game_over` 中暴露存档证明：

- `phase`
- `can_continue`
- `can_return_to_main_menu`（Agent View 中为 `can_return`）
- `save_status`
- `save_verified`
- `save_error`

### 真实 GAME_OVER phase

phase 必须使用 Agent 实际输出的值：

- `intro`：真实 Continue 可操作，且 Main Menu 按钮尚未就绪；只应执行
  `continue_game_over`。
- `summary_animating`：Continue 已离开，而 Main Menu 按钮尚未就绪；只能等待。
- `summary_ready`：真实 Main Menu 按钮可操作；此时才开始验证磁盘存档，但不能仅凭该阶段离场。

phase 由按钮的 `Visible`、`IsEnabled` 和 `IsVisibleInTree()` 共同判定。
`continue_game_over` 对 `NGameOverContinueButton` 执行 `ForceClick()`；
`return_to_main_menu` 对 `NReturnToMainMenuButton` 执行 `ForceClick()`。后者不再直接调用
`NGameOverScreen.ReturnToMainMenu`。

### 存档证明三态

字段组合是严格协议，而不是三个可以独立猜测的提示值：

| `save_status` | `save_verified` | `save_error` | 含义与允许动作 |
| --- | ---: | --- | --- |
| `pending` | `false` | `null` | 尚未获得磁盘证明；继续轮询，不提交 Brain 终局，不离场 |
| `verified` | `true` | `null` | 当前内存进度与真实磁盘 `progress.save` 一致；允许进入 Brain 终局事务 |
| `error` | `false` | 非空错误码 | 没有获得磁盘证明；保持阻塞，不提交、不轮换、不离场 |

缺字段、字段类型错误、未知状态，或诸如 `verified + false`、`pending + true`、
`verified + 非空错误` 的矛盾组合，都必须按错误处理。任何消费者都不能把“不是 error”、
`summary_ready` 或 `can_return=true` 当作成功证明。

## `progress.save` 的真实重读与语义校验

Agent 不补写存档，也不重新调用原生保存函数。它只观察原生总结流程的结果：

1. 在 `summary_ready` 前返回 `pending`。
2. 读取 `SaveManager.Instance.Progress.ToSerializable()`，把 schema 设为当前
   `SaveManager` 对 `SerializableProgress` 的最新版本，再通过游戏自己的序列化器生成期望 JSON。
3. 由 `UserDataPathProvider.SavesDir`、`ProgressSaveManager.fileName` 和当前 profile 作用域解析出
   实际 `progress.save` 路径。
4. 以只读方式重新打开磁盘文件；共享模式允许游戏同时读、写、删除，验证器本身不持有写权限。
5. 用严格 UTF-8 读取并分别解析内存快照与磁盘 JSON。
6. 对两棵 JSON 树递归比较，而不是比较文件时间、长度或“文件存在”：
   - 对象要求成员集合与数量相同，但忽略对象属性顺序；
   - 数组保持顺序并逐项相等；
   - 字符串、布尔值与空值逐值相等；
   - 数字按原始 JSON 文本严格相等；
   - 额外字段、缺失字段、类型差异或值差异都会失败。

成功才返回 `verified/true/null`。profile 未初始化、路径不可用、文件缺失或为空、读取失败、非法
UTF-8/JSON、内存快照非法或内容不一致，都会返回 `error/false/<错误码>`。典型错误码包括：

- `progress_profile_not_initialized`
- `progress_snapshot_empty` / `progress_snapshot_invalid_json`
- `progress_save_path_unavailable`
- `progress_save_missing` / `progress_save_empty`
- `progress_save_read_failed:<ExceptionType>`
- `progress_save_invalid_json`
- `progress_save_content_mismatch`
- `progress_snapshot_failed:<ExceptionType>`

这条校验覆盖当前完整 `ProgressState` 序列化结果，而不是只核对本局新增分数。这样既能证明分数和解锁
相关字段已随原生事务落盘，也不会因为旧文件仍存在而产生假阳性。

## Brain 的 fail-closed 存档屏障

`.tmp/brain-native-save-barrier.patch` 把磁盘证明放在所有 Brain 终局副作用之前。目标顺序固定为：

1. `intro` 点击原生 `continue_game_over`。
2. `summary_animating` 只等待。
3. `summary_ready` 读取 `save_status/save_verified/save_error`。
4. 只有精确的 `verified + true + 无错误` 才调用既有幂等 `_finalize`。
5. `_finalize` 成功持久化分角色统计、最终运行日志和学习状态，再提交轮换终局账本。
6. 只有上述原生证明和 Brain 账本都成功后，下一次决策才允许点击真实
   `return_to_main_menu`。
7. 后续每个 `UNLOCK` 屏逐个使用 `confirm_unlock`；按钮未就绪时等待。

`pending` 只等待。`error`、缺字段、错误类型、矛盾组合或未知 phase 都 fail closed：不得调用
`_finalize`、不得增加局数、不得写轮换终局、不得发 `return_to_main_menu`。相同
`(run_id, reason)` 的阻塞日志去重，但后续轮询仍可观察游戏是否自行恢复为 `verified`。

屏障同时覆盖“准备终局”路径和任何 `return_to_main_menu` 决策过滤路径。因此不能从旧的
GAME_OVER 回声、重连分支或其他决策路径绕开。Agent 动作端点目前仍以 UI 可操作性判断
`return_to_main_menu` 是否可调用，所以直接使用 MCP/HTTP 的外部调用者也必须遵守这组三字段契约；
自动栈由 Brain 强制执行。

### 人工接管不能绕过

按 `Ctrl+Alt+F9` 触发的人工接管局会被标为 `human_assisted`，并从自动学习、分角色统计、LLM 复盘和
轮换配额中排除。但这只是 Brain 数据隔离规则，不是游戏存档豁免。

人工接管局同样必须先得到 `verified + true`。在原生存档未验证时，即使该局不会计入 Brain 统计，也
不能返回主菜单。否则会出现“Brain 没污染，但人工获得的原生分数/解锁仍丢失”的同一故障。

## MCP：动作 POST 不重放，并立即对账一次

终局 Continue、返回主菜单和确认解锁都是有副作用的动作。请求可能已在游戏内执行，但响应在网络或
读取阶段丢失；此时自动重发会造成双击，例如一次响应丢失的 `confirm_unlock` 可能把下一个解锁页也
一并关闭。

当前 MCP client 对动作 POST 采用以下规则：

- 动作 POST 的 `retry_count` 固定为零，最多发送一次。
- 若收到结构完整的 API 错误，结果是“服务端明确拒绝”：不重放、不对账，并强制
  `retryable=false`。
- 若发生超时、断连、响应体读取失败、截断或非法 JSON、响应 envelope 缺字段/类型错误等，结果为
  `outcome_unknown`：动作可能已经执行，绝不重发原 POST。
- 在构造并返回 `outcome_unknown` 之前，`Sts2Client` 会立即发起一次真实
  `GET /state`。这不是一条仅供调用方执行的文字建议，而是 client 已经实际进行的一次网络读取。
- 这次即时对账 GET 直接调用底层传输，只尝试一次，不走普通请求的重试循环，也不执行退避。
- `OSError`、`ValueError` 和 `http.client.HTTPException` 的正常/错误响应读取失败都会进入不确定
  动作流程；`KeyboardInterrupt` 与 `SystemExit` 不被吞掉。

因此，一个不确定动作的首次返回具有固定外层字段：

- `status="outcome_unknown"`
- `outcome_unknown=true`
- `stable=false`
- `retryable=false`
- `error.code="action_outcome_unknown"`
- `reconciliation`：即时 GET 的结构化结果

### `reconciliation` 成功结构

即时 GET 成功解码状态时：

- `attempted=true`
- `method="GET"`
- `path="/state"`
- `submitted_action=<实际提交的非 null 动作字段>`
- `succeeded=true`
- `status="succeeded"`
- `required=false`
- `state=<真实 GET /state 返回的状态>`

这里的 `required=false` 只表示 client 已成功取得一次状态，不表示业务上已经证明动作成功。
调用方必须优先使用 `reconciliation.state`，结合 `submitted_action` 做动作特定的语义判断。

### `reconciliation` 失败结构

即时 GET 本身失败时：

- `attempted=true`
- `method="GET"`
- `path="/state"`
- `submitted_action=<实际提交的非 null 动作字段>`
- `succeeded=false`
- `status="failed"`
- `required=true`
- `error=<结构化读取或 API 错误>`

失败结构没有可用的 `state`。`error.retryable=false` 表示这一次内嵌对账不会自行重试，不表示允许
重放动作 POST。

### 调用方对账顺序

调用方处理 `outcome_unknown` 时必须遵循：

1. 先读取 `reconciliation`。
2. 若 `succeeded=true`，先用其中的 `state` 对账，不能无视已取得的状态再盲发请求。
3. 若即时对账失败，或返回的状态不足以证明动作已应用/未应用，只能继续执行只读 GET。
4. 在取得动作特定的确定证据前，不得发起后续有副作用动作，更不得重发原 POST。

动作特定证据示例：

- `continue_game_over`：观察 `intro` 是否已经离开，以及 phase/可用动作是否推进。
- `return_to_main_menu`：观察是否已经进入 `MAIN_MENU`、`TIMELINE` 或 `UNLOCK`。
- `confirm_unlock`：观察当前解锁实体或 screen 是否已变化。

状态仍不足时继续只读，不猜测、不重发。

### 即时无重试 GET 与普通 GET/HEAD 的区别

两类读取不能混为一谈：

- `outcome_unknown` 内嵌的即时 `GET /state` 是保守的一次性对账：直接读一次，不重试、不退避，
  成功或失败都写入 `reconciliation` 后立即返回。
- 普通 GET/HEAD 仍走 `Sts2Client._request` 的原有语义：对符合原逻辑的 `URLError` 和明确标记
  retryable 的 HTTP 错误，最多按 `max_retries` 重试并退避；其他读取、解码或异常类型继续保持原有
  传播语义，并不因为动作安全改造而统一重试。

所以，即时对账失败或语义不足后，调用方可以再调用普通只读状态接口；这些后续 GET 使用普通读取的
重试规则。无论只读 GET 执行多少次，动作 POST 仍然只发送一次。

## 跨进程终局恢复的证明边界

根仓已提交的 `e018e72d` 处理下面的 Brain 崩溃窗口：

> Brain 已写完最终运行日志和角色统计，但在 `rotation.record_terminal` 原子发布前进程退出。

下一进程启动时只检查轮换账本中仍活动的精确 `run_id + character_id`，并要求：

- 对应角色 profile 能解析且与活动角色一致；
- 最终运行日志包含完整必需字段，且 `run_id/profile_id/character_id` 全部匹配；
- 不是 `in_progress`、`human_assisted` 或 `excluded_from_learning`；
- `victory`、时间、决策、战斗记录和归因字段类型完整；
- `run_number` 与 `profile_run_number` 是排除布尔值的正整数且相等；
- 角色统计中的持久化局数严格等于 `profile_run_number`，不能落后，也不能“超前猜测”。

证据全部成立才补做一次 `record_terminal(..., terminal_persisted=true)`，并依赖持久 run-id ledger
防止第二个进程重复翻转。任何缺失、损坏、身份不匹配、人工局、旧局或统计序号不一致都保持活动槽位
阻塞。

但这些持久产物只证明 Brain 的最终日志和角色统计存在。现有终局日志、角色统计与 rotation ledger
都没有独立记录 `save_status/save_verified/save_error`，也没有原生存档证明 token。因此：

- 跨进程恢复不是 `progress.save` 恢复，也不能单独证明某个历史终局通过了原生存档屏障。
- 屏障集成之前留下的旧终局，即使日志和统计满足恢复条件，也不能从这些产物反推原生存档已验证。
- 只有明确由“已经集成并启用 fail-closed 屏障”的版本新产生的终局，才能依赖执行顺序得到保证：
  先 `verified`，后写最终日志和角色统计，再发布 rotation。
- 不得把这条“集成后新终局的顺序保证”追溯应用到历史持久产物。

这一区分也意味着，文档不能把 `e018e72d` 描述成原生存档验证机制；它只是 Brain 账本事务最后一步的
跨进程补发与 run-id 幂等机制。

## 四段事务与最终不变量

对屏障集成后新产生的终局，完整顺序为：

`原生 Continue/总结 → progress.save 重读验证 → Brain 角色账本 → rotation run-id ledger → 原生离场/解锁队列`

最终不变量如下：

- `summary_ready != save_verified`。
- 原生存档未验证时，Brain 不提交终局、不轮换、不离场。
- Brain 账本未持久化时，不轮换、不离场。
- 轮换只有在终局日志与角色统计成功后才推进一次。
- 动作 POST 最多一次；不确定时 client 立即只读对账一次，调用方先消费该状态。
- 即时状态不足或读取失败时只能继续只读 GET，不得重发 POST。
- 人工接管只改变 Brain 归因，不改变原生存档屏障。
- 历史 Brain 持久产物没有原生存档证明，不能获得追溯性保证。
- 原生 `progress.save` 与 Brain `knowledge/profiles/<profile>/` 是两个独立事务，任一成功都不能替代
  另一份证明。

## 故障处理

- `pending` 长时间不变：先查原生总结协程和 Main Menu 按钮是否真正进入 `summary_ready`，不要强制
  离场。
- `progress_save_missing/read_failed/invalid_json/content_mismatch`：保留当前 GAME_OVER 屏和错误码，
  检查实际 profile 路径、游戏原生日志及写入时序；禁止由 Brain 手工补写。
- `outcome_unknown` 且 reconciliation 成功：先使用内嵌 `state` 对账；证据不足才继续只读 GET。
- `outcome_unknown` 且 reconciliation 失败：记录结构化 `error`，继续普通只读 GET；禁止重发 POST。
- 重启后活动 run 未推进：核对最终日志、角色身份、角色统计局数与 run 序号；不要把这些检查结果解释
  成原生存档证明。
- 多个 UNLOCK 连续出现：逐屏等待 `confirm_unlock` 可用并确认，不使用固定坐标盲点。

## 经验与注意事项

- “按钮可点”“总结动画结束”“成功回主菜单”和“磁盘已落盘”是四个不同事实，必须分别取证。
- 验证存档要读取当前 profile 的真实文件并比较完整内容；只看文件存在、mtime 或单个分数字段不够。
- 原生存档、Brain 角色账本和轮换 ledger 是有先后依赖的独立事务，不能把任意两步合并成一个成功
  标志。
- 对未知动作结果，先消费 client 已取得的状态；只有证据不足时才继续只读，绝不能重发有副作用请求。
- 跨进程恢复的证据能力由持久字段决定；没有保存原生证明，就不能为屏障集成前的旧局补造证明。
- fail-closed 的意义是保住集成后新终局的原生进度和角色统计一致性；它不是人为玩法上限，也不改变
  任何白绮卡牌数值。
