# 工作树与索引积压根因及恢复

日期：2026-08-31

## 结论

本轮看到的“海量未提交改动”不是单一问题，也不能概括成“做了很多代码但没有 commit/push”。历史上数量最夸张的 `D + ??`、`MM` 和 staged 记录，主因是复盘提交使用私有 index 成功建立并推送 commit 后，真实 `.git/index` 的精确同步持续受到 `index.lock` 阻挡。HEAD 已经前进，真实 index 却仍混合保留多个旧基线，于是 Git 把已经提交的内容再次显示成 staged 删除、修改或同路径 untracked。

恢复后的剩余项分属不同所有权：15 条明确保留的用户暂存、仍在各自任务中处理的工作树修改、`.tmp` 临时报告/patch/截图、美术生成与验收证据，以及按复盘协议被忽略但必须保全的 `review_work` / `review_salvage` 现场。它们不能仅凭 `git status` 行数被当成同一批“漏提交代码”。

## 根因：commit 成功，真实 index 后处理失败

自动 Git 与复盘 patch 的正常事务分为两层：

1. 从当时的 HEAD 创建独立 `GIT_INDEX_FILE`，只把本次精确路径写入私有 index；
2. 从私有 index 建立 commit，以 compare-and-swap 更新分支，并按事务配置推送；
3. 最后只把本次目标路径在真实 `.git/index` 中同步到新 commit，同时保留事务开始前的其他用户暂存。

故障发生在第 3 步。真实 index 被其他 Git 进程持有 `index.lock` 时，同步不能完成；但第 1、2 步建立的 commit 和已经前移的分支不会因此消失。旧 review patch 路径又没有覆盖这一窗口的耐久恢复事务，后续提交继续推进 HEAD，真实 index 则逐渐成为由多个旧时刻条目组成的混合快照。

Git 状态由 `HEAD ↔ index ↔ worktree` 两次比较产生。HEAD 前进而 index 留在旧树时，即使工作树内容已经与 HEAD 完全相同，也会显示为 staged；新文件或曾经删除/改名的路径还会形成肉眼看起来像“删除后又出现”的 `D + ??`。因此这是索引账本陈旧，不等于对应工作树内容尚未进入提交历史。

现有代码和历史提交与该解释一致：

- `sts2-ascend/brain/autogit.py` 的 review patch 路径明确记录“HEAD 已因 patch 前进，但 `index.lock` 令真实 index 停在 parent”的恢复场景；
- 提交 `e81da2c311083f2ad5b975f8b0b83928a218a3d6`（`fix(brain): recover review patch index transactions`）为 review patch 补上耐久 index journal；
- journal 在工作树或 ref 变化前保存 parent、候选 commit、精确路径和原目标 index 快照；下一笔事务在把 staged overlap 解释为用户意图之前先尝试恢复；
- 恢复时若发现后来确有用户改动 index，就保留后来内容，不自动覆盖。对应提交增加了“下一次事务恢复锁失败现场”“新文件 `D + untracked` 恢复”“绝不覆盖后来用户暂存”三类定向回归用例。

## 原始现场保全与数字复核

修复真实 index 前，现场完整保存在：

`sts2-ascend/knowledge/code_backups/index_recovery/20260831-1618-stale-machine-index/`

| 文件 | 字节数 | SHA-256 |
| --- | ---: | --- |
| `index.before` | 719,733 | `F3001C3F6CA7ED089605B9FFCD5331E1112C00B9EA674F3B0C40AE97B36370CA` |
| `staged.before.patch` | 382,769,504 | `15AFA3CD8C2BDB5EFEF50B63B95CA870888A04E0DD869BDB43F926BBFEB56F23` |

上述哈希已从当前备份文件本体重新计算。`staged.before.patch` 可复核出 1039 个 `diff --git` 段，与恢复时记录的 1039 个 staged 路径一致。不要拿该旧 index 对当前 HEAD 重新计算 staged 数量：HEAD 在恢复后仍由 Brain 正常推进，跨基线比较会把后续提交也算进差异，不能替代当时的 1039 路径现场。

恢复分类器 `.tmp/classify_and_repair_stale_index.py` 对每条 staged 路径执行以下证明：

- 路径必须在当时 HEAD 中存在，且是普通 blob，不是 gitlink；
- 工作树文件必须存在；
- 使用 `git hash-object --path=<path>` 应用仓库 clean-filter 后计算工作树 blob；
- 只有工作树 blob OID 与 HEAD blob OID 完全相同，才进入可恢复集合。

最终只有 1008 条满足上述条件。恢复操作仅对这 1008 条分批执行 `git restore --staged --source=HEAD -- <精确路径>`，只修真实 index，不改工作树文件。其余条目没有因为“看起来像假脏”而被批量重置。旧占位资源的孤儿 index 条目也仅解除索引记录，没有删除对应工作树内容。

## 被忽略的复盘现场为什么不能计为漏提交

`sts2-ascend/.gitignore` 整体忽略 `knowledge/code_backups/`。当前该目录下仍存在 `review_work/` 和 `review_salvage/`，所以它们不会出现在普通 `git status` 中，但会占用磁盘并在全盘清理时被看到。

这是复盘保全协议的预期行为：

- `review_work/` 从创建起保存无 remote、无 hardlink 的隔离 clone/快照；
- 复盘超时、进程失败、自检失败、路径拒绝或提交冲突时，`review_salvage/<批次>/` 保存完整工作树改动、`files/`、`raw_sandbox/`、patch、provider 输出、报告与 manifest；
- 宿主不能自动套用旧 patch，也不能在远端确认补合或确认无有效成果前删除失败包；
- `REVIEW_REJECTIONS.md` 只是受跟踪索引，不替代失败包原始证据。

本轮抽查的最新失败包 `20260831-163937-1788165577282377100-46475d21` 含 `files/`、`raw_sandbox/`、`manifest.json`、报告与候选 inventory；manifest 标明 `failure_kind=lifecycle_stop`、`raw_sandbox_included=true`、`auto_apply=false`，并明确要求只作为证据交回模型重审。这证明这些 ignored 目录是有生命周期和闭环条件的取证现场，不是普通“未提交文件”。

## 后续操作边界

- 禁止用 `git reset --hard`、全仓 `git add -A` 或 `git clean` 消除状态行；这些命令会混淆用户暂存、任务成果与取证现场。
- 修复 index 前先保全原 index 和 binary staged patch，并记录长度与 SHA-256。
- 只对能够证明 `worktree blob == HEAD blob` 的精确路径修复 staged；不通过证明的路径保持原样。
- 自动提交继续使用私有 index、精确 pathspec、分支 CAS 与耐久 index journal，不把真实用户 index 当作提交输入。
- `.tmp`、美术证据和独立任务修改分别审查；ignored 复盘包只按 manifest、拒合账本和远端闭环状态处理。
- 汇报工作树时至少区分 committed history、真实 index、tracked worktree、untracked 和 ignored forensic state 五层，不能再用一个“未提交改动数”代替。
