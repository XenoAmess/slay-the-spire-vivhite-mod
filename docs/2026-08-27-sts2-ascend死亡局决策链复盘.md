# sts2-ascend 死亡局决策链复盘

## 问题

`knowledge/runs/*.json` 虽保存每个成功动作的 `action/params/reason`，旧复盘却只把每局最后
5 条战斗摘要和最多 3 条地图、事件、休息理由送给模型。战斗中的出牌、药水和结束回合过程
基本不可见，模型无法可靠判断“手里有牌、有能量却结束回合”。直播驾驶舱展示的
`SCAN → GATE → RANK → LOCK` 此前又只是覆盖式运行快照，没有进入历史 run。

## 体积与取舍

2026-08-27 的真实样本中：

- 现有复盘提示词约 115 KB；
- 最近 100 个完整 run 的逐动作链共 6,626,836 字节、23,826 条决策；
- 平均每局约 66 KB，最新第 713 局为 94,770 字节、337 条决策；
- 当前第 705/706/707/709～713 局整批为 479,106 字节。

GLM-5.3-Flash 的本地 OpenCode 元数据显示 1,000,000 token 上下文；100 局全量链再叠加代码、
原生知识和工具输出没有安全余量。因此采用明确的证据层级：每批最新死亡局的所有已持久决策
必须完整内嵌，其他局保留有界趋势摘要。第 709～713 局实测新提示词为 209,086 字节，完整
包含第 713 局全部 337 条决策；相比旧提示词增加约 94 KB，仍远低于模型上下文上限。

“2x usage”是 OpenCode Go 对该模型的配额标签，不应误解成文本体积自动翻倍。输入本身的
直接增量约为一局决策链；按现有中文 JSON 粗略估计通常增加数万 input token，而不是把
100 局数百万 token 一次吞入。

## 实现

- `llm_review.py` 的摘要与完整链共用同一 active/compact 证据解析路径；不会拿 fallback 最近局
  冒充指定批次。
- `decision_chain_evidence.full_failure_run.decisions` 选择本批局号最大的失败局，保留所有字段、
  所有行和完整 reason，不做 200 字裁剪。
- 提示词明确要求先逐条阅读该链，并按楼层、回合、动作引用证据；其他局允许只做趋势分析。
- 新 run 的每个战斗动作补记 `turn/energy`。`end_turn` 额外保存有界手牌、可用动作、来伤及
  富决策轨迹；高信息的路线、休息、事件、选牌、商店和药水选择也保存轨迹。例行出牌仍保持
  紧凑，避免日志无意义放大。
- 历史 run 没有新字段时保持兼容，仍会把已有逐动作链完整交给模型。

## 上线注意

Python 模块不会热加载。所有语法检查、自检和单测必须在旧 Brain 在线时完成；确认健康后才用
统一入口 `Stop-Agent.ps1 -KeepGame` 紧接 `Start-Agent.ps1 -SkipDeploy`，不部署 DLL、不关闭游戏，
把 Brain 断流控制在两分钟内。上线后同时核对新 session/PID、游戏 PID 未变、dashboard 心跳、
runner 日志和复盘队列恢复，不能只看 `Stack ready`。
