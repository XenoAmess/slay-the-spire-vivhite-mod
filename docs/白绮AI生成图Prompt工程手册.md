# 白绮 AI 生成图 Prompt 工程手册

> 状态：长期维护文档
> 最近更新：2026-08-31
> 适用范围：原版战士视觉替换、独立白绮角色及其卡牌、UI、Spine、Sprite、场景美术
> 生成链分流：不透明完整图使用 Codex 原生图像生成；只有明确需要 Alpha 的透明素材使用
> EvoLink `gpt-image-2` + `background: "transparent"`

## 1. 结论先行

AI 生图在本项目中适合承担“完整、可被自然理解的视觉对象”，不应被当作像素级抠图、
Alpha 清理器、atlas 排版器或 Spine 自动拆件器。

生成工具必须由最终消费者决定，而不是由历史习惯决定：

| 消费者 | 唯一生成路径 |
| --- | --- |
| 完整、不透明、有场景背景的卡牌插画或场景成品 | Codex 原生图像生成能力 |
| 源码明确需要独立 Alpha 叠层的 Sprite、Spine 部件或透明 VFX | EvoLink 原生透明链 |

不得用 EvoLink 透明链生成完整卡图，也不得先生成透明人物再补背景。“方便以后抠图”不构成
透明需求。卡图专属消费、场景、裁切、Prompt 和验收规范见
[《白绮卡牌图片生成技术规范》](白绮卡牌图片生成技术规范.md)。

当前最稳定的对象包括完整人物姿势、头像、按钮肖像、徽记和蓝蝶等独立饰物。最困难的
对象是脱离上下文的前发、脸壳、躯干、单段大腿/小腿、关节端面和隐藏搭接片。困难并不
全来自模型：右靴八轮复盘证明，错误的朝向契约会让模型连续八次“正确执行错误要求”；
右大腿复盘又证明，透明 PNG 直显和低 Alpha 绝对数量会把实际干净的图误判成有光晕。

因此每次失败必须先归因，再决定是否改 Prompt：

1. **消费契约错误**：方向、slot、pivot、遮挡或尺寸理解错；先修规格，不能怪模型。
2. **Prompt 错误**：词语诱导了假发、胶囊、产品展示图或多余装饰；改正正向语义。
3. **模型错误**：没有遵守已经正确、明确且可验证的要求。
4. **验收错误**：错误显示透明 RGB，或只按绝对低 Alpha 像素数排名。
5. **集成错误**：单图合格，但关节叠放、缩放、过滤、网格或动画后不合格。

四角透明、四边不触、`Alpha < 128` 像素较多，都不能单独证明图片有可见光晕；聊天工具
或普通图片查看器也可能显示 `Alpha=0` 像素内保留的 RGB。最终判断必须使用真实 Alpha
SourceOver 合成，并在实际叠层和动画中复核。

白绮还有一条不因卡牌、姿势或特效用途而改变的口部硬禁令：嘴角、嘴唇、牙齿、口腔及
脸部附近不得出现红色或猩红色长条、细线、丝带、液滴、液体、血丝，亦不得出现任何看似
从嘴里向外延伸的魔力。玩法关键词“謦欬”只存在于规则与文本中，禁止把它画成口部出血、
吐血丝或嘴边红线；卡图也不需要为生命费用额外发明口部视觉符号。命中该禁令的结果只能
保留为历史审计，不得进入运行时，也不得作为后续生成参考。

## 2. 当前证据集

截至 2026-08-31，追加式 EvoLink 付费归档共有 117 个请求、112 张返回 PNG 和 5 次无 PNG

所有 117 个已归档 EvoLink 请求均为：

- endpoint：`https://api.evolink.ai/v1/images/generations`；
- model：`gpt-image-2`；

## 3. 生成调用前先写“消费契约”，再写 Prompt

任何 Prompt 的第一份输入不是人物设定图，而是游戏真正如何消费这张图。

必须先回答：

- 它是单幅图片、单帧、spritesheet、atlas page，还是 atlas region？
- 谁加载它：C# getter、Godot 场景、Spine skeleton-data、slot 还是材质？
- 绑定哪个 bone、slot 和 attachment？pivot 在哪里？
- 它在画面中的真实朝向是什么？“左腿/右腿”是解剖侧还是屏幕侧？
- 上下层是谁？哪些区域必须藏在相邻部件后面？
- 运行时缩放、过滤、相机和安全画布是多少？
- 动画中最大旋转会暴露哪些隐藏像素？

证据优先级：

1. 实际消费源码和场景；
2. 当前候选/原版骨骼、atlas、region、pivot 和动画；
3. 已确定视角的白绮战斗母版；
4. 原始人物设定图和头像；
5. 肉眼推测。

“最新认可母版”和“构建器实际输入”必须用路径与 SHA-256 分别确认，不能凭文件名或记忆
当作同一张图。本轮左小腿复盘发现，人工讨论常用的 `0022` 战斗母版并不是 split builder
当前默认输入；builder 实际消费的 `vivhite-combat-body-master-v1.png` 与 `0018` 相同。
`0022`、`0018` 的腿部画面方向和硬编码骨轴还存在冲突。如果生成代理只看 `0022`，绑定代理
只看 builder，双方都可能各自正确却无法组装。生成规格卡因此还必须记录“用于视觉参考的
母版”和“运行时/候选实际消费源”两项，发现不一致时先停付费调用并决定哪一个是新真值。

右靴是反例：八轮 Prompt 都要求“鞋尖朝左、鞋跟在右”，模型稳定照做。项目随后选择
`0022` / 新 rig 的“鞋尖朝屏幕右、鞋跟在左”作为目标方向，因此八张相对新目标全部反向；
但 split builder 当前实际采样的 `0018` 恰好仍是旧反向历史素材，且硬编码 ankle→foot
位置向量本身没有 toe child，不能单独证明鞋尖语义。正确结论不是“builder 一直正确”，
而是生成前没有先统一 `0018` 旧消费者与 `0022` 新目标。增加重试次数只会更稳定地生成
已经决定淘汰的方向。

建议在生成前为每个语义素材写一张最小规格卡：

```text
id / runtime consumer / slot / bone
screen-space orientation
pivot and hidden overlap zones
target silhouette and aspect ratio
source references and each reference's role
forbidden adjacent parts
actual-size acceptance target
```

## 4. Prompt 的推荐骨架

本项目效果最稳定的 Prompt 不是长篇文学描述，而是有清晰层级的生产契约：

```text
Use case: <identity-preserve | stylized-concept | production-pose>
Asset type: <exactly one concrete visual object>

Consumer contract:
<它绑定在哪里、屏幕方向、pivot/遮挡事实；只写已核实的信息>

Input images:
Image 1 defines <identity / costume / exact pose / edge style>.
Image 2 defines <only one other explicit role>.

Primary request:
Draw exactly one <object>. <主体、姿势、视角和身份要素>.

Orientation and geometry:
<用 screen-left/right、upper/lower、轴线、宽高比、端点和搭接区描述>

Style and material:
<平涂层级、描边、材质、允许的内部高光；尽量使用正向描述>

Composition:
<画幅、主体占比、四边留白、不可裁切的关键尖端/手指/鞋底>

Constraints:
<只列真正可能出现且会破坏用途的对象、武器、多视图、文字和场景>
```

这一条只适用于透明素材：透明度由 EvoLink API 参数负责，Prompt 不得写透明底、白底、灰底、
绿幕或棋盘格。完整不透明图走 Codex 原生生成，Prompt 反而必须明确写
`Scene/backdrop`、前中远景、满幅环境和场景如何响应主体；不得沿用 `isolated vignette`、
`no environment` 或 `empty canvas`。

### 4.1 先写正向拓扑，后写少量负向边界

“不要画假发”不如“七片相连的浅横向额前刘海、开放下缘、上方一条隐藏搭接片”；
“不要画管子”不如“平面渐缩服装面片、两端实心、沿上左到下右轴排列”。

有效的正向信息包括：

- `exactly one`、`one connected silhouette`；
- 可枚举的翼片、发束、色区和端点数量；
- 屏幕方向和轴线，而不是含糊的角色左右；
- 明确哪一端是隐藏安装根；
- 主体占画布的范围和每边留白；
- 关节处需要实体搭接，而不是空心袖口。

负向列表对“数量、范围和异物”有效，例如禁止第二只靴、人物全身、武器、文字、多视图、
sprite sheet。八轮记录显示，重复堆叠 `no glow / bloom / rim light / haze / fringe` 并不能
把 generations 路由变成 Alpha 清理器，反而会挤占真正的几何信息。

### 4.2 引用图必须声明角色

不要把几张图无说明地堆给模型。每张参考只能承担清楚的职责：

- 原设定图：服装、配色、饰物；
- 用户头像：脸、眼睛、眼镜、发质和气质；
- `0002`：身份/风格连续性，不负责分件 Alpha；
- 已批准 UI 普通态：同尺寸状态变体的 framing、姿势和剪影；
- 冻结后的权威战斗母版：三分之四视角、屏幕方向和战斗比例；当前 `0022` 只是已认可的
  视觉候选，必须先与 builder 实际 `0018` 消费源完成取舍，不能默认两者相同；
- `0015/0018` 一类完整姿势：宏观姿势、构图和身份连续性；
- `0025`：死亡姿势语义真值；
- 已通过附件：只能在确认其真实 Alpha 与用途一致后作为边缘/材质参考。

参考图能锁住宏观身份/姿势，并适合语义级的全局尺度、留白和构图修改；`0016`、`0019`、
`0029` 都证明了这一点。但“只删除外光、其余像素完全不变”通常不会得到像素编辑，
generations 路由仍会重新解释和重绘整张图。两次局部端面修复还曾把极低 Alpha 扩散到整张
画布。因此不能把图生图当作 Photoshop，也不能让失败图在重试链中无限自我继承。重试应
从最后一个**语义正确**候选分支，而不必继承最新轮；`0029` 放弃摆拍的 `0028`、重新引用
`0025` 是成功范例。

## 5. 参数如何选

| 素材类型 | 建议起点 | 理由 |
| --- | --- | --- |
| 完整不透明卡牌插画 | Codex 原生生成、横向约 `3:2`、高细节 | 卡图需要完整场景、身份、手势和牌义空间；生成后确定性中央裁成 `25:19` / `1000×760`，不进入透明链。 |
| 完整身份/战斗/动作姿势 | `2:3` 或自然长宽比、`2K/high` | 脸、手、服装与整体比例需要细节；完整层能容忍一致的整体照明。 |
| 水平侧卧/倒地完整姿势 | `3:2`、`2K/high` | 让身体长轴利用横向画布，并保留头、手、裙摆和两只鞋的安全边。 |
| 头像/选人按钮 | 与目标接近的比例、`1K/high` | 先保证缩到实际尺寸仍可识别，再做允许的等比尺寸适配。 |
| 徽记/刚性饰物 | 自然外形比例、`1K/high` | 明确拓扑时首轮成功率高；高质量有利于装饰细节。 |
| 独立大型法阵/VFX | `1:1`、`2K/high` | 径向几何、中心留空和内部层次需要分辨率；辉光作为独立层验收。 |
| 技术服装附件 | `1K/low` 或 `medium` | 降低产品渲染和细节增生，但不能据此保证 Alpha 干净。 |
| 模型内重绘 | 只在形状/身份值得保留时使用 | 它是语义重绘，不是精确缩放或像素清边。 |

`quality=high` 对眼睛、眼镜、蝶翼和完整服装有益，但会强化精品插画、宝石高光和产品
展示感；`quality=low` 常使技术附件更简单，也可能让身份、端点和宽度退化。不存在全局
最佳档位，应由素材语义决定。`0022` 的 `2K/low` 适合研究方向和剪影，同时损失手、眼镜
与服装细节，不能据此把 low 设为完整人物终稿默认。

画幅必须匹配物体自然轮廓。把细长腿件放入过窄竖画布、再要求很小画面占比，实际会把
它推成针杆；把短靴强塞进方图可能改变透视。主体缩小后绝对低 Alpha 数自然降低，不能
因此认定它更干净。

同一语义每次 `n=1`，上一轮验收后再构造下一轮。不同部件可以并行，同一部件的八次
尝试必须串行，保证每轮确实利用上一轮证据。

当前路由实测像素尺寸包括：1K 的 `1:1=1024×1024`、`3:4=880×1184`、
`2:3=832×1248`；2K 的 `1:1=2048×2048`、`2:3=1680×2512`、
`3:2=2512×1680`。不要假定声明比例必然严格等于数学分数；验收和 atlas 预算读取返回 PNG
的实际尺寸。

## 6. Alpha 的正确验收方法

### 6.1 不得直接相信透明 PNG 的预览外观

PNG 可以在 `Alpha=0` 的像素中保留任意 RGB。部分查看器会把这些 RGB 显示成黑、蓝、
紫或灰色大光场；它们在正常渲染中完全不可见。真实 SourceOver 为：

```text
display_rgb = source_rgb * alpha + background_rgb * (1 - alpha)
```

因此每张图至少要显式合成到：

1. 纯黑；
2. 纯白；
3. 接近它实际场景的蓝灰、绿灰或 UI 底色。

存在关节、叠层或邻接消费者的素材还必须合成到实际相邻附件的 setup pose 和最大旋转；
完整姿势、UI 与独立 VFX 则验真实场景底色、实际显示尺寸和真实前后景层，不虚构相邻人体件。

`view_image`、聊天缩略图、棋盘格预览、`Alpha>0` bbox 或低 Alpha 总数都只能提供线索，
不能单独下结论。

### 6.2 四层门禁

| 门禁 | 检查内容 | 不能替代什么 |
| --- | --- | --- |
| 文件门禁 | PNG 签名、RGBA、尺寸、四角 Alpha | 不证明肉眼无光晕。 |
| 单图视觉门禁 | 三种底色 SourceOver、身份、异物、裁切 | 不证明 atlas 紧凑或关节不叠亮。 |
| 技术边界门禁 | `A>0/16/64/127` bbox、远处稀疏 Alpha、实际尺寸 | 不证明多个附件组合自然。 |
| 集成门禁 | setup/极限姿势叠层、缩放、过滤、Vulkan 逐帧 | 不可由静态 PNG 代替。 |

普通一像素抗锯齿会产生低 Alpha；绝对数量还随主体周长和尺寸增长。比较时至少同时看：

- 低 Alpha / 非零 Alpha 比例；
- `A>0` 与 `A>127` bbox 每侧扩张距离；
- 是否存在远离实体核的像素岛；
- 三底合成是否肉眼可见；
- 两件重叠后是否累积成亮缝。

右大腿 `0083` 的主要连通 `A>0` bbox 相对 `A>=128` 实体核只扩约 2–3 px，三底均无可见
光场；右靴 `0064` 按同一阈值口径约扩 3–6 px，也没有可见宽光。旧记录仅凭低 Alpha 数
把它们判为“光晕失败”，
属于验收误判。远处极低 Alpha 即使肉眼不可见，仍可能放大自动 crop 或 atlas region，
这应记录为打包效率问题，而不是伪装成视觉光晕。

### 6.3 禁止的 Alpha 处理仍然不变

正确验收不等于允许程序修图。不得用阈值、色键、洪水填充、蒙版、Alpha 收缩或边缘
清理改变生成图。程序只可读取指标、做真实合成预览，以及在素材通过后进行不改变创意
内容的等比尺寸适配和确定性打包。

## 7. 成功样本告诉我们的事

### 7.1 身份母版

两张用户原图同时约束服装与脸时，银发、紫瞳、金框眼镜、蓝蝶和魔法少女气质能够稳定
保持。纯文字对照会把服装推向更成熟、更华丽的通用设计。结论是：身份资产必须保留干净
原始参考；文字用于约束，不负责重新发明身份。

### 7.2 五张 UI

头像、轮廓、地图标记和普通/锁定按钮多数在 1–2 次内完成，因为：

- 消费尺寸和构图契约明确；
- 对象完整，不存在关节切口；
- 每张图只承担一种状态语义；
- 生成后立即在 `85×85`、`49×64`、`132×195` 实际尺寸验收；
- 合格即停，没有为了“更漂亮”继续烧额度。

轮廓图第二次反而被画成中空光环，证明状态贴图也应单独验收，不能假设后续尝试一定优于
首轮。普通态和锁定态分别生成，避免程序灰化破坏项目血缘规则。

更具体地说：头像 `0006` 受益于 `1:1`、85×85 实际可读性和圆形安全区；地图标记 `0009`
受益于 `3:4`、49×64 目标和可枚举的蝶翼 + 晶体 + 短 V 拓扑；锁定态 `0012` 把已批准
普通态只用作 framing / pose / silhouette 参考，并明确允许的亮度、饱和度和色域，首轮就能
保持构图。相反，`0008` 要模型把实心轮廓“整体外扩 8%”，结果变成中空环，说明形态学
膨胀、描边外扩百分比和像素同构不适合交给 generations。

历史上 `0010 → 0011` 同时改变了参考图数量、构图、正三分之四程度、留白和边界描述，
不能把成功归因于某一句 `no haze`。它只能提供相关性；新轮次仍要坚持一次只验证一个主要
假设。

### 7.3 选人英雄与独立法阵

`0013` 明写 `three-quarter-length ... through upper thighs`，模型正确裁到大腿；它不是
“模型忘了画腿”，而是 Prompt 给了错误构图。`0014` 改成 `exactly one continuous
full-body`，逐项要求最高发梢/蝶饰、十指和两只完整鞋底，并给约 12% 留白后才得到完整身体。
需要全身 rig 源时禁止使用含义为半身构图的 `three-quarter-length`。

`0015` 用已批准 UI 肖像强化图形风格并稳定姿势，`0016` 能保留宏观姿势和调整构图，但
没有把完整人物柔光变成分件硬边。最终选择 `0016` 的原因是它作为**单一完整 attachment**
可以容忍连续整身柔光，不代表它通过拆件 Alpha。

`0017` 无参考、`1:1/2K/high` 首轮成功：中心留空、径向对称、限定蓝紫金几何和让所有
发光远离边界，比简单写“魔法阵”更有效。人物层的 no-glow 规则不能复制给 VFX；独立 VFX
应正向写 `bounded inner luminescence`，并在真实前后景与边界上单独验收。

水平战斗魔法弧 `0023` 使用 `16:9/2K/high`，把运动拓扑写成“左侧紧凑起点 → 宽阔中段 →
右侧渐尖闪光端”，限定明亮内核、紫/靛色带和受控青金细节，并要求所有 glow pixel 远离
四边。法阵与魔法弧共同证明：特效 Prompt 也要写可枚举的空间结构和能量流向，不能只堆
`beautiful / magical / glow`。

### 7.4 蓝蝶

`0030` 首轮在造型上成功，关键不是负面词多，而是单一权威参考、可枚举拓扑、清楚的
安装根和方向、一个连续对象，以及与蝶翼自然外形匹配的方形画布。真实 Alpha 三底合成
也没有此前直显所误报的宽光晕。

后续专属消费者把静态结论升级为离线动态结论：`0030` 源图与候选页逐字节一致，四边非零
Alpha 为 0，推荐 pivot `(176,650)` 位于 `A=253` 的实心连接片内。真实相邻 `0031` 后发、
`0044` 头脸和 `0033` 前发的 A/B 层序证明，蓝蝶若置于所有头发最前会暴露过长的深蓝金边
连接片；正确 draw order 是 `后发 → 头脸 → 蓝蝶 → 前发`，用前发遮住连接片而保留完整双翼。
16/16 Windows Vulkan 极值帧通过，`die@1.05s` 同步解绑，商店 `relaxed_loop` 随机 seek 也
保持唯一实例。由此 `0030` 可作为单个刚性 region，不需要把蝶翼和连接片再拆开；它仍须进入
统一全身骨架后复测，不能把隔离头部灰盒冒充正式 runtime。证据在
`assets/vivhite-ironclad/evaluation/semantic-butterfly/`。

这套经验可推广到徽记和刚性饰物，不能直接推广到脸、膝、踝或裙片：蓝蝶不需要连续的
人体解剖、端面和大角度关节遮挡。

`0031` 后发则展示了“视觉 Alpha”和“打包 Alpha”必须分开：其 `A>0` bbox 相对实体核最远
向下扩 121 px，但 `A>=16` 只扩约 0–1 px；实体核 16 px 以外的 525 个 `A=1` 级像素在
三底合成中最大只改变 1 个 8-bit 色阶，没有可见光幕。它静态 Alpha 可用，但若 packer
按任意非零 Alpha 自动裁切会浪费 atlas，所以仍需打包门禁，不能反向把它写成美术失败。

`0031` 随后进入一个 `7×7` weighted mesh：49 顶点、72 三角形，冠顶固定在 head/root，只有
下半部左中右发尾获得受控权重且末梢总权重不超过 `.72`。真实 Windows Vulkan 在八动画各
21 帧共 168 帧中全部非空、无触边并有变化；`relaxed_loop` 11 个唯一帧且首尾 hash 相同，
覆盖商店随机相位，实际尺寸未见冠顶脱离、双头、颈穿透或明显三角折线。因此它可保持“一张
weighted 后发帽体”，不拆成多根付费发束，也不继续生成。证据在
`assets/vivhite-ironclad/evaluation/semantic-back-hair/`。

该后发候选早于蓝蝶专项，接触表采用了 `前发 → 蓝蝶` 的旧邻接顺序；这只影响邻居层序，不
推翻后发权重结论。总装必须使用蓝蝶 A/B 已证明的 `头脸 → 蓝蝶 → 前发`，并在死亡阶段另行
验证，因为后发专项在 `die@0` 就卸载正常头部，没有冒充倒地发丝通过。

### 7.5 战斗母版和死亡姿势

完整人物让模型处理它熟悉的人体、服装和重力关系，身份一致性明显好于零散人体残段。
整体柔光只存在于一个 attachment 时不会形成关节叠亮。

战斗链并非单调“越新越好”：`0018` 用完整姿势参考 + 原设定 + 头像，首轮就得到高细节、
空手、朝右战斗姿势，并成为 builder 当前实际源；`0019` 的“只清外光”没有证明像素边缘
改善；`0020` 去掉姿势参考、只留正面原图后回正并重新带出粉色长饰；`0021` 用短 Prompt
强化真三分之四后方向恢复；`0022` 用 `2K/low` 简化并强化剪影，同时让手和身份细节退化。
screen-right 文字应覆盖鼻、胸、髋、膝、趾和前掌方向，但方向关键时仍须提供已验姿势图；
正面设定只负责身份，不能负责战斗镜头。

侧卧死亡的自然闭眼、空手、重力正确姿势在首轮 `0025` 就已形成。`0026/0027` 没有 PNG，
现存 task 只有 task id，不能臆测失败原因；`0028` 为规避问题把正向叙事改成
floor-exercise/resting，模型即使收到“不用手支撑”的否定词，仍画成托头摆拍。`0029`
没有继承最新失败轮，而是明确回溯 `0025`，把整身缩至约 72% 宽、55% 高以内并增加留白。
这是“第一轮拿到语义真值，第五轮从正确分支做尺度/留白精修”，不是第五轮才得到姿势。

独立 slot、原子切换、落地和回弹证明了完整死亡图是正确素材类型，不必再把站姿网格硬卷
成尸体。旧 V2 消费者在切换前后仍有约 61 px 横跳，用户也明确认为死亡观感怪；当时因此
只能写成“死亡美术源通过、动态方案待修”，不能冒充最终解决。正向场景语义通常压过否定
词；不能为了绕过一次无返回而把 `death/collapse` 改成与动作本质冲突的
`resting/floor exercise`。

V3 没有重画 `0029`，而是保持其原生 RGBA 和冻结哈希，先把 neutral 压低、收缩为接近侧卧
轮廓，再于 `1.05s` 原子切换独立死亡 slot。真实 Windows Vulkan 16 帧复验把实体左边界跳变
从旧 `61 px` 降到 `16 px`，实体底边只跳 `1 px`，落地底边序列为
`684, 686, 680, 684, 684 px`；每帧恰好一个人物，且无空帧、双影、触边或 VFX 残留。这次
纠正说明：当“美术语义正确、动态切换不顺”时，应先调前序轮廓、锚点、切换时刻与落地回弹，
不要把可用美术误判为必须再次付费生成。`0029` 因此升级为“独立死亡消费者离线 Vulkan
通过”，仍未等同于正式 runtime 或用户真机审美通过。证据保存在
`assets/vivhite-ironclad/evaluation/v3-death/`。

成功点并不意味着完整人物天然容易：仍需严格控制视角、手脚完整、空手、画布留白、人物
尺度和身份；但它把模型擅长的问题与 Spine 擅长的问题分开了。

### 7.6 篝火完整坐姿

`0024` 让模型画一个低位、三分之四朝右、重心可解释的完整坐姿，同时逐项要求头、躯干、
双臂、双手、骨盆、双腿、双靴和裙边可读，并排除椅子、石头、篝火和场景。它适合作为
rest-site 私有网格的完整美术源，因为模型理解“一个人如何坐稳”远好于理解一组脱离身体的
坐姿残段。Prompt 中写“for a deformable skeletal mesh”只描述用途，不会自动创造遮挡后的
隐藏像素；大角度局部变形仍须由网格、权重和 Vulkan 验收负责。

## 8. 失败与误判样本告诉我们的事

### 8.1 前发和头脸

- `front hair`、`Live2D layer` 仍可能被理解成完整假发；正向写出浅横向比例、发束数量、
  开放下缘和隐藏搭接条才会收敛拓扑。
- 用户头像能保持紫瞳、眼镜和表情；无参考会退化成通用动漫脸。
- “沿现有轮廓删除外部像素且其他不变”会触发整图重绘，不能当作清边命令。
- 脸、眼镜、前发可以在新方案中合并为完整头部姿势层，避免最敏感的脸发叠缝。

`0033` 是一次重要纠错：八张前发在真实三底 SourceOver 下都没有旧记录所称的宽幅光晕；
按 `后发 → 0044 头脸 → 0033 前发` 做过的实测合成中，`0033` 的发束缺口、头顶覆盖、眼睛和眼镜
几乎天然对齐，静态效果优于旧结论选出的硬矢量假发 `0038`。它尚未成为动态生产件，原因
不是 Alpha，而是当前临时候选只有组合 slot；一张连通前发若刚性绑头骨，不能消费已有
`hair_left/right` 摆动，若做多骨权重又要验证中央刘海不被拉裂。

头脸 `0040–0047` 也全部撤销旧光晕判定。`0045` 是当前综合最佳：身份、三分之四方向、
完整头壳和颈根稳定，实体约 `585×756`，三底干净且相对打包浪费较小；`0040` 留作高分辨率
身份母版，`0044` 是保守备选。它仍未进入独立 head slot；接入时必须按
`后发 → 头脸/颈根 → 前发 → 蝶饰` 排序，重算跟随 head 的双眼 VFX 锚点，并在 hurt、cast、
死亡头部/发骨极值及共用骨架的商店 `relaxed_loop` 验证。注意，完整三层合成实测使用的是
`0044`；`0045` 目前只是单图综合最佳，尚未完成同口径后发/前发组合，不能把两项证据合并。

### 8.2 躯干

- 单一稳定战斗参考能保持三分之四方向和服装结构；只用正面设定图容易补出裙片并回正。
- `torso + pale skin + no head/limbs` 一类残缺人体语义可能触发内容过滤。
- 复杂百分比搭接、空肩口和人台式描述会互相牵制；模型并不理解 Spine 工程数字。
- 高质量、晶体、金属和华丽词会增加立体高光；技术附件应使用更短的正向服装模块描述。

真实复核后，`0054` 的 Alpha 应判通过：`A=2–127` 全部在实体核约 6 px 内，三底没有宽
光幕；远处只有稀疏 `A=1` 点，属于 trim 风险。它仍只能是“条件静态美术候选”，因为胸廓
和肩口比 `0018/0022` 膨大、左肩饰和两个袖口已烘入图中，会与左臂在后、右臂在前的 slot
层序冲突；腰插片随 `torso_upper` 而裙随 pelvis / skirt，重击躯干大角度旋转还可能露缝。
下一步应先冻结母版和肩腰锚点并做组合 rig，不应为不存在的 Alpha 问题继续生成。

### 8.3 靴和腿段

- 鞋尖、鞋跟和安装片方向写清后模型服从度很高；所以规格写反尤其危险。
- `anatomical thigh/cylinder/joint opening` 容易得到空心管、补全小腿或人体残段。
- 为绕开过滤而使用 `capsule/diagram/test strip`，又会把腿画成笔、温度计或胶囊。
- `flat tapered garment panel`、直轴、实心端和沿轴排列的色区更容易得到可绑定几何。
- 反复缩小会把腿推成针杆；绝对低 Alpha 下降只是尺寸效应。
- 若踝部独立生成持续不稳，应把“小腿+靴”定义成一个连续附件，把关节上移到膝部。

右大腿 `0083` 已经证明独立腿件并非天然不可行：方向、分区、端点和真实 Alpha 均可达到
静态素材标准。下一道门槛是和裙摆、右小腿的实际叠层及 Vulkan 动画，而不是继续生成。

左大腿的最佳也应从“绝对低 Alpha 更少”的 `0079` 改为轮廓和分辨率更合理的 `0078`。
`0078` 三底干净、两端实心、轴向正确，正常边缘只扩约 4 px；`0079` 只是把主体缩成针杆。
这一组同时证明不能反向走到“所有光晕都是误判”：`0074`、`0077` 的确存在全画布非零
Alpha 污染，且边缘数量 4156、最大边缘 Alpha 分别达到 83 / 23。正确方法既不能凭直显
冤枉干净图，也不能因为发现查看器问题就放弃像素和三底门禁。

左小腿 `0088` 也在真实三底合成后由“八轮 Alpha 失败”纠正为静态候选：可见边缘只比
实体核扩约 0–3 px，轴线约偏左 `2.59°`，几乎匹配 builder 现有 `2.76°`。它真正剩下的
问题是上下端盖线、偏细比例、slot 顺序无法按原假设由大腿盖住上端，以及尚未在极限膝踝
旋转下集成。此案例说明第一次结果可能已经解决模型问题；错误的验收与错误的消费者假设
会让后七次全部成为无效优化。

右小腿 `0096–0103` 也全部无可见宽光晕，综合最佳不是旧记录的 `0103`，而是白袜身份、
比例和轴向更平衡的 `0100`。`0101` 角度最贴硬编码骨轴，却像通用垫片。更深的问题仍是
真值冲突：builder 骨轴约 `57.68°`，其实际 `0018` 母版实体约 `68.2°`，`0022` 又约
`74.2°`。精确角度 Prompt 只有在骨轴先校正后才有意义；否则“模型差 3.8°”可能反而比
严格服从错误 rig 更接近人物图。现有顺序又是 right thigh → right lower → right foot，
没有 drawOrder 动画；小腿会压住大腿，`0100` 上端深色轮廓可能形成膝部横缝，必须与
`0083` 做 setup 和极限转角叠层。

左靴 `0056–0063` 的旧“整圈光晕”判断也全部撤销；真实三底均为紧边。最佳从按低 Alpha
绝对数选出的 `0059` 改为几何更匹配的 `0063`：其实体宽高比约 `0.866`，与 builder 脚部
UV 的 `340/390≈0.872` 只差约 0.6%。更重要的教训是层序：当前 foot slot 在 lower-leg
之后，靴口会盖住白袜，Prompt 反复要求“让插片藏在小腿下”与源码相反。Prompt 必须说明
靴口是前景覆盖件；若真的需要隐藏 connector，就要先把 connector 与靴身拆成前后两个
slot，不能让模型替错误 draw order 擦屁股。

比例匹配也不等于 pivot 已匹配：左靴 attachment 原点位于 foot `(485,1940)`，真正随父骨
旋转的踝点却是 `(485,1840)`；在旧 UV rect 内约为 `(42.65%,33.33%)` 与
`(42.65%,7.69%)` 两个不同点。下一版规格卡必须同时写安装原点和实际旋转枢轴。

右靴 `0064–0071` 八张的真实 Alpha 均无宽光晕，但没有一张满足已选择的 `0022` / 新 rig
鞋尖朝右目标；`0064` 只能作为平涂风格和边缘参考。它们尚不能与右小腿做端到端联调。

当前 normal slot 固定顺序为左腿 thigh/lower/foot=`1/3/5`，右腿=`7/9/11`，没有
drawOrder 动画；所有新生成腿靴图都尚未进入 atlas 或 slot，split candidate 仍读取
`0018` 整身 UV。静态候选的真正下一步是组合 rig，不是直接发布或继续追 Alpha 数字。

### 8.4 手臂语义组必须先冻结遮挡职责

屏幕左侧旧名 `arm_left_*` 经整身母版、非对称肩饰、UV 与 draw order 联合核对，实际表示
角色远侧、解剖右臂。该方向不能只靠“角色左/右”文字猜测；付费前规格卡必须同时写屏幕侧、
远近侧和解剖侧，并附实际消费者证据。

远侧手臂灰盒证明默认两件制足够：`far_upper_arm + far_forearm_hand`，腕只保留测量锚点，
不为了“骨骼更多”预先制造腕缝。后到前层序必须是上臂、前臂手、躯干肩盖；蓝金肩饰归
躯干肩盖，手臂美术只需提供藏在肩盖下的实体搭接。该远手不承载 `slash_mesh`，普攻魔法弧
归屏幕右侧近手，眼火归头部。八动画共 40 帧 Vulkan 灰盒在 `.28` 下通过，包含
`cast(-35°,-48°)` 与 `die(+71°,+55°)` 极值，但仓库尚无可发布的独立远臂美术。

这给下一轮 Prompt 的约束顺序是：先锁躯干肩盖轮廓和肩/肘 pivot，再生成连续的上臂与
前臂空手；不要让模型重复肩饰，也不要预切腕。只有真实美术在 cast/death 相邻叠层中证明
腕部确实需要旧范围约 `-20°..+31°` 的独立旋转时，才升级第三件。灰盒证据保存在
`assets/vivhite-ironclad/evaluation/semantic-left-arm/`，不能作为发布美术或 AI 参考。

### 8.5 常见错误假设

| 错误假设 | 实测结论 |
| --- | --- |
| 低 Alpha 多就是可见光晕 | 错。先做真实 SourceOver，再看边界扩张和叠层。 |
| `background=transparent` 会清空透明像素 RGB | 错。透明 RGB 可以保留，但正常渲染不可见。 |
| generations 可以精确修一圈 Alpha | 错。它会重新解释并重绘。 |
| 否定词越多越干净 | 没有证据；会挤占几何信息。 |
| 主体越小越干净 | 只会降低绝对像素数，还可能损失分辨率和比例。 |
| high 一定优于 low | 取决于用途；high 会增加展示质感，low 会损失身份。 |
| 角色左/右等于屏幕左/右 | 错。必须用实际母版、骨骼和源码核对。 |
| 静态 PNG 通过等于可发布 | 错。还需关节、atlas、Vulkan 和真机集成。 |

## 9. 八次额度应如何使用

八次是风险上限，不是同一 Prompt 的八次抽奖。

1. 第一次：消费契约 + 干净权威参考 + 最短完整 Prompt。
2. 返回后立刻做格式、三底合成、几何、身份、实际尺寸和异物检查。
3. 先给失败分类：规格、Prompt、模型、验收或集成。
4. 每轮只验证一个主要假设，例如方向、画幅、参考角色或语义粒度。
5. 图形正确但身份弱，才增加身份参考；方向错误先修规格，不要润色。
6. 只有轮廓值得保留时才图生图；不得要求它做像素级 Alpha 清理。
7. 连续三四轮出现同一结构失败，应改变语义粒度，例如靴改成小腿+靴、脸发合并。
8. 第八次仍不合格，保留所有记录、最佳候选和剩余缺陷，停止并交用户统一评审。

同一组件不得并行发出多次付费请求。不同组件可以一组件一子代理并行，但主代理必须先
分配互不冲突的编号与输出目录，并统一做消费契约和跨组件一致性验收。

## 10. 面向新战斗方案的 Prompt 策略

新的优先方向是“完整关键姿势 Hybrid”，而不是让模型生成 21 个微型人体残段。每个动作
关键姿势应从同一身份和战斗母版起链：

```text
Use case: identity-preserve production-pose
Asset type: one complete single-frame 2D Spine action-pose attachment

Input images:
Image 1 defines the accepted combat identity, camera, scale and costume.
Image 2 defines the authoritative face and glasses.
Image 3 defines only the requested action silhouette.

Primary request:
Redraw exactly the same original magical girl as one complete figure in <cast/attack/heavy/hurt>
peak pose. Preserve identity, costume, camera and body scale. Empty hands; magic only.

Pose geometry:
<头、骨盆、双脚、双手的屏幕方向和动作受力；注明哪个锚点必须与母版对齐>

Composition:
Same canvas family, same camera distance, exactly one continuous full body, measured safety margins.
The highest hair tip and butterfly, all ten fingers, and both complete boot soles are visible and uncropped.

Constraints:
One figure and one pose; no weapon, prop, duplicate, pose sheet, panel, text or scenery.
Do not use a three-quarter-length or upper-thigh crop.
```

不要要求模型同时输出多帧、spritesheet 或 atlas。每个关键姿势单独生成、归档和验收；
Spine 负责动作前摇、位移、回弹、VFX 和在遮挡最强时刻的 attachment 切换。

### 10.1 `attack_peak` 首个闭环的实证

`0104` 和 `0105` 是这套新策略的前两次实战。两次都使用 `2:3 / 2K / high / n=1`，引用
`0018` 战斗母版、原始人物设定图和头像身份图，并要求同一 `1680×2512` 画布族、空手掌击、
一个人物和一个姿势。两次付费结果的原 PNG、逐字 Prompt、脱敏 request 与 task 均已归档。

最终选择 `0104`，停止继续消耗剩余六次额度；`0105` 只作为历史备选保留。选择依据不是
原 PNG 在黑底查看器中的主观大小，而是冻结消费者后的证据：

- neutral 与 action 都保留模型返回的完整 `1680×2512` 画布，经过同一个固定变换进入
  `1536×2272` region 和 `868×1302` authored world；不得按每张图自己的 `A>0` bbox
  单独缩放、居中或“填满” atlas，否则每个动作的人物像素密度都会漂移；
- 原图黑底直显会夸大外围低 Alpha、动作横向展开和魔法刀光造成的宽度；只有把人物层和
  VFX 层分别在实际 `.28` 场景比例下渲染，才能判断人物是否真的过大；
- `0104` 的独立人物层在 `.0799 → .08` 原子切换时，脚底只变化 `+4 px`，人物 bbox 从
  `215×343` 变为 `232×347`；这属于动作展开，不是整身缩放回归；
- 角色图本身不包含刀光。掌心与原 neutral VFX 锚点的差异由 Spine pose-specific anchor
  修正，而不是要求模型把特效烘进人物：实测在 `.28` 下约为屏幕右移 `59 px`、上移 `8 px`，
  对应 authored offset 约 `(210, 30)`；
- 使用真实 Spine GDExtension、Windows Vulkan 和运行时 `0.1s` mix 逐点采样 14 帧，人物层
  与完整 composite 都非空、无裁切，`.08/.20` 同帧始终只有一个人物 attachment。

这次还纠正了一个验收顺序错误：先看原始大图、再凭肉眼决定“过大/光晕太宽”，会把动作
轮廓与 VFX 误算成人物尺寸。正确顺序是先锁消费者的整画布变换，再分别渲染 character-only
和 composite，最后才决定是否重生成。`0104` 当时的状态是“隔离候选离线 Vulkan 通过”；
2026-08-29 已随正式五页 runtime 部署，并由实际普攻消费通过，详见 10.5。

### 10.2 `attack_heavy_peak` 第一次生成与正式消费者结论

`0106-combat-attack-heavy-peak-attempt-01` 使用 `0018 + 0104 + 人物设定 + 头像` 四张职责

黑底原图仍显得人物铺满画布、外围辉光很宽；这不能直接推翻它。把 `0106` 通过与 `0104`

右移 `17.27 px`、上移 `8.19 px`，在强 VFX 遮挡下可接受，但仍保留为用户真机审美门禁。

因此 `0106` 已升级为“隔离候选离线集成通过”，并停止在 1/8 次；不为用满额度生成第 2 张。

### 10.3 `cast_peak` 第一次生成与直显误判纠正

`0107-combat-cast-peak-attempt-01` 使用战斗母版、原始人物设定和头像三张职责分离的引用，
返回一个高 screen-right 掌、低 screen-left 掌形成对角线的完整空手施法姿势。人物身份、

原 PNG 在普通直显中像有很宽的蓝紫光场；真实指标推翻了这一肉眼初判：四角 Alpha 全 0，

固定消费者下，cast 实体约 `206×349 px`，neutral 约 `209×351 px`，宽高只差约

### 10.4 拆件批次收口后的 Prompt 结论

拆件线的最新动态消费者证明：多数失败并非“透明不够干净”，而是生成语义粒度与实际骨骼
消费职责不匹配。当前冻结结论如下：

- 头脸优先 `0045` weighted consumer，`0045` rigid 为回退、`0044` 保留历史；三候选共
  `120/120` Vulkan 帧通过，但头脸、前发和双大腿仍是 research-only，不是生产附件；
- 远臂与近臂都只拆“上臂袖 + 前臂手”，腕只作测量点；远臂 40/40、近臂 9/9 灰盒通过，
  但没有可发布的独立手臂美术；
- 双腿都收敛为“大腿 + 小腿靴一体”，保留膝、锁定踝；`0078/0083/0100` 只可作研究参考，
  旧右腿 `0064–0071` 的鞋尖方向错误；
- 躯干必须是 `torso_core + 四个独立裙片 + 远肩饰前/后片`；`0054` 的 Alpha 不是问题，
  真正阻塞是烘入袖、肩饰、腰裙和比例冲突。躯干语义组 `0048–0055` 已用满 8/8，未经用户
  针对该语义追加额度，不得通过改名规避上限；
- 总装 A/B 灰盒 336/336 帧通过，但 `deployable=false`、`production_runtime_ready_slots=[]`。
  仍完全缺少 13 个 EvoLink 生产附件：`torso_core`、四裙片、远肩饰前/后、远/近上臂袖、
  远/近前臂手、远/近小腿靴一体。这里的“缺 13 个”不代表其他研究件已经生产通过。

右小腿 `0096–0103` 八轮原图、Prompt 与脱敏参数已完整归档；不合格结果继续保留，但不会被
程序拼接、Alpha 修补或冒充最终素材。五页 Hybrid 总装与完整隔离 PCK 已经完成并应冻结；
后续先完成明确授权后的真机门禁，再决定是否值得申请新的拆件生成额度。

### 10.6 白绮卡图的类型视觉语法

卡图是满幅不透明场景插画，不是透明人物与魔法 vignette。背景必须有前景、中景、远景和
空间透视，并参与牌义：攻击场景沿出射方向响应，防御场景在闭合边界外承受冲击，能力场景
围绕人物竖向升华。详细生产契约以
[《白绮卡牌图片生成技术规范》](白绮卡牌图片生成技术规范.md) 为准。

卡图必须在隐藏卡名、规则文字和类型边框后仍能区分用途，不能只靠红／绿边框或色相暗示。
初始牌先冻结三种基础构图语法，后续同类卡可以变化主题，但不得颠倒底层轮廓：

| 类型 | 主轮廓 | 动势与姿势 | 禁止混淆 |
| --- | --- | --- | --- |
| 攻击 | 开放三角、箭头、斜线和锐角投影 | 人物偏施法起点，动作不对称；魔力沿明确方向向敌方射出，但完整收在卡图安全区内 | 主视觉不得变成包围人物的闭合球壳；不得只靠红色表示攻击 |
| 防御技能 | 闭合圆、球壳、穹顶和连续边界 | 人物稳定居中，双手向内维持护域；外来冲击在边界外停止或偏转 | 不得出现穿出护域、指向敌方的主光束；碎片只能服务“受击被挡” |
| 自身能力 | 竖轴、星冠、同心轨道和向上展开 | 人物是变化中心，姿势相对对称；轨道围绕核心升华，不指向敌方 | 不得形成完整防御球壳，也不得出现明确命中敌人的射线 |

颜色只是第二层辅助：攻击使用高对比白蓝光核与紫色锐边；防御使用靛蓝／青蓝主体和金色
闭合边界；能力使用白金／紫色升华轨道。三类都遵守口部硬禁令，并禁止借红色、猩红色或
血色偷懒表达攻击与“謦欬”。

首轮三张基础牌的固定读法为：

- `弦光投影`：左到右的开放斜向投射，锐角几何明确指向敌方；
- `闭域映射`：双手维持居中的闭合几何护域，冲击在外侧终止；
- `白绮的变身式`：正中竖向星核与多层升华轨道，不存在敌方命中方向。

验收必须同时看原色、灰度和小尺寸：将 `1000×760` 运行时裁切放入真实卡框，并额外检查
约 `250×190` 与 `100×76` 缩略图。即使去色和轻度模糊，攻击仍应读成“向外射出”，防御
仍应读成“闭合包围”，能力仍应读成“自身升华”。若只能凭颜色、卡名或类型文字判断，或
防御出现主出射光束、攻击变成闭合护球，均判定失败。

## 11. 每次调用前后的最小清单

付费前：

- [ ] 已判断单图、单帧、spritesheet、atlas page / region；
- [ ] 已读取消费者源码、场景、Spine slot/bone/event，而不只看原图；
- [ ] 已确认视觉参考和 builder 实际输入的路径、哈希与姿势是否相同；
- [ ] 已把屏幕方向、pivot、遮挡层、自然长宽比和实际尺寸写入规格卡；
- [ ] 每张引用图只有一个明确职责，且血缘干净、用途已验真；
- [ ] 已按最终消费者选择生成链：不透明完整图用 Codex 原生生成；明确透明素材才用 EvoLink；
- [ ] 透明素材 Prompt 不含背景词；完整场景 Prompt 明确前中远景、满幅环境和空间响应；
- [ ] Prompt 只要求一个成品、对象或姿势，不包含 pose sheet 或 atlas；
- [ ] Prompt 明确禁止嘴边红线、口部血丝、红色液体及任何从口中延伸的魔力，不用口部元素表现“謦欬”；
- [ ] 若且仅若目标明确需要透明，request 使用 EvoLink `gpt-image-2`、`background=transparent`、`n=1`；
- [ ] 若目标为完整不透明图，使用 Codex 原生生成并写入独立追加式归档，不调用 EvoLink；
- [ ] 任一路线的输出目录都不覆盖旧轮次。

返回后：

- [ ] EvoLink 透明图已保存原 PNG、逐字 Prompt、脱敏 request 与 task；Codex 原生图已保存原图、逐字 Prompt 与可验证 generation 记录；
- [ ] Codex 原生图只记录可验证的生成事实，不臆造内部模型、seed、token 或隐藏请求参数；
- [ ] 文件格式、尺寸、主体、身份、方向、异物和实际显示尺寸已检查；
- [ ] 透明素材已真实 SourceOver 到黑、白和实际场景底；不透明完整图已检查满幅场景，并按消费者输出无 Alpha 的 RGB8；
- [ ] 透明素材已区分可见光幕、正常抗锯齿、远端 `A=1` trim 风险和真实全画布污染；
- [ ] 存在关节或叠层的透明素材已在 setup / 最大旋转检查 pivot、draw order、搭接和 VFX 锚点；
- [ ] 完整卡图已检查确定性裁切、灰度缩略图、真实卡框和场景背景；
- [ ] 状态明确写成失败、静态候选、动态通过或生产通过；
- [ ] 下一次只验证一个主要假设；若本轮已达用途则立即停止烧额度。
