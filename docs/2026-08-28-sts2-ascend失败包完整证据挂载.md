# sts2-ascend 失败包完整证据挂载

## 问题

失败批次重投时，宿主过去只把 target 与 attempts 的部分 manifest、report、inventory 和 patch 摘要压进 256 KiB prompt。实际 808–812 lineage 中，后续 attempt 的有效 `policy.py` 候选补丁被截成约 11 KiB 的头尾；隔离 clone 内又没有可供 GLM 深读的失败包文件。GLM 因而把“宿主没有提供完整证据”误判为“没有有效代码可补”，写出 `no_valid_change`。

这不是模型态度问题，而是证据输入机制缺口。原始失败包仍是取证真相，宿主不得自动应用其中 patch，也不得因为模型在残缺输入上给出空结论而删除它。

## 修复

- 每次失败包重审，在无 remote、无 hardlink 的隔离 clone 内建立固定相对目录 `sts2-ascend/.review_evidence/failed_review/`。
- target 和全部 queue lineage attempts 都进入同一 `index.json`。逐包提供完整 manifest、report、file states、retry inventory、全部根级 patch、模型输出，以及 `files/` 快照。
- 对 raw sandbox 不复制整仓；严格按 retry inventory 导出每个 changed path 的原始工作树文件，删除项在 index 中显式记录。原始 raw sandbox 继续完整留在失败包中。这避免每次重审复制数 GB，也没有重新引入全仓指纹。
- index 对每个实际挂载文件记录相对路径、字节数与 SHA-256；完整性范围仅是失败包证据，不扫描真实仓、refs、工作树或在线状态。
- 文件挂载后设为只读。模型退出后，宿主用内存中的预期 index 再验大小与 SHA-256，并在 Git inventory/selfcheck/patch 导出之前精确移除证据目录，确保取证文件永远不会进入模型提交。
- 任一 package、必需文件、inventory 或退出后哈希不可用时，宿主不采纳任何 `retry_resolution`；尤其不能采纳 `no_valid_change`。target 原包不删除、队列不消费并继续重试。若证据在模型启动前就不完整，不创建一个没有模型成果的巨大空 attempt。

## 同批修复的热重载缺口

TTS owner 的代码 epoch 明确由 `tts/quipper.py`、`tts/indextts_gpu.py`、`tts/owner_epoch.py` 决定。过去复盘只改这三处时虽会提交，却不会生成 Brain restart marker，运行中的 owner 无法通过新 Brain 完成交接。现在仅把这三个已证明的 owner 路径加入热重载集合；其他 TTS/脚本路径不扩大。

## 验证与注意事项

- 完整标记还必须由 materializer schema 闭环证明：`retry_evidence_ready=true`，manifest 精确声明 canonical candidate/inventory，候选大小一致，inventory 的 package/pre_head/schema 与 manifest 一致。只有 `wip.patch` 时一律视为不完整。
- target manifest 声明的 `replay_attempt_packages` 与本轮调用 attempts 做双向集合核对，任一侧漏包都在付费模型启动前失败并交回队列自愈，不能用不完整 lineage 关闭 target。
- 证据 preflight 失败且模型从未启动时，不运行 WIP capture；该 clone 直接清理，不遗留没有模型成果的 snapshot。
- 回归覆盖完整 target+attempt 大 patch、二进制 changed file、已有 snapshot、逐文件 hash，以及挂载后精确移除。
- 缺少 report 时确认付费模型命令不会启动，原包仍存在。
- 模拟模型改写挂载 patch 后，确认哈希失败且 `no_valid_change` 回执被忽略。
- 确认三条 TTS owner 路径触发热重载，而普通 `Start-Agent.ps1` 仍不会误触发。
- 修改 `llm_review.py` 后运行 Brain selfcheck；生产 Brain 不在本次开发/测试中手工重启，运行版本仍按既有局间事务安全加载。

## 旧宿主误闭环后的 hold 恢复

运维保存在 `knowledge/code_backups/review_hold/` 的失败包现在也是 Brain 的持久恢复来源。worker 启动及每 60 秒维护时会先核对 target 与其声明的全部 attempt；只有整条 lineage 都存在，才逐包恢复到 `review_salvage/`、撤销缺少完整挂载证据 schema 的旧回执，并按原模型重新登记 GLM 重审队列。任一声明 attempt 缺失时整组保持 hold，不会静默缩短证据链。

恢复只复制并重新排队，不应用历史 patch，也不删除 hold 原件。后续必须由 GLM 读取完整挂载证据重新给出结论；在代码提交、远端确认和拒合清单闭环全部完成前，hold 仍是独立保全副本。远端确认后的精确 hold 清理继续作为独立增量实现，避免恢复机制与删除机制挤在同一个提交中。

恢复组可能在普通 pending 已积压后才完成大文件复制，因此“追加到队尾”不能等同于“普通批之后执行”。batch 选择器现在先扫描可运行的 `retry_group`，让失败包闭环债优先；若该组仍在 `retry_after` 或绑定模型 cooldown 中，则继续跳过整组并运行普通批，不让不可运行的重投堵住复盘链。
