# Brain 遗物统计稳定 ID 与编码边界修复

## 现象与调查范围

白绮 profile 的遗物统计在终端中曾显示成形如 `�Բ������` 的乱码。本次复核原始
UTF-8 字节与 Unicode code point 后确认，当前文件里的对应键实际是合法中文
`吃不完的糖`，乱码来自终端代码页显示，并不是 `stats.json` 已写入 U+FFFD。
不过调查同时确认了一个真实的统计身份问题：奖励的本地化 `description` 会被当作
遗物主键，同一遗物在不同语言或异常显示文本下无法稳定合并。本次只追踪本机真实的
`STS2-Agent API → Python → stats.json` 链路，没有手工改写历史统计。

调查时读取到的当前 `sts2-ascend/knowledge/profiles/vivhite/stats.json` 是合法 UTF-8，当前聚合键为 `吃不完的糖`、`GREMLIN_HORN`、`永恒羽毛` 等，文件和现存重置归档中没有检出 UTF-8 字节序列 `EF BF BD`。因此本轮不执行历史 U+FFFD 清洗；回归测试保留损坏显示文本作为边界输入，确保它将来也不能污染统计。

## 定位结果

链路逐段证据如下：

1. 本机 `http://127.0.0.1:8080/state` 响应可由严格 UTF-8 解码；调查时返回 `VIVHITE_RELIC_ORIGIN_STAR_CHART / 孤高冠冕`、`CLOAK_CLASP / 斗篷扣` 等正确 ID 与中文名。
2. `brain/client.py` 使用 `raw.decode("utf-8")`，没有 `errors="replace"`；非法 UTF-8 会抛出 `ConnectionDown`，不会在这里生成 U+FFFD。
3. `brain/knowledge.py` 使用 `encoding="utf-8"` 和 `json.dumps(..., ensure_ascii=False)` 原子写入。写盘层不会把正确中文改成 U+FFFD。
4. 实际持久化漏洞在身份选择：普通奖励载荷没有 `relic_id`，`policy.py` 会暂用本地化 `description` 生成 `("relic_pick", description)`；终局 `commit_run_end()` 原先无条件把该字符串作为 `stats["relics"]` 的字典键。一旦有效 JSON 中的上游显示字符串已经含 U+FFFD，它就会永久进入统计。

结论：真实问题不是 UTF-8 文件写入损坏，而是统计边界把本地化显示文本误当成稳定遗物身份；U+FFFD 拒绝属于同一身份边界的防御性校验。

## 修复

- 成功领取遗物后，Brain 使用动作响应中的运行库存做前后差分。若恰有一个遗物新增，就以新增项的稳定 `relic_id` 替换奖励描述标签。
- 丢失回执后由下一次状态确认动作成功时，复用同一库存差分逻辑。
- 增量对局日志只持久化不含 U+FFFD 的遗物归因标签。
- `Knowledge.commit_run_end()` 增加最终统计边界：空键或含 U+FFFD 的遗物键不得新建或增加样本。
- 不迁移、不删除、不重写既有乱码行；若旧数据仍存在，其原计数保持不变，但未来对局不能继续向该键加分。

这套处理优先恢复稳定 ID；只有响应中无法精确证明库存新增时，才兼容保留完整且无 U+FFFD 的旧本地化标签。

## 定向验证

新增 `sts2-ascend/tests/test_relic_stats_encoding.py`，覆盖：

- 正确中文经 API 严格 UTF-8 解码保持不变，非法 UTF-8 被拒绝。
- 乱码奖励描述通过动作后库存增量恢复为 `ANCHOR`。
- HTTP 解码、标签归一化、统计写盘后的 JSON 只含稳定 ID，并可严格 UTF-8 读取。
- 已有乱码历史键不被静默清洗，也不再增加计数。
- 增量运行归因不会继续持久化乱码键。
- 正常成功动作事务确实把规范化后的 ID 写入 `credit_tags` 与 `attribution_tags`。

测试结果：

- `tests.test_relic_stats_encoding`：6/6 通过。
- `tests.test_profile_card_stats + tests.test_pending_selection_reconciliation`：7/7 通过。

本机 `C:\Python314\python.exe` 启动时仍会输出既有的 `Could not find platform independent libraries <prefix>` 环境提示，但本次两个测试命令均正常执行并以 `OK` 结束；该提示与遗物编码链无关。

## 共享工作树边界

本任务的精确生产代码触点为：

- `brain/knowledge.py`：新增 `relic_stats_key()`；修改 `Knowledge.commit_run_end()` 的遗物入账边界。
- `brain/agent.py`：修改 `_durable_attribution_tags()`；新增 `_run_relic_id_counts()` 与 `_resolved_relic_pick_tags()`；让 `Agent._commit_successful_action()` 接收动作后状态；在 `Agent._reconcile_ambiguous_action()` 和 `Agent.run()` 的成功回执分支传入该状态。

共享工作树中另一个 playability-lock 诊断任务同时修改了 `brain/agent.py` 的 `_decision_log_entry()` 与 `Agent._signature()`，增加不可打原因和 `action_readiness` 证据。两项任务存在文件级重叠，但没有函数级或 hunk 级重叠；编码修复没有回退、覆盖或代改这些诊断字段。

运行中的 Brain 同期更新了 `knowledge/profiles/vivhite/stats.json`。本任务只读该文件取证，没有将其加入补丁、没有恢复旧版本，也没有手工清理其中任何键。
