# sts2-ascend 关闭 GLM 与 DeepSeek

日期：2026-09-05

## 结果

- 生产复盘链调整为 OpenCode/Kimi K3 → Codex/GPT-5.6-Luna；Luna 保持最低优先级。
- `glm-flash` 与 `deepseek-v4-flash` 保留在静态配置中作为可审计记录，但设置为 `enabled: false`，并清空旧式 `preferred_models`，不会参与新批次选择。
- 已经绑定到这两个后端的历史失败事务不再继续调用被禁用模型。调度器忽略其旧 provider cooldown，保留失败包与批次证据，并在落盘后改绑当前已启用模型。

## 故障反思

本轮 DeepSeek 长时间卡住并不等同于模型完全不可用。直接原因是原生 Profile 校验加入 Agent 主循环后，旧的 ambiguous-action 自检夹具没有提供 `native_profile_id`。门禁持续拒绝动作；夹具随后抛出的断言又被主循环的运输异常恢复边界捕获，最终形成无界循环，使模型侧和宿主侧自检都超时。

问题不在“校验越多越安全”，而在于新增横切门禁时只验证了生产拒绝行为，没有同步验证所有消费者、旧夹具、明确错误和有界退出。修复为：夹具显式满足现行 Profile 契约，并用停止条件让回归失败在有限帧内交给断言报告，不再从模拟 API 抛出会被生产重试层吞掉的异常。

后续门禁遵循最小化原则：只有不可逆写错档、学习污染、凭据泄露或对外发布风险才考虑运行时硬阻断；优先复用已有校验，普通稳定性问题使用观测、告警、有限重试或提交前验证。新增硬门禁必须同时具备必要性证据、明确拒绝原因、恢复路径、时间上界，并同步覆盖旧夹具和端到端自检。

## 验证

- 复盘模型链与迁移单元测试：24 项通过。
- `sts2-ascend/brain/selfcheck.py`：`SELFCHECK OK`，约 6 秒完成；修复前在同一夹具无限循环并超过 400 秒。
- 配置解析结果只包含 `kimi-k3`（优先级 1）与 `luna-max`（优先级 2）。
