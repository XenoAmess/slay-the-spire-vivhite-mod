# 2026-08-24 edge-tts 静默三层根因与防治

"edge tts 又不读了"的完整排查。**三层独立缺陷叠加**，前两层是真合成挂死，
第三层（丢队沙漠）才是本次长时间静默的主犯——修完前两层仍静默，直到
用磁盘 mp3 时间戳分布才定位到第三层。

## 三层根因

### A 层：进程内 asyncio 合成取消挂死（上午发现）
`asyncio.wait_for(Communicate.save(), 30)` 超时后取消本身在 edge_tts/aiohttp
内部挂死——`wait_for` 永不返回，3 个合成线程全部卡死。判据：日志只有播放器
的"合成超时未归"而无任何"合成失败"（合成函数从未返回）。
**修复**：合成改子进程 `python -m edge_tts --write-media`，`subprocess.run(timeout=35)`
硬杀。

### B 层：uv shim 跳板导致子进程杀不干净（下午发现）
uv 旁路环境里 `sys.executable` 是 shim 跳板（`builds-v0\.tmpXXX\Scripts\python.exe`），
它再孵化真实解释器当**孙进程**。超时杀掉的只是跳板，孙进程握着 stdout/stderr
管道不撒手 → `subprocess.run` 等管道 EOF 永远等不到 → 合成函数依旧永不返回。
判据：`sys.executable` 与 `sys._base_executable` 路径不同。
**修复**：用 `sys._base_executable`（真实解释器）直跑 + `PYTHONPATH` 传递
当前 `sys.path`（保证能 import edge_tts）。无孙进程，杀得干净。

### C 层：丢队沙漠（本次静默的主犯）
朗读器中途启动会从 offset 0 **重放整场直播流**：数百句瞬间涌入，队列（256）
打满后 reader 的丢弃逻辑 `q.get_nowait()` **静默扔掉最老一半**——恰好是播放器
脚下的句子。被丢句永远不会有合成结果，播放器每句空等 90 个 waited-秒
（worker notify 导致过计数，实际约 40~76 真实秒）才跳过，且跳过时
`sent=None`、SAPI 兜底**根本没读**，日志却谎报"SAPI 兜底"。
上百句丢弃区 ≈ **1.5~3 小时寂静**。

**判据（可复用的取证手法）**：mp3 中间文件从不删除——按 mtime 分布对照
日志超时行：seq 3~9 的 mp3 还是早晨 05:31 的旧文件（新 worker 从未写过=
被丢弃），而 seq 421~428 是 13:53 新写（合成流水线健康）。合成与播放的
断层一眼可见。

**修复**：reader 丢队时在 `done_cond` 内标记 `done[seq]=(None,None)` 并
`notify_all()`——播放器瞬时跳过、直追直播前沿；启动 offset 改为定位流尾部
8KB 对齐行首（迟到只读最新，不重放历史）。

## 防治纵深（全部落地）

1. **诚实日志**：超时路径区分"有原文→SAPI 兜底"与"无原文→静默跳过（被丢弃）"，
   假话从此绝迹；每 20 句打合成心跳（成功/失败计数）。
2. **熔断**：连续 5 次合成失败 → 10 分钟内全部直走 SAPI 并大声记日志
   （edge-tts 网络性死亡时不再全哑）。
3. **线程防死包装**：合成/播放线程整体 try/except + log——线程静默死亡
   （stderr 进隐藏控制台不可见）从此必留痕迹。
4. **stderr 重定向**：启动时重定向到 `knowledge/edge_dbg.err.log`。

## 验证

- 单发/3 并发子进程合成 standalone 2.8~3.5s 正常。
- 真机端到端：写最小测试流 → 朗读器上线 → 合成成功（edge_pf_00000.mp3
  产出）→ wav 播完即删 → LIVE-END 后 3 秒干净退出、释放锁、err.log 干净。
- 旧朗读器与孤儿 shim 进程清理，1683 个 edge_pf 临时文件清除。

## 备忘

- 杀进程树要想到**孙进程**：uv shim/脚本启动器都会再孵化，Stop-Process
  只杀直接匹配的进程，孤儿会握着管道/文件继续作祟。
- `subprocess.run(timeout)` 的可靠性前提是**子进程树会随根死掉**；
  任何"启动器→真实进程"双层结构都会绕过它。
- 诊断静默类故障先看**磁盘中间产物的时间戳分布**，比日志撒谎程度低。
