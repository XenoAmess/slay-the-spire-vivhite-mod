# sts2-ascend 异步复盘局间重载竞态

## 现象与证据

2026-08-28 的失败包重审产出运行时代码提交 `8c000da8`。提交在 11:12:58 完成，
`knowledge/pending_restart.json` 于 11:12:59 进入 `committed`，但第 851 局的局末主线程
先经过了唯一一次 `request_restart` 检查，复盘线程随后才置位。旧 Brain 因而继续开始第
852 局，PID、`boot_head` 和 `boot_review_commit` 均证明该局仍运行旧代码。

第 852 局结束后旧逻辑才再次碰到局末检查并重载。生产交接本身正常：旧心跳到新心跳约
6 秒，Runner 识别退出码 42，新 Brain 以 `boot_review_commit=8c000da8` 达到 `ready`。
因此故障不在 Runner，而在 Agent 只检查一次异步完成标志。

## 根因与修复

- 将“是否有待加载复盘 epoch”抽成统一判定：先认内存 `request_restart`，再认
  `committed`（及兼容旧格式）的耐久 marker。
- marker 只和 Runner 在 import 时冻结的 `boot_review_commit` 比较；不读取 Git HEAD，
  普通 run、文档或并行提交不会触发重载。
- 每次执行 UI 动作前，在真正空的 `MAIN_MENU` / `CHARACTER_SELECT` 重新检查。命中后
  以退出码 42 交给现有 Runner，避免旧 Brain 再开一局。
- 不在 `GAME_OVER` 直接重启。新进程可能仍看到同一终局帧，失败局会多走幻影结算，
  胜利局更可能被重复计数。`_finalize` 只完成归档并等待旧进程把界面送回菜单。
- 若用户中途放弃导致菜单仍有未归档旧局，先沿既有 new-run 检测把旧局按失败归档；
  在 `reset_for` 接受新局和任何新局动作之前完成重载交接，既不丢旧局证据，也不让新局
  使用旧策略。
- `prepared`、非法 marker、已由当前进程加载的同 epoch，以及战斗等局内屏均不触发。

## 验证与上线注意

- `test_review_health_marker.py`：9/9，覆盖内存标志、耐久 epoch、prepared 拒绝、
  GAME_OVER 胜利回声、未归档旧局以及新局首动作前交接。
- `test_review_closure.py`：16/16。
- `brain/selfcheck.py`：`SELFCHECK OK`。
- `git diff --check` 通过；相关大套测试继续作为提交前回归。
- 线上更新先在当前 Brain 已完成 import 后修改和测试，避免未验证工作树被中途热载；
  提交后仅在局间使用统一 Stop/Start 入口验收，继续遵守 Brain 断流不超过 2 分钟。

## 踩坑

“局末”不等于“跨进程安全边界”。终局证据已经写完，也不能假设游戏在新进程启动前
必然离开 `GAME_OVER`。安全边界必须同时约束游戏界面、run 载荷和本进程归档状态；
异步线程的内存标志还必须由耐久 marker 兜底，否则一次检查天然存在漏窗。
