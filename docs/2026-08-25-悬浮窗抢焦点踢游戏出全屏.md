# 2026-08-25 悬浮窗抢焦点踢游戏出全屏（右侧栏盖住游戏）

## 现象

游戏时不时被屏幕右侧任务栏盖住——本质是**游戏窗口被抢焦点踢出独占显示**，
任务栏随之浮到游戏上面。用户观察到"某种机制触发了什么窗口"。

## 根因

每场复盘 `_launch_viewer` 都会拉起一个**新的 ASCEND-VISION 悬浮窗**（Tk，
`overrideredirect + topmost`）。Tk 的 overrideredirect 窗口是 WS_POPUP，
**创建/映射时默认抢激活**——全屏游戏被顶掉。复盘每局一场 = 每十几分钟抢一次，
完全吻合"有时候出现"。

帮凶：viewer 锁的竞态——`acquire_lock` 任何异常**默认放行**（return True），
两个实例同时启动撞出 OSError 就双实例运行（现场查获 2 个 viewer 孤儿）。

## 修复

1. **WS_EX_NOACTIVATE**（0x08000000）：映射前给窗口扩展样式打上"永不激活"，
   悬浮窗变成纯覆盖层（与既有点击穿透的 OR 组合手法一致，用 `wm_frame()` 句柄）。
2. **焦点还原**：建窗前记住 `GetForegroundWindow`，映射后用 ALT 技巧
   （keybd_event ALT down → SetForegroundWindow → ALT up，绕过前台锁）把焦点
   还给游戏。interactive 模式（人工拖拽用）不套用，保留原行为。
3. **锁改原子语义**：`os.open(O_CREAT|O_EXCL)` 独占创建 + 死锁接管 +
   **任何异常一律拒绝**（失败放行是双实例根源）。

## 验证

- 双实例并发启动 → 恰好存活 1 个（锁原子性）。
- 启动 viewer 前后 `GetForegroundWindow()` 句柄不变 → **焦点未被偷**。
- 交互拖拽模式不受影响（NOACTIVATE 仅自动模式套用）。

## 教训

- **任何自动化拉起的 GUI 窗口都必须考虑焦点代价**——全屏应用场景下
  "窗口出现"本身就是一次焦点抢夺；纯展示窗口应 WS_EX_NOACTIVATE 化。
- 锁的失败语义要**fail-closed**：异常时"拿不到锁"才是安全默认，
  "异常就放行"等于没有锁。
