# sts2-ascend Edge 实时旁白稀疏输出静默修复

日期：2026-08-30

## 问题

Edge TTS 已经生成了有效音频，但实时旁白长时间没有声音。故障不在音频设备、音量或直播姬捕获链，而在 `edge_speaker.py` 的序列消费状态机。

旧实现把 `played` 当成了下一条已入队任务的序号。当当前没有新句子时，播放线程仍会等待一个尚未入队的未来 seq，约 90 秒后把它提前记为 timeout/静默并向前推进。真实文本稍后以同一 seq 到达时，Edge 生成的结果已经没有消费者，遂成 orphan 音频。输出节奏越稀疏，这个问题越容易稳定复现。

## 证据

- 应用语音配置为 `volume=200`、`muted=false`。
- Windows CoreAudio 的默认 Console/Multimedia 端点是 Realtek Digital Output (S/PDIF)，状态正常，音量 100%，未静音。
- 直播姬 Desktop Audio 捕获的是同一端点 ID，输入启用、未静音、音量为 1.0，且 Streaming 期间没有端点失效。
- 故障期间的 MP3 和 WAV 能够正常生成；抽样 WAV 为有效的 24 kHz 单声道非静音音频。日志显示未来 seq 先被约 90 秒的 idle timeout 跳过，其后同 seq 的真实合成结果才到达。

因此，“已生成音频”不等于“已播放”；定位时必须以真实播放完成事件为准，不能只看合成成功或文件落盘。

## 修复方案

### 1. 以入队事实驱动播放

新增 `_PlaybackBuffer`，把一条旁白的生命周期显式分为 admission、`pending`、`claimed` 和 `done`：

- 只有已 admission 的 seq 才能进入等待和 timeout 逻辑。
- 播放线程不再根据 `played` 臆造一条未来任务；idle 时没有真实任务，也就不会凭空起 90 秒计时器。
- 播放线程 claim 已入队的序号，工作线程发布合成结果，成功或已确定的失败才进入 `done`。
- 只对真实入队且正在等待的句子执行超时降级；超时后才到的结果被识别为 late result，不会重新进入播放序列。

这样将“播放进度”与“工作是否存在”分开，消除了稀疏输出下的虚假 timeout。

### 2. 隔离不同 speaker 实例的临时文件

WAV 文件名改为包含当前 PID 和随机 nonce 的实例私有名称，再加 seq 定位句子。这避免旧、新 speaker 在同一 seq 上重名，也避免一个实例误删另一个实例正在使用的 WAV。

### 3. 闭环处理 close、late result 和当前 WAV

`_PlaybackBuffer.close()` 在同一个 Condition 临界区内将 buffer 标记为 closed，收集已接受但尚未播放的 WAV，并清理 `pending`/work/`claimed`/`done` 状态。文件删除放在锁外执行，避免把文件系统延迟带入共享锁。

已 close 后到达的发布会被拒绝，其 late WAV 立即清理；播放线程当前持有的 WAV 也有明确的 `finally` 收尾路径。MP3 同样始终在 `finally` 中删除，即使合成后的转换、发布或播放失败，也不会遗留本次中间 MP3。

### 4. 让关闭真正等到清理完成

player 和 worker 线程都使用 non-daemon 语义，避免解释器在清理途中直接抛下它们。关闭时给 player 最多 5 秒等待预算；所有 worker 共享额外 3 秒总预算，而不是每个 worker 各等 3 秒。这在保证有界停止的同时，给 close 和 late-result 清理留出可验证的收尾窗口。

## 验证

- Edge 路由和 owner-epoch 相关的目标测试合计 21/21 通过。
- 额外压力验证覆盖连续 admission/发布/播放、close 与 late publish 竞态、已接受未播放 WAV 回收，没有再观测到未来 seq 被 idle timeout 提前消费或本轮临时文件泄漏。
- 测试日志使用独立的临时路径，不写入生产 TTS 日志和运行目录，避免测试事件被误当成直播现场证据。
- 2026-08-30 04:23 的实际运行观测中，seq 0–9 均出现真实播放完成，而不只是合成完成。这验证了修复后的产生、发布、消费和清理全链。

## 踩坑与避免方法

- 不要用“上一条已播序号 + 1”表示“下一条已入队任务”。序号连续性不能替代 admission 事实。
- timeout 只能从真实任务入队后开始计时。idle 本身不是一条超时任务。
- 临时文件名不能只用 seq。进程重启或两个实例交接时，seq 会重用，必须再加实例唯一性。
- close 不能只发一个停止信号；必须原子地禁止新发布，接管已接受未消费文件，并覆盖 late publish 竞态。
- 语音无声时，要分别验证端点、捕获、合成、发布、播放完成五层，不要用“有 WAV”直接推断扬声器或直播姬有问题。
- 测试与生产必须隔离日志和临时目录，否则时序证据会被测试样本污染。

## 运营注意

- TTS 历史目录中仍有约 3.1 GB 临时文件。本次修复没有删除它们：批量删除属于破坏性操作，必须另行获得用户明确授权，并且在删除前精确校验目标范围。
- 后续监控应同时看“合成成功”和“播放完成”，并警惕同 seq 跳过后才生成、WAV 长时间留存、或 close 后仍成功发布等信号。
- 直播中如需重载整套服务，必须使用项目统一入口并遵守 Bilibili 中断最多两分钟的硬性死线；一旦 Streaming 中断，先恢复直播，再继续语音诊断。
