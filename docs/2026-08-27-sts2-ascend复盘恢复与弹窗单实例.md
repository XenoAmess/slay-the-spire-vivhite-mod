# sts2-ascend 复盘恢复与弹窗单实例

## 已发生的问题

1. 复盘提交曾使用固定文件 allowlist。模型完成的安全静态项目文件不在名单时，
   成果会在已经花费复盘额度后才被拒绝；同一批的 `.pyc` 或其他 cache 产物也曾让
   已通过自检的源码整批作废。
2. 失败批次只保存可自动套用的 patch，无法满足后续逐文件分析被规则拒绝成果的需求。
   失败包本身没有受 Git 跟踪，还需要另一份持久清单记录批次、原因和补合状态。
3. 直播现场出现过两个 `ASCEND-VISION` 窗口互相置顶。进程命令行确认，第二个窗口
   来自 `review_salvage/.../raw_sandbox/repo` 副本：手工运行该副本的自检时，测试实例化并
   驱动了真实 `Agent`/`Agent.run()` 路径，构造器启动了 detached 驾驶舱监督器。副本的
   文件锁与主树不同，自检父进程结束后，使用旧数据的孤儿窗口仍在刷新和置顶。

## 已落地的处理

- 复盘验收改为 deny-only：完整盘点隔离工作树，接收 `sts2-ascend/` 下安全的静态
  源码、配置、脚本、测试、文档和静态知识，包括新建/ignored 文件和 `brain/config.json`。
  cache 只从 patch 排除，不再拖死同批已验证源码；在线运行状态、Git 元数据与
  越界/不安全路径会拒绝自动合入整批，并先保全完整现场。
- 超时、自检失败、边界拒绝或提交冲突时，完整保存全部工作树字节，包括 cache、
  ignored、越界和被规则拒绝的文件。`REVIEW_REJECTIONS.md` 为每个新失败包建立单独
  commit；只有完成补合/空包审计、更新状态并从远端确认结论后，才删除对应失败包。
- 已精确结束来自 raw sandbox 的孤儿 viewer，没有停止游戏、Brain 或正在工作的复盘。
  复盘子进程继续继承 `STS2_ASCEND_DISABLE_VIEWER=1`；Windows viewer 另使用 session-local
  命名互斥体 `Local\STS2_ASCEND_ASCEND_VISION`，即使某个手工 raw 自检没有继承禁用环境，
  不同仓库副本也无法再开第二个驾驶舱。原文件心跳锁仍用于生命周期归属和诊断。
- 后续全量自检又复现了另一条同源副作用：OpenCode 继承真实 Brain 的
  `STS2_ASCEND_BOOT_ID`，自检中的两次 `Agent.run()` 因无法更新真实 Brain PID 记录而报
  “无法发布 Brain ready 启动握手”；同一测试还会向正式 session 的驾驶舱文件写入假状态。
  现已在 OpenCode 与宿主自检子环境移除专属于启动握手的 `BOOT_ID`，强制禁用 viewer，
  并在两处主循环测试中 stub 驾驶舱启动。带伪造 `BOOT_ID` 的全量自检 3.1 秒通过，
  自检前后没有新增 viewer，也没有改动 Brain PID 记录。

## 工作方式结论

- 复盘提交验收与 Brain 热重启要分开：静态项目成果可正常提交；只有 Brain 长驻进程
  实际加载的 Python/运行配置实质变更需要局间热重启，不因文档或其他静态文件
  制造 Brain 断流。
- 长任务按独立、可验证、可回退的增量及时 commit/push。本次路径分类、deny-only 主链、
  runner 恢复和 viewer 单实例分别落地，避免等待所有后续项一次修完才上库。
- “必须先证明必要性”的成本约束只限于无现实证据的额外安全边界推演。它不限制功能优化、
  真实故障修复、架构改进或主动推进；安全方向没有用户要求、运行日志、可复现测试或现有数据时，
  不再继续消耗模型额度。
