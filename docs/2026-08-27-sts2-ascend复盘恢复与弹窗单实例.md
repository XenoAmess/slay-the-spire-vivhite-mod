# sts2-ascend 复盘恢复与弹窗单实例

## 已发生的问题

1. 复盘提交曾使用固定文件 allowlist。模型完成的安全静态项目文件不在名单时，
   成果会在已经花费复盘额度后才被拒绝；同一批的 `.pyc` 或其他 cache 产物也曾让
   已通过自检的源码整批作废。
2. 失败批次只保存可自动套用的 patch，无法满足后续逐文件分析被规则拒绝成果的需求。
   失败包本身没有受 Git 跟踪，还需要另一份持久清单记录批次、原因和补合状态。
3. 直播现场出现过两个 `ASCEND-VISION` 窗口互相置顶。进程命令行确认，第二个窗口
   来自 `review_salvage/.../raw_sandbox/repo` 副本：手工运行该副本的自检时，测试实例化并
   驱动了真实 `Agent`/`Agent.run()` 路径，构造器启动了 detached 驾驶舱监督器。副本的
   文件锁与主树不同，自检父进程结束后，使用旧数据的孤儿窗口仍在刷新和置顶。
4. 18:30 的 OpenCode 卡住并不是 GLM API 或上下文耗尽。会话数据库显示 provider 已正常结束，
   最后一个 selfcheck 工具一直停在 `running`；同秒 raw clone 的 viewer 进入 Tk 主循环。旧启动器的
   `close_fds=False` 让 detached viewer 继承了工具捕获管道，即使 selfcheck 已完成，OpenCode 也永远
   收不到 EOF。旧的 8 KiB 文本读取又让直播流看起来像“长时间完全没输出”，掩盖了真实卡点。
5. 失败包有“全量取证现场”不等于已有可靠补合输入：历史 `wip.patch` 可能为空，
   包内还会同时存在有效源码、cache 和在线 viewer 现场。由宿主盲套旧 patch 既不能捞回真实成果，
   也越过了“由 GLM 对照当前 HEAD 复审、重实现和解冲突”的责任边界。

## 已落地的处理

- 复盘验收改为 deny-only：完整盘点隔离工作树，接收 `sts2-ascend/` 下安全的静态
  源码、配置、脚本、测试、文档和静态知识，包括新建/ignored 文件和 `brain/config.json`。
  cache 只从 patch 排除，不再拖死同批已验证源码；在线运行状态、Git 元数据与
  越界/不安全路径会拒绝自动合入整批，并先保全完整现场。
- 超时、自检失败、边界拒绝或提交冲突时，完整保存全部工作树字节，包括 cache、
  ignored、越界和被规则拒绝的文件。`REVIEW_REJECTIONS.md` 为每个新失败包建立单独
  commit；只有完成补合/空包审计、更新状态并从远端确认结论后，才删除对应失败包。
- 已精确结束来自 raw sandbox 的孤儿 viewer，没有停止游戏、Brain 或正在工作的复盘。
  复盘子进程继续继承 `STS2_ASCEND_DISABLE_VIEWER=1`；Windows viewer 另使用 session-local
  命名互斥体 `Local\STS2_ASCEND_ASCEND_VISION`，即使某个手工 raw 自检没有继承禁用环境，
  不同仓库副本也无法再开第二个驾驶舱。原文件心跳锁仍用于生命周期归属和诊断。
- 后续全量自检又复现了另一条同源副作用：OpenCode 继承真实 Brain 的
  `STS2_ASCEND_BOOT_ID`，自检中的两次 `Agent.run()` 因无法更新真实 Brain PID 记录而报
  “无法发布 Brain ready 启动握手”；同一测试还会向正式 session 的驾驶舱文件写入假状态。
  现已在 OpenCode 与宿主自检子环境移除专属于启动握手的 `BOOT_ID`，强制禁用 viewer，
  并在两处主循环测试中 stub 驾驶舱启动。带伪造 `BOOT_ID` 的全量自检 3.1 秒通过，
  自检前后没有新增 viewer，也没有改动 Brain PID 记录。
- viewer 启动改为 `close_fds=True`，从根上切断 detached 子进程对 OpenCode/selfcheck 捕获管道的
  继承。复盘流改为按可用字节即时读取，不再等满 8 KiB；8 小时总预算保持不变，另设 5 分钟静默
  告警与 10 分钟无进展终止。stall 会完整留档并交回原 GLM 重试，不记入模型不可用冷却。

## 失败包逐包重投机制

### 1. 唯一 target、attempt lineage 与队列恢复

离线入口只接收显式指定的失败包，不会在 Brain 启动时扫描并重投全部历史现场。每个包的
package id 是稳定且唯一的 `replay_target` / `retry_group`；该 target 与直播正常局、其他 target
分开取批。同一 target 重试再失败时，新包不成为新 target，而是标记为 `replay_role=attempt_evidence`，
带 `replay_parent_attempt` / `replay_attempt_no` 加入 `salvage_attempts`。提示词中只有唯一 target 需要回执，
但会同时看到由各 attempt 完整失败包派生的有界证据。两个 target 即使含重叠局号，也不会被普通“按 run 去重”
吞掉或混成一次 GLM 任务。

工作线程取批时为条目分配不变 `queue_id`，`reviewing.items` 保留完整条目。一个新失败包发布时，
取证字节与 manifest 里的 `replay_enqueue_pending`、target/role、`replay_queue_ids` 通过同一次目录原子改名
一起成为持久事实。因此即使宿主在失败包发布后、queue 收尾前崩溃，新 Brain 也会通过 queue id
找回中断的 pending/reviewing 条目，统一它的 target 和 attempt lineage；若队列中已没有该事务，则幂等地
补建且仅补建一个 target job。

失败包 manifest 中的 `model` / `source` / `every` 被复制到每个重审条目，退避、worker 异常和
Brain 重启都会持久保留这个实际计划。这保证机制修好后是把原失败批次再交给 GLM，而不是宿主
弄一个另外的代理模型替它完成。对没有记录这些字段的旧 schema，才按当前优先/兜底配置补默认值。

旧失败包若没有任何真实 run id，入队器会将它标记为 `evidence_only`，同时仍分配一个正整数
synthetic run 以满足队列 schema。这个数字只出现在 `queue_identity_runs`；prompt 的 `requested`、
`exact`、`missing`、`runs_summary` 均为空，`decision_chain_evidence.full_failure_run` 为 `null`。
因此当前知识库后来出现同号 run 时，也不能被借作旧失败包的批次证据或死亡局完整思维链。

启动恢复不是只跑一次就算完成：同一个 worker supervisor 负责 replay intent 对账、ledger 补齐、
pending/reviewing 恢复、延迟现场补全与 host-only closure。任一启动/运行维护步骤异常时不改坏持久状态，
30 秒后从整套幂等入口重试；线程真正退出时在 `finally` 中释放 `_worker_started` latch 和线程引用，
后续健康检查可以重新拉起 worker，不会因残留 latch 永久停摆。

### 2. evidence schema v3

重投入队时不扫描 raw clone。Brain 恢复后，worker 才从完整 `raw_sandbox` 懒物化两份**派生证据**：

- `retry_candidate.patch`：只包含 deny-only 分类为安全静态项目文件的候选改动；
- `retry_candidate_inventory.json`：列出全部变化路径，并分成 `accepted_candidate_paths`、
  `transient_artifact_paths`、`online_runtime_paths` 和 `rejected_or_unexpected_paths`。

沙箱验收、失败 WIP 捕获和重审物化统一使用临时私有 index 与 object directory，只把 raw clone objects
当 alternate 读取；`read-tree`、force-stage 与新对象都落在私有空间，不移动 raw HEAD，也不覆盖 raw
index 或写入 raw object database。物化基线是 manifest 中的 `pre_head`，并为 raw `.git/index` 建立
独立的只读 index 环境，防止私有工作树 index 抹掉模型原 index 证据。v3 不再把现场压成一个来源，
而是独立盘点并导出：

- raw worktree 相对 `pre_head` 的静态改动；
- raw index 相对 `pre_head` 的独立 staged 改动；
- raw `HEAD` 在已前进时的 commit diff；
- 每个指向非 `pre_head` 对象的本地 `refs/heads/*`；
- 每个 stash。

`for-each-ref` 看到的所有 refs 都写入 inventory provenance，但只有 `refs/heads/*` 中的 commit 会进入
代码候选源；`refs/notes/*` 等其他 refs 只用于取证溯源，不会被当作待补合代码。
每个来源在 inventory 中单独记录 object、路径分类、candidate hash 和去重关系，总 candidate 只串联
accepted-only 片段。整个过程不写 raw clone 的 HEAD、local refs、stash、worktree、index 或 object database。
如果早期物化器曾向 raw object database 写入不可达 objects，不会破坏性清理这些取证字节；
manifest 的 `retry_evidence_history` / `raw_forensic_note` 保留迁移来源，v3 后续绝不再写入原 objects。

某些 commit/CAS 失败包可能没有 raw clone，但已保存 deny-only 验证过的 `validated_candidate.patch`。
v3 会将它提升为 `retry_candidate.patch` 并生成对应 inventory；不会因 raw 缺失就把包含 cache/在线现场的
全量 `wip.patch` 冒充“已验证 candidate”。候选 patch 不包含 cache、在线运行文件或被拒路径，
但它们的路径仍在全量 inventory，字节仍在原失败包。原 `files/`、`raw_sandbox/`、`wip.patch`、
报告和 manifest 是取证真值；派生 candidate/inventory 是可重建索引。

提示词在固定总字节预算内回灌 manifest、inventory、报告与候选 patch，并明确要求 GLM：

1. 对照当前 HEAD 重新审核，不假定旧 patch 仍可直接使用；
2. 选择性重实现仍有效的成果，自己解决与当前代码的冲突；
3. 运行 selfcheck，由现有 deny-only 验收/提交链提交它的结果。

宿主不 apply `retry_candidate.patch`，也不代写该批策略；它只提供证据、队列、验收、反馈与耐久恢复。

### 3. 软回执与耐久闭环

GLM 必须对当前包在复盘报告写一行：

```text
retry_resolution: <package-id> integrated|no_valid_change|still_pending
```

- `integrated`：有效改动已基于当前 HEAD 重实现、解冲突并验证；
- `no_valid_change`：复审确认没有仍应合入的改动；
- `still_pending`：本轮没有解决该包。

这是**软回执**，不是宿主用来拒绝其他已验收代码的新门禁。没写或写 `still_pending` 时，本轮已接受的
commit 保留，新失败包只作为 attempt evidence 追加；唯一 target 连同原 `retry_group` / `model` / `source` /
`every` 退避到队尾，继续由 GLM 处理。
这既允许一次复盘分步取得有效改动，也避免一行报告遗漏伪造“包已闭环”。

GLM 给出 `integrated` / `no_valid_change` 后，宿主先把回执、commit 与完整 lineage 写到 target，
再传播给每个 attempt。这时只落回执，不隔离或删包；必须先让 `_finalize_review_batch`
成功消费持久 `reviewing` 事务，才启动 host-only closure。代码 commit 必须已在 upstream；
之后每个包只走一次最终清单闭环：

1. 把且仅把该包原子改名为 `.glm-closed-<package-id>`，完整字节仍在；
2. 精确替换 `REVIEW_REJECTIONS.md` 的该包行，为这一条最终状态单独 commit；
3. Stop 未到来时做一次 push 尝试，并从 upstream 精确确认该 marker 的下一行就是目标最终状态；
4. 只有这次 ledger 远端确认后，才逐文件删除隔离目录；根 `manifest.json` 作为恢复回执最后删除，
   然后才执行目录 `rmdir`。

闭环顺序是 attempt-first、target-last。target 是 lineage 的耐久日志：某个 attempt 的回执传播失败时不删 target，
启动恢复可以再从 target 传播同一回执。清理循环在每个文件/目录前检查 Stop；中断时部分清理的
`.glm-closed-*` 仍是可恢复现场，下次启动在确认 upstream ledger 后续删。这些只是 host-pending
耐久恢复，不会再召回 GLM 浪费一轮已完成的复审。若进程恰在“最后删除 manifest、随后 rmdir”的
有界尾部崩溃，启动时可能只看到空 quarantine；空目录本身不构成删除授权，必须再次精确确认 upstream
中该 package 的最终 `并闭环` 行，才删除这个特定空尾目录。

### 4. 离线重投操作

从仓库根目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\sts2-ascend\scripts\Stop-Agent.ps1 -KeepGame
py -3 -B .\sts2-ascend\brain\llm_review.py --replay-salvage PACKAGE_A,PACKAGE_B
powershell -NoProfile -ExecutionPolicy Bypass -File .\sts2-ascend\scripts\Start-Agent.ps1 -SkipDeploy
```

`--replay-salvage` 只接受 `knowledge/code_backups/review_salvage/` 的直接子目录名。一次可用逗号命名多个包，
但入队后仍是多个独立 `retry_group`，不是一个大混合批。Brain session 处于 `starting` / `running` /
`foreground` 时入口会拒绝改队列，所以不应跳过统一 Stop。入口只原子写小 manifest intent 和 queue
条目，对失败包体积为 O(1)；不在受控停机窗口扫描 raw clone、hash 大文件或生成 candidate。
如果命名的目录是 `attempt_evidence`，入口会回溯并唤醒已有 target；target 缺失时保留 attempt
但绝不擅自提升出第二 target。进程恢复后 worker 才懒物化 v3 证据，并在后台串行逐 target 执行。

## Viewer 的两个独立故障面

“只有一个窗口”和“工具子进程能退出”是两个不同问题，不能只修其一：

- **跨目录单实例**：文件锁必须通过 `lifecycle.STACK_ROOT` 指向同一 stack，复盘子进程继承
  `STS2_ASCEND_DISABLE_VIEWER=1`。Windows 还使用 `Local\STS2_ASCEND_ASCEND_VISION` 命名互斥体，阻止
  主树、`review_work` 和 `review_salvage/raw_sandbox` 因各自 `__file__`/文件锁不同而同时开窗。
- **句柄隔离**：detached viewer 启动必须 `close_fds=True`。否则它即使被单实例机制允许、也可能继承
  OpenCode/selfcheck 的 stdout/stderr 管道，在进入 Tk 循环后长期持有写端，使宿主等不到 EOF。

复盘流的字节级读取与 15/30 分钟无进展 watchdog 是观测/自愈层：它们使长时间无字节可见且可终止，
但不代替上述单实例与句柄根因修复。

## run803 后自动存档停摆：私有提交成功、真实 index 未跟上

### 事故根因与数据状态

这次不是 Brain 停玩、push 失败或知识库丢失。run803 的在线存档已经用私有 index 成功建立 commit，
随后也成功 push；故障发生在 commit 发布后的真实 index 同步阶段：同步命令恰好撞上并发存在的
`.git/index.lock`，单次执行失败，真实 index 因而停留在 run802 的机器存档快照。

从 run804 开始，每次在线存档在事务入口都会看到进度 pathspec 仍有 staged 差异。旧逻辑无法区分
“上次机器提交后没同步完的旧 index”和“用户刚刚 stage 的内容”，所以按保护用户 staged 内容的规则
整笔拒绝，表现为一个多小时没有新的 `chore(sts2-ascend): 第xxx局存档`。其间 Brain 仍持续把最新
`stats.json`、`progression.json` 和逐局 run JSON 写入工作树；因此 804+ 的运行数据没有丢，只是尚未进入
Git 历史。

### 修复机制

自动存档仍在一次性私有 index 中构造 commit；修复不引入全仓脏状态或全仓指纹门禁，只补齐真实
index 的精确同步与恢复：

1. 分支 CAS 成功后，只对本次进度 pathspec 同步真实 index。遇到短暂 `index.lock` 时进行有界短重试，
   每次尝试前重新核对父子提交关系、目标机器 commit 仍在当前 HEAD 历史中、这些 paths 后续未变，以及
   目标 index 的精确身份，避免等待期间条件变化。
2. 短重试仍失败时，保存耐久 pending-sync 回执，记录需要落到的机器存档 commit、其父提交和精确
   paths；进程退出或 Brain 重启不会遗忘这笔未完成同步。恢复时再以 parent tree 精确验证当前 index，
   不依赖进程内状态。
3. 下一次 autogit 事务先执行 preflight 自愈。只有当前真实 index 在这些精确 paths 上仍与记录的机器父
   提交快照完全一致时，才仅前移 index 到机器存档 commit；工作树完全不动。
4. 对事故发生在 pending-sync 回执落地之前的历史现场，也可按同一证据恢复：定位最近的机器进度提交
   （`第…局存档` 或 `复盘前在线存档`），证明目标 paths 的 index 恰等于它的父提交后再同步。判定以
   机器提交身份和精确 path 内容为准，不要求它仍是当前 HEAD，所以 HEAD 后续已经加入代码、拒合清单等
   无关 commit 时仍可恢复。
5. 如果任何目标 path 已被用户真正 stage，index 就不会匹配记录的机器父快照；自愈会保留用户内容并
   拒绝覆盖。这里恢复的是可证明的机器遗留状态，不把普通 staged 内容宽松地猜成机器现场。

### 运维检查

出现“游戏仍在跑，但存档 commit 长时间不再增长”时，按以下证据链检查：

- 对比 Git 历史最后一个 `第xxx局存档`、工作树 `stats.json` 的 run 计数和最新逐局 JSON。工作树更靠前
  说明应先排查 autogit，而不是判定运行数据丢失。
- 查看 Brain 日志中“提交已建立，但真实 index 同步失败”、`index.lock` 和“目标路径已有用户 staged”
  是否连续出现；再用 staged diff 判断 index 是否恰好停在最后机器存档的父提交。
- 不要看到这些进度文件 staged 就直接全量 reset/unstage。先让 preflight 按精确 paths 与提交身份自愈；
  证明失败时应保留现场，因为它可能确实包含用户 staged 内容。
- 恢复后同时确认：补存档/后续正常存档已 commit 并 push；HEAD 中进度 run 已追上工作树；进度
  pathspec 不再残留机器 staged 差异；下一局仍能独立产生并推送新存档。

## 工作方式结论

- 复盘提交验收与 Brain 热重启要分开：静态项目成果可正常提交；只有 Brain 长驻进程
  实际加载的 Python/运行配置实质变更需要局间热重启，不因文档或其他静态文件
  制造 Brain 断流。
- 失败包的策略复审属于 GLM：它要重审、重实现、解冲突、自检和产出回执；宿主只负责
  完整证据、独立队列、验收提交与清单/隔离的耐久恢复。机制出错时先修机制并再调 GLM，
  不用维护 AI 代写具体策略掩盖故障。
- 长任务按独立、可验证、可回退的增量及时 commit/push。本次路径分类、deny-only 主链、
  runner 恢复和 viewer 单实例分别落地，避免等待所有后续项一次修完才上库。
