# sts2-ascend 三级复盘模型优先链预研

日期：2026-08-28

目标优先链：

1. `(opencode) opencode-go/glm-5.3-flash@max`
2. `(codex) gpt-5.6-luna / reasoning=max / auto-review`
3. `(opencode) kimi-for-coding/k3`

## 结论

方案可行，但不是在 `config.json` 里多加一个模型名就能完成。当前复盘实现把“模型选择”和
“OpenCode runner”绑在一起；要正确插入 Codex，必须增加一个很薄的 runner adapter，同时继续复用现有的
隔离 clone、失败包、deny-only 验收、selfcheck、提交推送、拒合清单、pending restart 与 Brain 健康确认。

推荐分两阶段：

- 直播期间可以在隔离工作区完成代码、测试、文档和默认关闭的暗部署，不中断当前 Brain。
- 真正打开三级链，建议下播后切配置并用统一入口热重启、验收和回滚演练。

## 是否必须下播后修改

### 风险判断

| 阶段 | 可否直播中进行 | 判断 |
| --- | --- | --- |
| 预研、写代码、假 CLI 单测 | 可以 | 在隔离 clone 中完成，不触碰运行中 Brain 和动态配置 |
| 提交默认关闭的兼容代码 | 可以 | 当前 Brain 已加载旧 Python 模块，不会因源码落盘自动换脑；不得提前改生效配置 |
| 切换 `review_model_chain` 并重启生效 | 建议下播后 | 会改变队列分配、失败重试亲和、复盘子进程和生命周期识别，属于中等运行风险 |
| Luna 自然接管验收 | 建议下播后首次观察 | Codex 当前会先经历约 100 秒 WebSocket 回退，且这是第一次接入真实失败包闭环 |

最终启用并不需要重新部署游戏 DLL，也不需要长时间停 Brain；仍可使用：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\sts2-ascend\scripts\Stop-Agent.ps1 -KeepGame
powershell -NoProfile -ExecutionPolicy Bypass -File .\sts2-ascend\scripts\Start-Agent.ps1 -SkipDeploy
```

正常可把断流控制在 2 分钟内。但“重启很短”不等于“上线风险很低”：本次改动会触及 Brain 局间入队、
worker 取批、失败包重试和 Stop/Start 的进程身份判断。如果实现有遗漏，最可能在一局结束时表现为 Brain
退出、复盘队列卡住、失败包绑定错模型，或遗留 Codex 子进程。因此在没有即时游玩收益的情况下，建议
直播中暗部署、下播后启用。若必须直播中上线，也应等当前 GLM 批次闭环，在自然局间窗口热重启，且准备
一键恢复旧配置与旧提交；不应为了测试而在生产中人为禁用 GLM。

## 已完成的可行性验证

- 本机 Codex CLI：`0.149.1`。
- 当前认证：ChatGPT 登录可用。
- 本机模型目录包含 `gpt-5.6-luna`，支持 `low/medium/high/xhigh/max`。
- `codex exec --json --ephemeral --approve-for-me` 非交互 canary 成功返回 `LUNA_READY`。
- canary 使用 `reasoning=max`，输入 12,279 tokens，其中 9,984 cached，输出 7 tokens。
- Codex Doctor 确认认证和 HTTPS provider endpoint 可达。
- 本机 WebSocket 连续 5 次超时后会自动回退 HTTPS；本次固定多等待约 100 秒，随后成功。
- 当前 built-in `openai` provider 禁止通过命令行覆盖
  `model_providers.openai.supports_websockets=false`，不能靠该配置强行跳过 WebSocket。

官方资料确认 Luna 支持 `max` reasoning；`codex exec` 适用于脚本和 CI；`--approve-for-me`/Auto-review
只是把越过 sandbox 边界的审批交给独立 reviewer，并不会扩大可写目录或网络权限：

- [GPT-5.6 Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna)
- [Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)
- [Codex Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review)
- [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference)

这里的 Auto-review 不是“再让一个模型审查代码结果”；它只负责处理主 Codex agent 的越界审批请求。
隔离仓内的正常读写不会触发审批，最终代码质量仍由公共 selfcheck、路径验收和提交闭环判定。

## 当前架构的直接问题

### 1. runner 与模型硬编码

`brain/llm_review.py` 的 `preferred_models` 只是 OpenCode model string；`resolve_review_plan()` 通过
`opencode models` 探测，`run_review()` 固定构造 `opencode run`，隔离 clone 又固定改写 `--dir`，输出只用
`OpencodeJsonTranslator`。所以直接把 `gpt-5.6-luna@max` 塞进现有列表会被当成 OpenCode 模型调用，必然错误。

### 2. 模型探测可能阻塞游玩线程

当前 `enqueue_review()` 在 Brain 主线程调用 `resolve_review_plan()`；后者可能同步执行
`opencode models` 最多 60 秒。新增 Codex 后不能继续往这个路径叠探测，否则“异步复盘不阻塞游玩”并不成立。

正确做法是：主线程只耐久入队证据，worker 取到新批次后再探测和选择 backend，并把完整计划原子写入
`reviewing`。失败重试项则携带此前已选择的计划。

### 3. 失败包的模型亲和目前不够真实

队列会写入和校验 `retry_same_model`，但 worker 并没有真正读取它。当前失败包继续交给 GLM，更多是因为
队列项碰巧还保存着同一模型，而不是显式状态机保证。

三级链上线前应明确实现：

- 模型已输出、改过隔离仓或进入验收后失败：保持同一 runner + 同一模型重审。
- sticky 模型冷却时，该失败包等待，但不能阻塞其他新批次。
- 只有在模型尚未开始工作，且已确认二进制缺失、认证拒绝、模型无权限等“启动前不可用”时，才可转交下一级。
- 临时网络错误、Codex JSONL `error`、WebSocket→HTTPS 回退不算不可用，不能静默换模型。

这与项目既有要求一致：GLM 做坏的失败包仍由 GLM 自己复审、解决冲突和闭环；三级优先级主要决定新批次
在上一级不可用时由谁接管。以后如需允许半成品跨模型转交，应增加显式策略，而不是暗改语义。

### 4. 生命周期目前只识别 OpenCode

`Start-Agent.ps1` 和 `Stop-Agent.ps1` 的复盘进程谓词只识别 `opencode.exe`。Codex 可能形成
`node/codex.exe` 子进程链，不能按进程名泛杀，因为维护 AI 本身也可能在使用 Codex。

应只识别同时满足以下条件的复盘实例：

- 命令是 `codex exec`；
- 包含 `--json --ephemeral --approve-for-me`；
- `-C` 指向本项目 `knowledge/code_backups/review_work/sts2-review-sandbox-*/repo`；
- 模型和 prompt 都是本次复盘计划。

同一精确谓词要同步用于 Brain orphan cleanup、Start 残留拒绝和 Stop scoped identity。

### 5. stdin 与失败取证

Codex 子进程必须显式使用 `stdin=subprocess.DEVNULL`。官方文档说明：即使命令行已有 prompt，只要 stdin
是 pipe，Codex 仍会把 stdin 追加到输入；继承一个长期不 EOF 的 stdin 可能造成卡住或提示污染。

建议 Codex 使用 `--ephemeral`，避免持续复盘继续扩大本机 Codex rollout（Doctor 当前报告约 4.45 GB）。
与之配套，宿主要把本场完整原始 JSONL tee 到隔离仓的 provider transcript；失败时随 raw sandbox 全量进入
失败包，不能只保留当前 256 KiB tail。隐藏思维链本来就不会暴露；可保存的是 reasoning summary、工具调用、
文件改动、错误和最终消息。

## 建议配置

```json
"review_model_chain": [
  {
    "key": "glm-flash",
    "priority": 1,
    "runner": "opencode",
    "model": "opencode-go/glm-5.3-flash",
    "variant": "max",
    "every_runs": 1
  },
  {
    "key": "luna-max",
    "priority": 2,
    "runner": "codex",
    "model": "gpt-5.6-luna",
    "reasoning_effort": "max",
    "approve_for_me": true,
    "sandbox": "workspace-write",
    "every_runs": 1
  },
  {
    "key": "kimi-k3",
    "priority": 3,
    "runner": "opencode",
    "model": "kimi-for-coding/k3",
    "every_runs": 5
  }
],
"runner_bins": {
  "opencode": "opencode",
  "codex": "codex"
}
```

缺少 `review_model_chain` 时，从现有 `preferred_models + model` 合成旧两级链，保证可回滚。OpenCode 的
`variant=max` 与 Codex 的 `reasoning_effort=max` 必须是两个字段，不能继续只靠 `@max` 字符串猜语义。

Codex 命令建议固定为：

```text
codex exec
  --model gpt-5.6-luna
  -c model_reasoning_effort="max"
  --sandbox workspace-write
  --approve-for-me
  --json
  --ephemeral
  -C <隔离仓>
  <短引导 prompt>
```

必须使用可以读写隔离仓的 `codex exec`，不能改成只审不改的 `codex review`。

## 最小实现结构

先不必拆大文件，可在 `llm_review.py` 内加入：

```text
ReviewPlan
  key / priority / runner / model
  variant / reasoning_effort / every_runs

RunnerAdapter
  probe(plan)
  build_command(plan, sandbox_repo, prompt)
  translator()
  bind_workdir(command, sandbox_repo)
```

OpenCode 与 Codex 只负责启动和翻译输出；后续全部进入同一条公共闭环。队列和失败包至少持久化：

```text
backend_key, priority, runner, model, variant, reasoning_effort,
every, retry_same_model, attempt_started_at, model_work_started
```

现有 `preferred_model_state.json` 可继续按稳定 `backend_key` 记录冷却，不要为了命名完美另起一套在线状态。
`pending_restart.json` 与 `boot_review_commit` 验证的是最终 commit 是否被新 Brain 加载，与 provider 无关，无需扩维。

## Codex JSONL 与 watchdog

新增 `CodexJsonTranslator`，兼容 `thread.* / turn.* / item.* / error`：

- `error` 只作为运输层诊断显示和保全，不能单独判失败或触发 cooldown。
- 最终成功只信进程退出码、隔离工作树 diff、selfcheck 和公共提交闭环。
- 原始任何字节继续刷新 liveness；WebSocket 重连事件不会误撞 15/30 分钟阈值。
- 非 JSON stderr 有界透传；item ID 使用有界去重表。
- 完整原始 JSONL 单独保全，直播流只显示可读摘要。

已观察到的约 100 秒 WebSocket 回退低于 15 分钟告警，不需要为 Luna 修改全局 watchdog。它应记录为
provider startup latency；等 Codex CLI 升级后重新 canary，再判断能否消除此延迟。

## 必测矩阵

1. 旧两级配置兼容，新三级顺序正确。
2. GLM 正常；GLM 冷却转 Luna；前两级不可用后 Kimi 按 5 局合批。
3. `enqueue_review()` 不调用任何外部模型探测。
4. Codex 参数、`DEVNULL`、隔离工作目录准确。
5. 五个 WebSocket `error` 后 `rc=0` 仍判成功，不进入 cooldown。
6. 100 秒模拟运输延迟不触发 15/30 分钟 watchdog。
7. `retry_same_model=true` 真正生效，sticky 包不阻塞新批次。
8. Codex 允许文件、cache 和拒绝文件仍走现有完整取证规则。
9. Start/Stop 精确命中复盘 Codex，不命中用户或维护 AI 的其他 Codex。
10. Codex 运行时代码改动照常 commit、push、发布 pending marker，并在安全菜单重载。
11. 冷启动、重复 Start、活动复盘 Stop、`-KeepGame` 与恢复旧两级配置全部通过。

## 推荐上线顺序

1. 直播中在隔离 clone 实现 adapter、队列状态机和假 JSONL 测试。
2. 先提交兼容代码，但保持旧配置生效；当前 Brain 不重启。
3. 下播后等待正在运行的 GLM 批次闭环。
4. 修改 `review_model_chain`，统一 `Stop-Agent -KeepGame` / `Start-Agent -SkipDeploy`。
5. 验证单 runner/Brain、8080、dashboard、run commit/push、失败包队列和无残留 Codex。
6. 不人为让生产 GLM 失败；等待真实冷却/不可用时观察 Luna 自然接管。
7. 首次 Luna 成功闭环后，再决定是否把功能视为稳定默认。
